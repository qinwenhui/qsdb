# 列裁剪穿透 `Window`（设计稿）

> **状态**：**已实现**（2026-10-16，`sql/exec_builder.rs`）。落地过程中**本稿被修正了三处**
> —— §三 H3（"整段平移"是错的）、§4.2（两段规则）、§4.3（放行面比原稿宽两条）。
> 都是"写下来才发现"的，**照原稿写会静默错值**。实测量见 §五。
> **起因**：2026-10-16 拿真实业务表比对 DuckDB 时，
> 发现**任何带窗口的查询都慢 5–6×**，根因是列裁剪被一刀切关掉。
>
> **给接手的人**：这份文档是自包含的。§一 复现、§二 根因、§三 为什么不能草率修
> （我试过、被证伪）、§四 设计、§五 验收。

## 一、症状与复现（全在 `基准机`，真表）

**表**：`/home/bench/qsdb-dnl` 的 `t_result_unit`
（174 万行 × **28 列，其中 20 个字符串列**）。
**探针**：`sql_bench <库目录> <SQL 文件> [轮数]`（进程内计时，绕过 CLI 启动噪声）。

```
# 同一张表、同一个聚合，只差一个窗口列
1  SELECT pdate, sum(fee) AS f FROM t_result_unit GROUP BY pdate
2  SELECT pdate, sum(fee) AS f, count(*) OVER (ORDER BY pdate) AS c FROM … GROUP BY pdate
```

| 表 | 无窗口 | 加窗口 | 增量 |
|---|---|---|---|
| 174 万行 | **47 ms** | **288 ms** | **+240 ms** |
| 10 万行（`tiny`） | 6.2 ms | 31.4 ms | +25 ms |

**两条决定性的对照**：

1. **窗口本身不慢**：把聚合结果物化成表 `agg15`（15 行）再跑同一个窗口
   → **0.16 ms**。⇒ 那 240 ms **不在窗口**。
2. **开销随行数增长**（10 万 +25ms → 174 万 +240ms）⇒ 是**扫描按行数多干活**。

**`perf` 佐证**（`QSDB_SCAN_SERIAL` 无关；用带符号的 `bench-release` 构建）：

| | 无窗口 | 加窗口 |
|---|---|---|
| `__memcpy` | 11.7% | **25.0%** |
| `extend_from_dictionary`（**字符串列字典解码**） | — | **15.6%** |

⇒ **多读了一堆列**，其中字符串列最贵。

## 二、根因

`crates/qsdb/src/sql/exec_builder.rs::prune_decision`（**改动前**；现在换成了
`if has_window_node(plan) && !phase1_window(plan)`）：

```rust
pub fn prune_decision(plan: &LogicalPlan) -> Option<(Vec<String>, Vec<String>)> {
    if has_window_node(plan) {
```

**遇到 `Window` 即 `true`** ⇒ `Window(…)` 之上的任何节点都会触发这条早退。

## 三、★ 为什么不能"把 guard 删掉"（我试过，被自己的测试当场证伪）

去掉 guard + 让 `rewrite_plan` 的 `Window` 臂过 `exprs_are_in_table_space` 闸门 +
补 `exprs_are_in_table_space` 认得 `Window` —— 结果：

```
error: type error: decimal window arg downcast failed (internal)
```

**根因是两条独立的"索引空间"hazard，guard 在掩护的是第二条：**

### H1 名字撞车（现有闸门已能挡）

`Window(Aggregate(Scan))` 里，窗口的 `ORDER BY pdate` 引用的是**聚合输出**的 `pdate`，
但 `pdate` **名字碰巧也是表列名**。而 `rewrite_expr` 的判据是**按名**：

```rust
let is_table_col = all.iter().any(|a| a.eq_ignore_ascii_case(name.as_str()));
idx: if is_table_col { mapping[*idx].unwrap_or(*idx) } else { *idx }
```

⇒ 会拿**聚合空间**的 idx 去查**表**映射 ⇒ 指到隔壁列。
→ 由 `exprs_are_in_table_space` 解决：`Window(Aggregate(…))` 的输入不是表 ⇒ 不重映射。

### H2 ★ 窗口**追加列** ⇒ 窗口之上整体左移（**这才是真难点**）

`Window` 的输出 schema = **输入列 ++ 窗口列**（见 `WindowExec::new`）。
扫描被裁掉 K 列 ⇒ 窗口的**输入变窄 K** ⇒ **窗口输出整体左移 K**。

而窗口**之上**的节点引用的是**窗口输出列**，它们的 idx 是按**原宽度**算的：

```sql
SELECT sum(d) OVER () AS s FROM t LIMIT 1     -- 计划：Limit(Project(Window(Scan)))
```

Project 引用的是窗口的输出列 `sum(d)`（idx = 扫描宽度）。这个名字**不是表列名**
⇒ `rewrite_expr` **原样保留 idx** ⇒ 裁完就**悬空**（列数对不上 / 指到别处）。

**⇒ 删 guard 不够：必须让 `rewrite_plan` 知道"窗口之下裁了 K 列"，
并把窗口之上所有引用一起平移。**

**为什么它不"就在手边"**：`rewrite_plan` 是**自上而下**递归的，而 K 要到**扫描处**
才定得下来 ⇒ 信息要**反向传播**。这正是本仓被咬过三次的那个坑
（`tests/projection_space.rs` 就是为它写的；`rewrite_plan` 的注释原话：
*"宁可少裁一列，也不能把表达式指到隔壁列上去"*）。

### H3 ★ 第二处陷阱：窗口之上的表达式**不是**整体平移（**实现时才暴露**）

**本稿 §4.2 的第一版草稿是错的**，照它写就炸 —— 而且炸得很安静：

> 第一版按"凡是窗口之上的表达式，idx 一律 −K"实现。
> `window_frame` 的 `count_星号数行而_count_列数非空` 当场变红：
> 首列变成**恒定的 `1`**（本该是 1,2,3,4,5）。

窗口输出 = **输入 ++ 窗口列**，所以窗口之上的表达式**分两段**，两段下场不同：

| 位置 | 是什么 | 怎么改 |
|---|---|---|
| `< 表宽` | **透传列**：窗口原样带下来的输入列 | 位置**仍是表列序** ⇒ 按 `mapping` |
| `>= 表宽` | **追加的窗口列**（`sum(x)`/`count(*)`） | 在**尾部** ⇒ 整体左移 K |

`SELECT i, count(*) OVER (PARTITION BY g …) FROM n` 里，透传的 `i` 在窗口输出里是第 1 位，
"整段 −1" 把它减成 0 ⇒ 读到了隔壁的 `g`（而 `WHERE g = 1` 让 `g` 恒为 1，
看起来**像是一列正常的值**，不打眼）。

**⇒ 判据是"位置"，不是"整个空间挪了多少"。** 分界线用**表宽**是精确的而非近似：
能走到这一支 ⟺ 窗口的输入是一条表空间链 ⇒ 它的输出宽度**就是**表宽。

## 四、设计

### 4.1 核心概念：给每个节点标"表达式活在哪个空间"

现有代码已经有半个模型（`exprs_are_in_table_space` = 二元：表空间 / 不是表空间）。
H2 要求把它推广成**带平移量的一维坐标**：

> 每个节点 N 的表达式，其 `Column.idx` 活在 **N 的直接输入的输出空间**里。
> 那个空间相对"表空间"可能有一个**平移量** `shift`（因为中间有节点变过 schema）。

- 扫描叶：空间 = 表空间，`shift = 0`
- `Window` 的输出空间 = 输入空间 ++ 追加列 ⇒ 对**落在输入前缀里的** idx，
  平移量 = 输入的平移量；对**追加列**，平移量 = 输入宽度 − K
- `Aggregate` / `Project`：输出是**全新空间**（列数、含义都变）⇒ 之上的一律**不按表映射**
  （现有行为，见 `exprs_are_in_table_space`）

### 4.2 实现形态（建议）

`rewrite_plan` 加一个参数 `k`（本次裁掉的列数），再加一个**只问结构**的量：

```
output_shift(节点) = 该节点**输出**的列序相对原计划左移了几列
    Scan/ExternalScan/CsvScan          → k
    Filter/Sort/Limit/Distinct/Window  → 继承输入   // Window 只是**在尾部追加**
    semi/anti Join                     → 继承左子   // 输出 = 左 schema
    Aggregate/Project/其它 Join        → 0          // **另起**列空间，宽度列序都与裁剪无关
```

于是"本节点的表达式该怎么改"三选一，**只看它输入的那一个数**：

```
space = output_shift(本节点的输入)              // 无输入（叶）⇒ 0
   space == 0                        ⇒ 原样（列空间没动）
   space > 0 且 输入是表空间          ⇒ 按 mapping 换算（`exprs_are_in_table_space` 那个闸门）
   space > 0 且 输入不是表空间        ⇒ 只可能是窗口输出空间 ⇒ **分两段**（见 H3）：
                                          idx <  表宽 ⇒ mapping
                                          idx >= 表宽 ⇒ idx − space
```

第三条**不需要按列名判**（按名判是 H1）—— 位置本身就是判据。

⚠️ 原稿这里写的是"input 是 Window ⇒ idx **一律** −K"，**错的**，见 H3。

另外两处必改（原稿只说了一半）：

- `Window` 臂原先**无条件**按名重写 `partition_by`/`order_by`（H1），
  且 `window_fns` **直接 `clone()`**（`Window(Scan)` 的参数列会悬空）
  ⇒ 两者都要走上面那套判据（新增 `map_window_fn`）。
- `build_inner` 的 `Window` 臂**硬编码 `scan_proj = None`** 传给输入 ——
  裁剪一旦开着，那会让扫描读回**全宽**批，而重写过的 idx（如 `pdate` → 0）
  就指到**另一列**上，且不报错。必须改成 `scan_proj.clone()`。

其中 `k = all.len() - proj.len()`，由 `prune_decision` 一并算出。

### 4.3 ★ 分阶段：**先只放行一种形状**（本仓纪律：宁可少裁一列）

第一阶段只对下面这个形状开启裁剪，**其余形状保持现状（`return None`）**：

```
( Limit | Project | Sort(Project(…)) )*
      Window( Aggregate?( Filter?( Scan ) ) )
```

判据（`phase1_window`，显式写死、可断言）：

1. 计划里那条通向 `Window` 的**链上只出现** `Limit`/`Project`/`Sort`；
2. `Sort` 只认**紧贴在一个 `Project` 之上**的那种（`Sort(Project(…))`）；
3. 窗口**之下**是 `Scan`/`Filter`/`Aggregate`（各自可再套同一条链）。

**落地时比原稿放宽了两条，都有独立理由：**

| 放宽 | 为什么安全 |
|---|---|
| 之上多认 `Sort`（原稿只 `Project`/`Limit`） | 排序键活在 `Project` 的输出空间里，而那个空间**位置与含义都不变**（投影式被重写了，产出列没变）⇒ `Sort` 臂"原样保留键"的约定仍然成立。**裸 `Sort(Window(…))` 不接受** —— 那时键要按两段规则改，而 Sort 臂是不改的 |
| 之下多认 `Filter`（原稿只 `Aggregate?(Scan)`） | `Filter` 恒等 schema，谓词与 `Scan` 同处一个列空间 |

> **`Sort` 这条不是可选项**：真表上最自然的写法就是尾巴挂 `ORDER BY pdate`。
> 实测（§五）裸 `Sort` 不放行时那三条查询**一动不动**（223 ms），放行后 41 ms。

其余形状（之上还有 `Aggregate`/join、多个 `Window`、窗口接 join）**继续关着**，
并在 `phase1_window` 的文档里写明"为什么这里没开"。

## 五、验收（✅ 全部通过，2026-10-16）

新增回归：**`tests/window_prune.rs`（8 条）**。核心是**两条路对撞** ——
同一条查询跑两遍：一遍走裁剪（投影里只写用得着的列），一遍不走
（把所有列都写进投影 ⇒ `proj == all` ⇒ `build()` 直接跳过重写），**逐值逐行**必须一致。
另有一条**钉住裁剪确实发生**（`prune_decision` 直接断言）—— 否则对上那半会因为
"两条路其实都没裁"而**永远绿**。反例（Aggregate 在上 / 两个 Window / 接 join /
Distinct 在上）各断言一次 `None`。

既有安全网 `projection_space`(5) / `window_frame`(13) / `window_decimal`(8) /
`order_by_prune` 全绿；`sh tools/check.sh` **ALL GREEN**。

### 真表实测（`基准机`，174 万行 × 28 列，其中 20 个字符串列，3 轮中位）

| | 改前 | 改后 |
|---|---|---|
| `GROUP BY pdate`（无窗口，= 基线） | 40–47 ms / **7 MB** | 40–47 ms / 7 MB |
| `+ count(*) OVER (ORDER BY pdate)` | **268 ms / 50 MB** | **41 ms / 8 MB** |
| 同上，尾巴挂 `ORDER BY pdate` | **223 ms** | **41 ms** |
| 小表（`tiny`，14 行）加窗口 | 35 ms | 5.8 ms |

**窗口开销整条消失了**：加窗口的查询现在与"不加窗口的同一个聚合"同档
（41 vs 41ms，8 vs 7MB）—— 与第 ① 节"物化后跑窗口只要 0.16ms"的推断吻合。

**值一致性**：4 个查询文件、16 条查询，**改前改后的结果指纹（digest，含行序）逐条完全相同**。
这是本次最硬的一条 —— 真表 28 列、20 个字符串列、核心列是 `DECIMAL(30,8)`，
错列取错的现象在肉眼上**看不出来**。

（`基准机` 上还跑着 Hadoop/Spark，绝对数字看量级与相对关系。）

## 六、明确不做

| 不做 | 理由 |
|---|---|
| **一次放开所有形状** | H2/H3 要处理 `Aggregate(Window(…))`、多 Window、Window 接 join、裸 `Sort(Window(…))` —— 每一个都要单独论证空间；本仓在这个坑上已栽三次，**宁可少裁一列** |
| 把 `Window` 改成"不追加列" | 追加列是它的语义（`row_number()` 这类要出新列），改不了 |
| 用名字判据在窗口之上重映射 | 正是 H1：名字会撞车 |
| 靠"结果对就行"验收 | 这类优化的失败模式是**静默指错列**（少裁一列只是变慢、不是变错；裁错一列是**错值**）⇒ 必须有**两条路对撞**的值断言 |
