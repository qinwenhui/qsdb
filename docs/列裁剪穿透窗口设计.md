# 列裁剪穿透 `Window`（设计稿）

> **状态**：设计定稿，**尚未实现**。
> **起因**：2026-10-16 拿真实业务表（电力日清结算明细）比对 DuckDB 时，
> 发现**任何带窗口的查询都慢 5–6×**，根因是列裁剪被一刀切关掉。
>
> **给接手的人**：这份文档是自包含的。§一 复现、§二 根因、§三 为什么不能草率修
> （我试过、被证伪）、§四 设计、§五 验收。

## 一、症状与复现（全在 `.14`，真表）

**表**：`/home/qctc/qsdb-dnl` 的 `t_dnl_day_24result_unit`
（174 万行 × **28 列，其中 20 个字符串列**）。
**探针**：`sql_bench <库目录> <SQL 文件> [轮数]`（进程内计时，绕过 CLI 启动噪声）。

```
# 同一张表、同一个聚合，只差一个窗口列
1  SELECT pdate, sum(fee) AS f FROM t_dnl_day_24result_unit GROUP BY pdate
2  SELECT pdate, sum(fee) AS f, count(*) OVER (ORDER BY pdate) AS c FROM … GROUP BY pdate
```

| 表 | 无窗口 | 加窗口 | 增量 |
|---|---|---|---|
| 174 万行 | **47 ms** | **288 ms** | **+240 ms** |
| 10 万行（`tiny`） | 6.2 ms | 31.4 ms | +25 ms |

**两条决定性的对照**：

1. **窗口本身不慢**：把聚合结果物化成表 `agg15`（15 行）再跑同一个窗口
   → **0.16 ms**。⇒ 那 240 ms **不在窗口**。
2. **开销随行数增长**（10 万 +25ms → 174 万 +240ms）⇒ 是**扫描按行数多干活**。

**`perf` 佐证**（`QSDB_SCAN_SERIAL` 无关；用带符号的 `bench-release` 构建）：

| | 无窗口 | 加窗口 |
|---|---|---|
| `__memcpy` | 11.7% | **25.0%** |
| `extend_from_dictionary`（**字符串列字典解码**） | — | **15.6%** |

⇒ **多读了一堆列**，其中字符串列最贵。

## 二、根因

`crates/qsdb/src/sql/exec_builder.rs::prune_decision`：

```rust
pub fn prune_decision(plan: &LogicalPlan) -> Option<(Vec<String>, Vec<String>)> {
    if has_window_node(plan) {
        return None;          // ← 一刀切：有计划里有 Window ⇒ 整条列裁剪关闭
    }
    let mut used = Vec::new();
    collect_plan_columns(plan, &mut used);
    …
}
```

`None` ⇒ 扫描读**全部 28 列**。

`has_window_node`（同文件）只沿 `Filter/Project/Aggregate/Sort/Limit/Distinct` 往下看，
**遇到 `Window` 即 `true`** ⇒ `Window(…)` 之上的任何节点都会触发这条早退。

## 三、★ 为什么不能"把 guard 删掉"（我试过，被自己的测试当场证伪）

去掉 guard + 让 `rewrite_plan` 的 `Window` 臂过 `exprs_are_in_table_space` 闸门 +
补 `exprs_are_in_table_space` 认得 `Window` —— 结果：

```
error: type error: decimal window arg downcast failed (internal)
```

**根因是两条独立的"索引空间"hazard，guard 在掩护的是第二条：**

### H1 名字撞车（现有闸门已能挡）

`Window(Aggregate(Scan))` 里，窗口的 `ORDER BY pdate` 引用的是**聚合输出**的 `pdate`，
但 `pdate` **名字碰巧也是表列名**。而 `rewrite_expr` 的判据是**按名**：

```rust
let is_table_col = all.iter().any(|a| a.eq_ignore_ascii_case(name.as_str()));
idx: if is_table_col { mapping[*idx].unwrap_or(*idx) } else { *idx }
```

⇒ 会拿**聚合空间**的 idx 去查**表**映射 ⇒ 指到隔壁列。
→ 由 `exprs_are_in_table_space` 解决：`Window(Aggregate(…))` 的输入不是表 ⇒ 不重映射。

### H2 ★ 窗口**追加列** ⇒ 窗口之上整体左移（**这才是真难点**）

`Window` 的输出 schema = **输入列 ++ 窗口列**（见 `WindowExec::new`）。
扫描被裁掉 K 列 ⇒ 窗口的**输入变窄 K** ⇒ **窗口输出整体左移 K**。

而窗口**之上**的节点引用的是**窗口输出列**，它们的 idx 是按**原宽度**算的：

```sql
SELECT sum(d) OVER () AS s FROM t LIMIT 1     -- 计划：Limit(Project(Window(Scan)))
```

Project 引用的是窗口的输出列 `sum(d)`（idx = 扫描宽度）。这个名字**不是表列名**
⇒ `rewrite_expr` **原样保留 idx** ⇒ 裁完就**悬空**（列数对不上 / 指到别处）。

**⇒ 删 guard 不够：必须让 `rewrite_plan` 知道"窗口之下裁了 K 列"，
并把窗口之上所有引用一起平移。**

**为什么它不"就在手边"**：`rewrite_plan` 是**自上而下**递归的，而 K 要到**扫描处**
才定得下来 ⇒ 信息要**反向传播**。这正是本仓被咬过三次的那个坑
（`tests/projection_space.rs` 就是为它写的；`rewrite_plan` 的注释原话：
*"宁可少裁一列，也不能把表达式指到隔壁列上去"*）。

## 四、设计

### 4.1 核心概念：给每个节点标"表达式活在哪个空间"

现有代码已经有半个模型（`exprs_are_in_table_space` = 二元：表空间 / 不是表空间）。
H2 要求把它推广成**带平移量的一维坐标**：

> 每个节点 N 的表达式，其 `Column.idx` 活在 **N 的直接输入的输出空间**里。
> 那个空间相对"表空间"可能有一个**平移量** `shift`（因为中间有节点变过 schema）。

- 扫描叶：空间 = 表空间，`shift = 0`
- `Window` 的输出空间 = 输入空间 ++ 追加列 ⇒ 对**落在输入前缀里的** idx，
  平移量 = 输入的平移量；对**追加列**，平移量 = 输入宽度 − K
- `Aggregate` / `Project`：输出是**全新空间**（列数、含义都变）⇒ 之上的一律**不按表映射**
  （现有行为，见 `exprs_are_in_table_space`）

### 4.2 实现形态（建议）

`rewrite_plan` 加一个参数：`shift: usize`（**本节点表达式的 idx 相对表空间的平移量**，
只在"表达式确实活在某个被裁过的输出空间"时非零）。

```
rewrite_plan(plan, mapping, all, shift):
    match plan:
        Scan → 只换 def（列裁剪落在它身上）；它自己的 predicate 按名寻址，不受影响
        Project/Filter/Sort/Limit/Distinct/Aggregate →
            input' = rewrite_plan(input, mapping, all, shift_of_child(plan))
            exprs' = 按"本节点的表达式活在 input 的输出空间"重写：
                     · input 是 Window ⇒ idx 一律 −K（**不按名判**，见 H1）
                     · 否则沿用现有 exprs_are_in_table_space 闸门
        Window → input' = rewrite_plan(input, …, 0)   // 窗口的表达式活在它输入的空间
                 partition_by / order_by / window_fns 按同一闸门重写
                 （**新增**：`rewrite_window_fn` —— 原先直接 `clone()`，参数列会悬空）
```

其中 `K = all.len() - proj.len()`（本次裁掉的列数），由 `prune_decision` 一并算出。

### 4.3 ★ 分阶段：**先只放行一种形状**（本仓纪律：宁可少裁一列）

第一阶段只对下面这个形状开启裁剪，**其余形状保持现状（`return None`）**：

```
Project( Window( Aggregate?( Scan ) ) )        // 根是 Project / 或窗口就是根
```

判据（在 `prune_decision` 里显式写死、可断言）：

1. 计划里**恰好一个** `Window`；
2. 那个 `Window` 的**直接消费者链**只经过 `Project`（和至多一个 `Limit`）；
3. 窗口**之下**是 `Aggregate?(Scan)`，`plan_scan_def` 认得出。

**这一形状下 H2 是可精确处理的**：窗口之上**只有 Project 一层**，
它的表达式**一律 −K**（不按名判，避开 H1）。

> **多数真实查询正是这个形状** —— 我们这张真表上，三条窗口查询全部落在里面
> （`sum(fee) … GROUP BY pdate` + `OVER (ORDER BY pdate)`）。
> 其余形状（窗口之上还有 Aggregate、多个 Window、窗口接 join）**继续关着**，
> 并在 `prune_decision` 里写明"为什么这里没开"。

## 五、验收

1. **安全网先跑**：`tests/projection_space.rs`（5 条）必须绿 —— 它就是这个坑的回归。
2. **值级**：`tests/window_frame.rs`(13) / `tests/window_decimal.rs`(8) 全绿；
   **外加**一条新用例：`SELECT sum(v) OVER () FROM t` 与不裁剪时**逐值一致**
   （`mapping` 全恒等 vs 真裁——**两条路对撞**，这是本仓对这类优化的标准做法）。
3. **真表复测**（`.14`）：第 ① 节那两条查询，`288ms` 应回到 **~50ms**；
   且与"用 `agg15` 物化后再跑窗口"（0.16ms + 聚合 47ms）的总和对得上。
4. **反例必须仍然拒绝**：给 `prune_decision` 加断言/单测 —— 窗口之上有 `Aggregate`、
   两个 `Window`、窗口接 join 的形状，`prune_decision` **返回 `None`**（不冒险）。
5. **闸门**：`sh tools/check.sh` ALL GREEN。

## 六、明确不做

| 不做 | 理由 |
|---|---|
| **一次放开所有形状** | H2 的"沿树传播平移量"要处理 `Aggregate(Window(…))`、多 Window、Window 接 join —— 每一个都要单独论证空间；本仓在这个坑上已栽三次，**宁可少裁一列** |
| 把 `Window` 改成"不追加列" | 追加列是它的语义（`row_number()` 这类要出新列），改不了 |
| 用名字判据在窗口之上重映射 | 正是 H1：名字会撞车 |
| 靠"结果对就行"验收 | 这类优化的失败模式是**静默指错列**（少裁一列只是变慢、不是变错；裁错一列是**错值**）⇒ 必须有**两条路对撞**的值断言 |
