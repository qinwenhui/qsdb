# 参数化查询设计（**协议已定死**，见 `生态能力契约.md`）

> 定案 2026-10-17。这份文档回答两个问题：**绑在哪一层**（为什么不是别的层），
> 以及**协议长什么样**（这一格一旦从 ⏳ 变 ✅，协议列不许再改）。

---

## 一、绑在哪一层：**内核的绑定器**（不是驱动、也不是 HTTP 层）

| 如果放在… | 会发生什么 |
|---|---|
| **驱动 / 客户端**（字符串拼接） | **注入**，且没有类型检查。这正是本仓现在被迫写进文档的那条："客户端要么自己拼 SQL，**我们不提供转义助手**" |
| **HTTP 层**（`replace($1, 值)`） | 还是字符串替换 = 注入；而且 HTTP 层**没有类型系统** —— `'2026-01-01'` 该是 DATE 还是 Varchar 无从判断 |
| **内核的绑定器** ✅ | 它**同时**握着 AST 与类型：把值做成 **AST 里的字面量节点**（不是文本），类型由协议声明、绑定期校验 |

同档引擎也是这个层次，只是包装不同：PostgreSQL 是 wire 协议层的
`Parse`(带参数 OID) / `Bind` / `Execute`；DuckDB / SQLite 是 `prepare` + `bind`
（嵌入式，库即内核）；ClickHouse HTTP 是 `{name:Type}` + URL 参数。
**共同点是"值永远不变成 SQL 文本"** —— 这是安全性的**全部**来源，也是本设计
唯一不可让步的性质。

---

## 二、协议形态

`POST /api/v1/query` 的请求体**加一个可选字段**（端点、其余字段一概不动）：

```json
{
  "sql": "SELECT * FROM t WHERE g = $1 AND v > $2",
  "params": [10, 3.5]
}
```

**向后兼容**：`params` 缺省 = 现在（没有占位符时行为一字不变）。

### 参数元素：两种写法都收

| 写法 | 含义 |
|---|---|
| `10` / `"abc"` / `true` / `null` | **从 JSON 推类型**（表见 §五） |
| `{"type": "DATE", "value": "2026-01-01"}` | **显式声明类型**（`type` 用 DDL 里那套类型名，走同一个解析器 ⇒ 名字不漂） |

显式是**可选**的，这样手写 HTTP 好用、驱动照 `setInt/setDate` 直传也不用多想；
同时它是"必填类型"的**超集** ⇒ 将来不会因为要加类型而改协议。

**规则**：参数是**位置数组**，`$n` 取 `params[n-1]`。
**个数必须正好覆盖用到的最大序号**（多给、少给都报错，见 §六）。

### 为什么不做会话态（PostgreSQL 那种 prepared statement 句柄）

本库是**无状态 HTTP**：`qsdb-client` 带 keep-alive 复用与重连，CLI 的查询注册表也
是按 query-id 现挂的。语句句柄在这种通道上是地雷（连接一换就失效，连接池一进来
更麻烦）。所以做成"每次请求带 `sql` + `params`"。

将来若要"解析一次、执行多次"，**在服务端加一个按原始 SQL 文本做 key 的计划缓存**
即可 —— 那是纯服务端优化，**协议一个字不用改**（这正是把参数放在请求体而不是
放在会话上的好处）。

## 三、占位符语法

| 写法 | 说明 |
|---|---|
| `$1`, `$2`, … | 位置，**可重复引用**（`WHERE a = $1 OR b = $1` 只传一个值） |
| `?` | 位置，按**源码顺序** = 第 1、2、3…个 `?` |

**同一句里不许混用**（`?` 与 `$n` 同时出现 ⇒ 显式报错）。理由：混用时的语义
（`?` 是否把序号推给 `$n`）没有一个"显然对"的答案，与其定一个微妙的规则，不如禁掉。

### `?` 怎么编号（**实现要点，别改**）

`?` 的序号**必须在绑定**之前**固化成 `$n`**。原因：本仓有"把同一个表达式再走
一遍"的路径（`rebind_over_agg` 的 HAVING/窗口重绑、`group_key_pos` 的试探绑定），
如果在绑定期用"计数器"编号，**重走一次就错位**，值会静默绑到别的占位符上。

固化方式**不写 AST 遍历器**（`Expr` 有几十个变体，漏一个就是静默漏参），而是
**用 sqlparser 自己的 tokenizer**：

1. `Tokenizer::tokenize_with_location()` 拿到全部 token 及其位置；
2. 取 `Token::Placeholder("?")` 的**出现顺序**（tokenizer 已经正确处理了字符串
   字面量、注释、带引号标识符里的 `?` —— 实测都不会被当成占位符）；
3. 按位置从后往前，在**原 SQL 文本的精确字节区间**上把 `?` 换成 `$k`，再解析一次。

⚠️ **`Location.column` 数的是「字符」不是「字节」**（实测：`SELECT '含中文内容', ?`
里那个 `?` 报 `C17` —— 只有按字符数才对得上）。所以换算到字节偏移必须**逐字符走
一遍**，直接拿 column 当字节用会在含中文的 SQL 上错位。

代价：只有用到 `?` 时才多解析一次（`$n` 不额外解析）。

### 能出现在哪些位置（**实测边界**）

| 位置 | 能不能用参数 |
|---|---|
| `WHERE` / `HAVING` / 投影 / `CASE` / `IN (…)` / `LIKE` / 比较 / 算术 | ✅ |
| `LIMIT` / `OFFSET` | ✅ |
| **窗口帧偏移**（`ROWS BETWEEN $1 PRECEDING`）、**`lag/lead` 偏移**（`lag(v, ?)`） | ✅ 这两处在**绑定期之前**从 AST 上直接读整数，绑定器单独认了一次参数 |
| 表名（`FROM $1`） | ✗ 那不是表达式位置 —— 会被当表名去找，报"表不存在"。**不做**（表名参数化是另一件事，且它意味着动态 SQL 形状） |
| `= ANY($1)`（数组参数） | ✗ 本库没有数组类型；`IN ($1, $2)` 照常可用 |

非表达式位置的**报错来自各自原有的检查点**（不是"静默当成别的东西"）。

## 四、绑定流程

```
HTTP body(params) ──► 反序列化 + 类型化 → Vec<Literal>
                          │
SQL ──► (若含 ?) tokenizer 固化 ──► parse ──► translate
                          │                        │
                          └──── ParamScope ────────┘
                                   bind_expr 遇 Placeholder("$n")
                                     → 查作用域 → PhysExpr::Lit(literal)
```

- 参数作用域照抄本仓已有的 `CteScope` 写法（thread-local + RAII `Drop` 清空）——
  绑定发生在查询自己的线程上，嵌套子查询共享同一份参数（本来就该共享）。
- 绑定结果就是一个**普通字面量**，所以**下游一个字都不用改**（类型检查、常量折叠、
  下推、溢出……全自动继承）。

## 五、类型映射

### 从 JSON 推（没写 `type` 时）

| JSON | 推成 | 说明 |
|---|---|---|
| `null` | 未定型 NULL | 与任何列都比得通（三值语义） |
| `true` / `false` | Boolean | |
| 整数 | Int64 | 超出 `i64` 范围 ⇒ 报错并建议显式写 `DECIMAL` |
| 小数 | Float64 | |
| 字符串 | Varchar | 与**不带参数**时写 `'…'` 的规则完全一致：比 DATE/TIMESTAMP 列时按日期/时间文本解析（解析不了就报错），比数值列则**报类型错误**（不静默转换） |

> ⚠️ 一条实测澄清：字符串推成 Varchar 后，**时间列的日期文本照样能用**
> （`WHERE d = $1` 传 `"2026-01-01"` 是好的，传 `"不是日期"` 会明确报
> "cannot parse as DATE"）。所以显式 `type` 主要用在两处：**DECIMAL 的精度**
> 与 **BINARY 的编码** —— 不是"日期必须显式"。

### 显式 `type` 认哪些名字

**与 DDL 用同一套类型名、同一个解析器**（`BIGINT` / `INT` / `DOUBLE` / `FLOAT` /
`VARCHAR` / `DATE` / `TIMESTAMP` / `DECIMAL(p,s)` / `BOOLEAN` …）——
名字不会两边漂。写错名字 ⇒ 报错。

值的格式按类型：整数/浮点给 JSON 数字（也收字符串，便于大数保精度）；
`DATE` 给 `"YYYY-MM-DD"`；`TIMESTAMP` 给 `"YYYY-MM-DD HH:MM:SS[.fff]"`；
`DECIMAL` 建议给**字符串**（保精度）；`BINARY` 给十六进制字符串。

## 六、错误面（**全部显式**）

| 情况 | 处理 |
|---|---|
| `$n` 越界（`params` 不够） | 报错，点明"第 n 个参数缺失" |
| 给了多余的参数 | 报错（静默忽略 = 调用方以为在防注入、其实没绑上） |
| `?` 与 `$n` 混用 | 报错 |
| 参数类型与用法对不上（如 `v = $1` 里 v 是 BIGINT、参数是字符串） | 绑定期**类型错误**（不是运行期） |
| 显式 `type` 名字不认识 / 值转不过去 | 报错，点明是第几个参数 |
| 占位符出现在非表达式位置 | 各自的检查点显式拒 |
| 没给 `params` 却写了占位符 | 报错（不能静默当 NULL！） |

**没有"静默当 NULL"这一档** —— 那是本仓最忌讳的失败模式。

## 七、安全性（本设计的存在理由）

值**从不进入 SQL 文本**：它在绑定期变成一个**字面量节点**。所以

```sql
-- 参数值 = "'; DROP TABLE t; --"
SELECT * FROM t WHERE s = $1
```

里那个值是 `Literal::Utf8("'; DROP TABLE t; --")`，**是一个字符串数据**，不是可执行
文本。**验收里必须有一条专门钉这个**（参数里放 SQL 元字符，跑出来是数据、表还在）。

`?` 的文本固化只改 `?` 这**一个字节**（tokenizer 给的位置），不碰任何值。

## 八、驱动侧怎么映射（给生态）

| 驱动 API | 映射 |
|---|---|
| JDBC `setInt(1, 10)` | `params[0] = 10`（`?` 可直接透传，服务端自己编号） |
| JDBC `setDate(1, d)` | `params[0] = {"type":"DATE","value":"2026-01-01"}` |
| ODBC `SQLBindParameter` | 同上两行（按 `ValueType` 决定要不要带 `type`） |
| JDBC `setNull(1, ...)` | `params[0] = null` |

**驱动不需要改写 SQL**（`?` 服务端认）—— 这正是不选"`$n` only"的原因：
省掉每个驱动各写一个"跳过字符串字面量里的 `?`"的改写器（那是驱动侧最容易出的
bug）。

---

## 九、本设计**不做**的

- **会话态 prepared statement 句柄**（§二末：理由 + 替代路径）
- **服务端计划缓存**（同上；接口已为它留好，不用改协议）
- **具名参数**（`:name`）。协议面是**位置数组**，所以具名可以在驱动侧翻译成
  `$n` 而不动协议 —— 真要做时不用重开协议。
