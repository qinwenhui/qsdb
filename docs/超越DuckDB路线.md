## 一、先认清：我们赢在哪、输在哪

> **数字一律看 [`真机基准对账.md`](真机基准对账.md)**（同轮同机对照表 + 逐格根因）。
> 这里只留**性质**——那部分不随时间过期。

| 用例 | 性质（**当前谁赢看对账文档**） |
|---|---|
| simple_count | **少干活**（元数据短路）—— 结构性优势 |
| simple_topn | **少干活**（有界 TopN，不全排） |
| simple_distinct | **要干活**：逐行编码/哈希的常数差 |
| simple_filter / group | 都用向量化；我们靠**并行聚合** |
| complex_cte | 接近 |
| complex_window | ✅ **列裁剪原先被窗口一刀切挡住 ⇒ 读全部列**（2026-10-16 闭环：`tests/window_prune.rs`、`docs/列裁剪穿透窗口设计.md`）。"整分区物化 + 单线程"那条**已被实测排除**（物化后跑窗口只要 0.16ms）—— 细节见 `真机基准对账.md` |
| complex_join_group / three_way | **每行成本**（probe 逐行）+ 建侧 |
| import_parquet | 写段 |
| import_csv | **CSV 解析** |
| export_parquet | ✅ **已有导出原语**（A3 `COPY … TO`，分块并行编码） |
| export_csv | ✅ **已有导出原语**（`FORMAT CSV`，分块并行格式化 + 按序写单文件） |

**规律（一句话）**：**我们赢在"少干活"，输在"要干活但没并行 / 没原语"。**
DuckDB 是 morsel 驱动的**全算子并行**流水线；我们的算子与写路径历史上多是单线程串行
——在 16 核上天然让出一截吞吐。

所以"超过 DuckDB"的主线不是调参数，而是**把并行补齐，并继续扩大"少干活"的优势**。

#### P1⑩ 的落地方案（2026-10-14 设计定稿 → **同日晚已全部落地**，`4cba9fe` / `753a330`）

> **状态：已实现**。`simple_distinct` 2.900s/767MB → **2.407s/586MB**，
> 相对 DuckDB 14.3× → **11.9×**（闸门 0 FAIL，`.14` `suite-h6.log`）。
> 三步是这么分的：第一步（绑定层改写）与第二步（融合计数节点）都做了；
> 第三步（与其它聚合混用）**仍然显式拒绝**——一次去重会改掉不带 DISTINCT 那些
> 聚合的输入，宁可报错不硬猜。
> **剩下的 11.9× 不在这一步能解决的范围内**：它是"500 万行字符串 × 逐行编码/哈希"
> 的常数差（与 join 那几格同源），不是"少干活"能省的。
> ⚠️ 换过尺子：bench 那一格从"等价改写"改成原生写法 ⇒ 与上一轮该格数字不可直接比。

**第一步：绑定层把拒绝改成等价改写**（关掉能力缺口——BI 工具天天用，拒着会痛）。

    count(DISTINCT x)                   → aggregate{ aggs: [count(x)], input: Distinct{keys: [x]} }
    count(DISTINCT x) … GROUP BY g      → aggregate{ group:[g], aggs:[count(x)],
                                                    input: Distinct{keys: [g, …, x]} }

⚠️ **语义坑（最容易写错的一处）**：改写后必须是 **`count(x)` 而不是 `count(*)`**。
`count(DISTINCT x)` **跳过 NULL**，而 `count(*)` 会把 NULL 组也算一行 ✗。
带上分组列 `g` 进 DISTINCT 键之后，`count(x)` 数到的正是"每组里非空 x 的不同值个数"
—— 与 `count(DISTINCT x)` 逐值等价 ✓。

`sum`/`avg(DISTINCT x)` 同一套（它们本来也跳过 NULL ✓）；`min`/`max(DISTINCT x)` 里
DISTINCT 是恒等变换，直接去掉即可。

**第二步（速度）：把 `Aggregate(Count) ← Distinct ← Scan` 融成一个单遍计数节点。**

现成的先例是 `JoinCountExec`（`count(*) over INNER JOIN` 的计数下推）——同一套路子：
识别形状 → 换成一个专用节点 → 不物化中间结果。这里同样：不输出 250 万行、
不做第二遍聚合，只维护一个"已见值集合"的计数。

⚠️ 集合必须**带真值**（不能只存 64 位哈希 —— 那是有碰撞概率的静默错值）。
建议复用 `GroupTable` 的 key 编码 + `fxhash → 桶 → key_arena` 那套（已被
`estimated_bytes` 的增量记账优化过），但**不要建 `group_lits`**：
250 万字符串组里，`group_lits` 的 `Literal` 槽 + 每组的 `String` 克隆正是
"组表仍胖"（767MB vs 对手 400MB）的大头，而编码后的 key **已经在 `key_arena` 里**。

**第三步（可选）：与其它聚合混用 + 走溢出**。若与 `sum`/`avg` 等混用，就回到
"GroupTable 新增一个聚合状态种类"的老路（`init_cols`/`update`/`finalize`/
`merge_subset`/`spill` 五处都要覆盖——**那是 Bug C 的老巢**，务必带契约测试）。
只在"纯 count(DISTINCT)"上做专用节点，可以完全避开这条风险路径。

### P1⑪ 字符串 DISTINCT 的**哈希分区并行**（2026-10-14 设计定稿，尚未写码）

**为什么是这一格**（写于 2026-10-14，当时是**全表唯一两位数缺口**；**当前差距看 `真机基准对账.md`**）：
`perf` 已经把它剖清楚了（见 `docs/真机基准对账.md` §二之四）：
剩余 **79% 全在哈希表本身**（查表 41 + 循环体 24 + 插入 14），**分布很平、
没有单点可打**。⇒ 只能靠"把总量摊到多核"，而不是再找一个热点。

**与已被否决的"行分片 + 键并集"的本质区别**（别再混为一谈）：

| | 切分维度 | 合并 | 结论 |
|---|---|---|---|
| 旧：行分片 | **行** | 各片键集**相交** ⇒ 必须**求并集**（串行重灌 500 万键） | ❌ 实测更慢 |
| **新：哈希分区** | **键**（`hash(key) % N`） | 各分区键集**不相交** ⇒ **计数直接相加** | 待实测 |

同一个键的字节相同 ⇒ 哈希相同 ⇒ 必然落同一分区 ✓ 所以"相加"是**精确正确**的，
不是近似。

#### 做法（两相，刻意选最简单的形态）

**相 1（顺序）**：逐批读输入，逐行算 `part = fxhash(编码后的键) % N`，
把**编码后的键字节**追加进该分区的 arena（`Vec<u8>` + `Vec<(u32,u32)>` spans，
与 CSV 那次的形态同款）。这批是唯一的额外内存：5M 行 × ~19 字节 + spans 8 字节
≈ **135MB**。

**相 2（并行）**：`parts.into_par_iter().map(|arena| { 一张 count-only 表逐个
`insert_raw_key` → 该表 `len()` }).sum()` ✓
用的是**已经写好并测过**的 `insert_raw_key`（溢出重分区就在用它），
不引入任何新的并发原语、没有跨线程生命期问题。

#### ⚠️ 三条必须处理的

1. **内存预留失败怎么办**（这次不能像 `DistinctCountExec` 那样"读着读着转溢出"，
   因为分区缓冲**已经吃掉了行数据**，回不去）：
   **在动手之前就要判** —— 输入是管理表 `Scan` 时行数可查
   （`db.scan_metadata_count`），按 `行数 × 32 字节` 保守估个上界，
   `ctx.try_reserve(该上界)` **成功才走分区路径，失败就原路返回现有的单线程路径**。
   ⇒ 预算紧的查询行为**与今天完全一致**，不引入新的失败模式。
2. **不要用 `filter_record_batch` 把批切给 N 个 worker**：那是把数据整体拷一遍
   （`perf` 里 memcpy 已经占 4.89%）。相 1 只搬**键字节**，比搬整行便宜得多。
3. **NULL 组**：编码是 `[0]`，照样哈希、照样落某个分区、照样只算一次 ✓
   （与 `count(DISTINCT x)` 跳过 NULL 是两码事 —— 那是绑定层改写负责的，
   见 P1⑩）。

#### 验收

- 值断言：`count(DISTINCT gs)` 必须仍等于 250 万（分区数 1/2/4 三种都测，
  `QSDB_SHARDS` 或专用旋钮）；
- **必须有一条"各分区共享键"的用例**（数据刻意重叠加满），证明**相加**不是**并集**
  ——旧行分片那条测试的翻版；
- 预期：**大约再快 2–3×**（当时的推算：2.4s → 0.8–1.2s）。**收益未实测，不许先写进战果。**

### P2 把"少干活"的优势再扩大（我们已赢的领域）

- 元数据短路继续下沉：`min/max` 也能走 parquet 统计（现在只有 `count(*)`）；
- zone map 用到 row-group 级（更狠的跳过）；
- 聚合下推（HAVING/limit 提前停）；
- 有界 TopN 已经赢了，继续把 `ORDER BY … LIMIT` 的路径做透（TopN 与聚合、TopN 与 join）。

## 三、纪律（避免又变成"感觉不对"）

1. **每次改动必须过闸门**：`bench_suite --all --max-seconds 10` 全绿 + DuckDB 对照表。
2. **对照必须同数据同形状**，且写明口径（缓存/并行度/压缩档）。
3. **不达标就是没做完**——"和 PG 同量级"不是理由（PG 不在对标范围内）。
4. **数字只落 [`真机基准对账.md`](真机基准对账.md)**，机制/状态/结论落本文档；
   **每次改动的收益都要能被复现**。
5. ⚠️ **本文档里出现"当前性能数字"一律算违规** —— 它们不会自己更新，会变成
   下一个人的判断依据（2026-10-15 已因此发生一次：生态团队照六批前的快照
   `5.55× / 30×` 做判断）。**要么链过去，要么别写**；历史值必须显式标成历史。
5. **聚合用例必须校验「值」，不能只比时间与结果行数**（2026-10-11 加的纪律）。
   聚合恒为一行 ⇒ 只数行数时**值算错也全绿**：`count(DISTINCT gs)` 被静默当成
   `count(gs)` 执行（回错数字）在 bench 里活了很久，就是这么过去的。
   期望值由造数分布直接推出（见 `bench_suite` 的 `expected_g_lt_1000` 等）。
   **另注意"数据本身分辨不出"的情形**：造数里 `gs` 全局唯一 ⇒ `count(gs)` 与
   `count(DISTINCT gs)` 数值相同，连值断言也分不清——用例的**数据分布**要能
   区分它想测的语义，否则等于没测。→ 已按此修 `gs`（`k-{i % (rows/2)}`，
   半数重复），见 `bench_suite::for_each_batch`。
6. **反馈打断纪律（2026-10-11 定，用户拍板）**：**只有「静默错值」类可以即时打断
   性能工作**，其余反馈一律进队列，攒到性能里程碑成批处理。
   - **允许打断**：静默给错结果/错行数/丢数据；静默丢弃 SQL 子句或参数；
     写坏数据、表不可读；协议面把合法请求 5xx 掉。
   - **进队列（不打断）**：新 API/新端点、门面与易用性、导出原语、性能缺口、
     文档对齐、编译期便利（如 `#[non_exhaustive]`）。
   - **为什么**：2026-10-11 前的实测规律是「每做一轮反馈平均再挖出 2 个自挖 bug」，
     于是一次次刚回到性能又被拉走。打断本身没错，**无预算的打断**才是问题；
     立这条是为了让"暂停"是**自愿的**。
   - 配套：同族 bug 的处置也要分档——**队列不积压时顺手挖同族**（F26 挖出 4 条、
     聚合那轮挖出 3 条，都值得）；**队列积压时只修反馈点那一条，同族记档不修**。
