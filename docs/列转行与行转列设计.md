## 〇、先修正我先前两个判断（**实测把它俩都推翻了**）

交接文档 `日清分方案-落地任务.md` §4.2 / §4.3 里我写过两句话，**跑真语料之后发现都不成立**，

| 我先前说的 | 实测结论 |
|---|---|
| `stack` 是"**行数会变的生成器**，要动执行层的『一行进、多行出』能力" | ❌ **不必**。它是 **`UNION ALL` 的 n 个分支**，执行器那边是我们**已有**的 Union |

⇒ **两者都是「绑定期重写成语义等价的既有算子」，一行执行器代码都不用加。**
  这个结论把整件事从"架构级改动"降成了"绑定期改写"，是本设计稿最值钱的一条。

## 一、语料里的真实形状（实测，不是猜的）

### 1.1 `stack` —— 28 个块 / 52 次

```
stack(6,
      '跨区跨省点对点中长期交易合约电量', CAST(ENERGY AS decimal(38,11)),
      '跨区跨省点对点中长期交易合约电价', CAST(PRICE  AS decimal(38,11)),
      '跨区跨省点对点中长期交易合约电费', CAST(FEE    AS decimal(38,11)),
      '用电侧日前统一结算点电价',        CAST(CUSTOM_AHEAD_PRICE AS decimal(38,11)),
      '关口节点（关口）日前价格',        CAST(UNIT_AHEAD_PRICE   AS decimal(38,11)),
      '跨区跨省点对点中长期合约省内输电费', CAST(BLOCK_FEE AS decimal(38,11)))
      AS (data_type, value)
```

- **形态完全规整**：`stack(n, k₁,v₁, …, kₙ,vₙ)`，参数总数恒为 **2n+1**；
  实测 n ∈ [2, 12]（首参即对数，不是可选的）
- **有显式两列别名**：`AS (data_type, value)` —— Spark 的多列别名，
  sqlparser 解析成 `SelectItem::ExprWithAliases`，**本仓目前在那里显式拒**
- **出现在 `SELECT` 列表里、与其它列并列**（不是独立算子）
- key 侧恒为字符串字面量；value 侧是**已 cast 成同一类型**的表达式

### 1.2 `PIVOT` —— 31 个块 / 54 次（扣掉死 CTE 后 28 个块拦路）

```sql
FROM ( SELECT PDATE, MONTH, …, data_type, CONTRACT_CODE, TPOINT, value FROM t16 ) t
PIVOT (
    SUM(CAST(COALESCE(value, 0) AS DECIMAL(38,11))) AS value
    FOR TPOINT IN ('1' AS `v1`, '2' AS `v2`, …, '24' AS `v24`)
)
```

- **`IN` 列表全是字面量**，且**每个都带 `AS` 别名** ⇒ 输出列名与类型**绑定期全知**
- 聚合是单聚合 `SUM(...) AS value`
- 24 个 IN 值 ⇒ 输出多 24 列（行转列）
- 输入是派生表（`FROM (…) t PIVOT …`）

## 二、`stack` 的设计

### 2.1 重写规则

```
SELECT A, B, stack(3, 'x', v1, 'y', v2, 'z', v3) AS (k, v) FROM T
```
**等价于**
```
SELECT A, B, 'x' AS k, v1 AS v FROM T
UNION ALL
SELECT A, B, 'y' AS k, v2 AS v FROM T
UNION ALL
SELECT A, B, 'z' AS k, v3 AS v FROM T
```

即：**把第 i 组单独提出来、把它上面的其它投影列原样复制 n 份，用 `UNION ALL` 串起来。**

### 2.2 类型

- key 列：各 `kᵢ` 的**公共超类型**（本仓已有 `common_supertype`）
- value 列：各 `vᵢ` 的**公共超类型**
- 两侧各自统一 → 分支间列类型一致，`UNION ALL` 的 schema 归一由既有逻辑处理

### 2.3 ⚠️ 成本与边界（必须写清楚）

- **其它投影列会被复制 n 份**。若它们含**昂贵表达式或聚合**，总成本 ≈ ×n。
  本仓的 CTE 是内联展开、没有公共子表达式消除 ⇒ 这是**真实成本**，不是纸面担心。
  （语料里 stack 的兄弟列都是裸列，所以不痛；但**不能假装它普遍不痛**。）
- **位置限制**：`stack` 只能作为 `SELECT` 列表的**顶层项**，
  **不许被别的表达式包住**（`stack(…)+1`、`sum(stack(…))` 都没有意义）⇒ **显式拒**。
- **别名必须有**（`AS (c1, c2)`）：没有别名就无从谈起输出列名 ⇒ **显式拒**，
  **不替用户编名**（本仓一贯口径：不静默造用户没写过的东西）。
- **`SELECT *` 与 `stack` 同用** ⇒ 显式拒（`*` 展开与行数变化叠加，语义要单独想清楚，
  没有需求就不做）。
- **行序**：`UNION ALL` 的分支顺序 = pair 顺序 ✓（与 Spark 一致）。
  语料下游全是聚合/PIVOT，不依赖序；但**不承诺全局有序**，`ORDER BY` 仍由外层管。

## 三、`PIVOT` 的设计

### 3.1 重写规则

```
FROM (子查询) t PIVOT ( agg(e) AS a FOR c IN (v₁ AS n₁, …, v_k AS n_k) )
```
**等价于**
```
SELECT <其余列…>,
       agg(CASE WHEN c = v₁ THEN e END) AS n₁,
       …
       agg(CASE WHEN c = v_k THEN e END) AS n_k
FROM 子查询
GROUP BY <其余列…>
```

即：**条件聚合**。这正是 Spark 内部把 Pivot 落成的形状。

### 3.2 「其余列」怎么定

```
其余列 = 输入列 − pivot 列 c − 聚合表达式 e 里引用到的列
```

⚠️ 这条要与真 Spark **逐值对账**确认（尤其"e 里引用的列"是否要从分组里剔除）。
**不对账就实现，很容易差一列** —— 而差的后果是分组粒度变了，**数字全错但不报错**。

### 3.3 ⚠️ 边界（**这里是本仓纪律的重点**）

| 形态 | 处置 |
|---|---|
| `IN` **全是字面量**（语料 100%） | ✅ 支持 —— schema 绑定期确定 |
| `IN` 里含**子查询 / 非字面量**（Spark 支持动态取） | ❌ **显式拒**。那才是"输出 schema 依赖数据"，与我们"绑定期定 schema"正面冲突，**不在本批范围** |
| `IN` 值**没有 `AS` 别名** | ❌ **显式拒**（Spark 会拿 `1`、`2` 当列名 —— 那是**别家替用户编名**，本仓不这么干） |
| **多聚合** `PIVOT (SUM(x) AS s, MAX(y) AS m FOR …)` | ❌ 暂**显式拒**（语料只有单聚合；多聚合的输出列名组合规则要单独定） |
| 没有 `FOR` / 没有 `IN` | sqlparser 层面就不成立 |

**空分组 ⇒ `NULL`**（`SUM` 全 NULL 的结果），与真 Spark 一致。

### 3.4 与 `stack` 的配合

语料里的模式是 **`stack`（列转行）→ `PIVOT`（行转列）** 串起来用：
把宽表的若干列先拍成 `(data_type, value)` 长表，再按 `TPOINT` 透成固定 24 列。
两条都落地后，这一族（28 个块）应当整体通过。

## 五、验收

- **正确性**：与 `.14` 上的**真 Spark 3.5.2 逐值对账**（同一份数据）。
  ⚠️ `stack` 的 key 侧是字符串常量、`PIVOT` 的列名来自 `IN` ⇒ **列名与列序**也要比，
  不只是比数值。
- **回归**：`tests/stack_unpivot.rs` / `tests/pivot.rs`
  —— 核心是**两路对撞**：`stack`/`PIVOT` 的写法 与 **手写成 UNION ALL / CASE+GROUP BY**
  的等价写法，**逐值逐列必须一致**。
- **语料**：`work/daily/` 里那 28 个块从 ERR 变 OK，
  跑通数 **120 → 148 / 154**。
- 闸门 ALL GREEN。
