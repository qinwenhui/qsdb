### ★ `export_csv` **4.36× → 快 1.53×**：CSV 导出原语（2026-10-15）

与 `export_parquet` **同源同因**：4.36× 从来不是"CSV 格式化算法差"，而是
**没有内核原语** —— 那条路跑的是 bench 工具里 arrow 的单线程 writer。
补上 `COPY … TO (FORMAT CSV)` 之后（分块**并行格式化** + 按序写单文件），
bench 换口径，差距当场消失。

**内存这一列的说明**：`bench_suite` 走 `QsdbOptions::default()`（段缓存默认档）。
⚠️ **我们的 RSS 含可挤兑的段缓存**，所以"我们胖"多半被高估；但**导入侧我们仍然
大赢**（CSV 1/11.6、parquet 1/3）—— 那两格不靠缓存解释。
（早先那版 `--budget-mb 2048 --cache-mb 1024` 的放大口径已作废。）

### ★ `export_parquet` 4.1× → **0.89×（反超）**：A3 导出原语（2026-10-15）

| 口径 | 值 |
|---|---|
| 修复前 | 3.58s（`.14` 首测）/ 3.05s（2026-10-15 刷新） |
| **修复后** | **0.766s**（`--all` 单实例闸门同轮，5M 行） |
| DuckDB | **0.862s**（同机同轮实测 862/838/866ms） |

**根因不是调参，是"没有导出原语"**：此前 `export_parquet` 走的是 **bench 工具里
arrow-rs 的通用单线程 writer** —— 而 DuckDB 那侧跑的是它自己的内核 `COPY … TO`。
**两侧口径根本不对等**（老注释自己写明了这点，见 `bench_suite.rs` 里那段）。
⇒ 修法是 A3 给内核加导出原语（`COPY … TO`），**bench 换口径**改走它。

**做法**（`crate::export`）：轮次式读入（512K 行）→ 切块（64K 行/块）→
**`par_iter` 并行编码** → 落 `part-NNNNN.parquet`。内存上界 ≈ 一轮缓冲，
并行度 ≈ 块数（5M 行 → 78 个 part）。
`export_scan_only` **0.139s** ⇒ 扫描只占导出的 18%，省下的是写侧。

> ⚠️ **口径提醒（别当成完全对等）**：两侧各用**自己的默认压缩**。产出体积
> **我们 78MB vs DuckDB 137MB** —— 说明我们的压缩档更狠（zstd-1），
> 即我们**做了更多活还更快**；但也因此这不是逐字节可比的对照。
>
> ⚠️ **分区导出的已知取舍**：有 `PARTITION_BY` 时，part 文件数 =
> `分区数 × 轮次数`（上例 365 分区 × 10 轮 = 3650 个 ~12KB 小文件）。
> 根因是内存上界按**全局行数**（512K）卡、而不是按分区卡 —— 分区一多，
> 每轮落到每个分区的行就少。**低占用优先**（本仓定则）故保留现状，
> 记为后续项（自适应刷盘 / 小文件合并）。`_common_metadata` 的 `schema_of`
> 那条路不受影响。

### 修复前为什么慢 26-58 倍（三个根因，都不是"哪都不行"）

1. **默认耐久档在做 fsync**：`Durability::ProcessCrash` 文档承诺"页缓存即持久"，
   实现里 `write_atomic_opts(sync=false)` 仍调 `f.sync_all()`。一次 `db.append` =
   段 + manifest + idx，其中**两次**走这里 → `.14` 实测 **45ms × 2/次**。
2. **切片批的字节数虚高 61 倍**：`RecordBatch::get_array_memory_size()` 按底层缓冲
   **容量**算——500k 行父批切出 8192 行仍报 4,000,096 字节（逻辑 65,536）。后果：
   攒批阈值"每批都超"→ 每批提交一次；**记账也虚高** → 配额下过早落盘/误报
   `MEMORY_PRESSURE`（"明明装得下"）。
   修法：`memory::batch_bytes()`（切片感知）+ INSERT 攒批改**行数为主**（512k 行）。
3. **`Qsdb::append` 按"批"提交而不是按"调用"提交**：传 13 个批 = 13 次提交
   （13 个段 + 13 次 manifest + 13 次索引）。`INSERT … SELECT` 的源按 8192 行一批
   扫出 → 5M 行 **610 次提交**；同数据按 65536 行一批传进来只要 10s。
   修法：**一次调用 = 一次提交**（按分区归并后 concat 成一个段；超 256MB 切块）。
   **这一条是主因**，也是"用户不该知道批大小"的落点。

### ★★ 内存那一栏**此前是被污染的**（2026-10-15 修尺子）

**先说结论**：`bench_suite` 每轮都重新 `open`（`run_once` 里）⇒ 段缓存**每轮都是冷的**、
一次命中都没有，但**每轮都要把它灌满**。于是"峰值 RSS"量到的是
「**工作集 + 一次完整灌缓存**」——**既不是用户会遇到的口径**（真 server 缓存是热的），
也把每一格都抬高。`open()` 的文档注释还写着"默认缓存 0"，代码却是
`QsdbOptions::default()` 的 **256MB**（文档与代码不符 —— 本次一并改正）。

**这个畸形口径已经造成过实际后果**：我们曾据它判定「`complex_window` 内存 43×、
是最该先修的一格」，而**真实工作集是 6.6×**。

**修法**：`bench_suite::open()` 默认 `scan_cache_bytes = 0`（与它自己的文档一致），
要看"给缓存会怎样"显式 `--cache-mb` 单跑一轮。诊断工具 `cache_probe`
（同 crate）把**缓存自己的记账** `cache_stats().used` 与 `VmHWM` 并排打出来。

**修尺子前后的同一批数**（cache=0 = 工作集）：

| **complex_cte** | 377MB | **130MB** | 300.6MB | **0.43×** | **我们更小** |

> ⇒ **"我们内存全面落后 20–30×"整句是尺子造成的**。真实图景是**互有胜负**：

### ★★ `complex_window` 内存的根因：**并行扫描（已定位到范围，机制未全钉）**

先把症状钉死（同一谓词、同一张表、输出都是 **2500 行**）：

| 查询 | 时间 | 峰值 |
|---|---|---|
| `SELECT g, v FROM t WHERE g < 50` | 21ms | 36MB |
| `+ 任意窗口`（连 `count(*) OVER ()` 都算） | 97ms | **139MB** |
| 同上但**串行扫描**（`QSDB_SCAN_SERIAL=1`） | 408ms | **14.6MB** |
| `WITH x AS (SELECT g,v FROM t WHERE g<50) SELECT …, count(*) OVER () FROM x` | 20ms | **37MB** |
| `WHERE g < 0`（0 行） | 1ms | 3.2MB |

**内存随线程数线性增长**（同一句查询）：

| `RAYON_NUM_THREADS` | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|
| 峰值 | **14MB** | 24MB | 38MB | 71MB | **137MB** |

⇒ 约 **8.5MB/线程**。**串行时该查询比 DuckDB（22.6MB）还小。**

**已排除**（都有实测，写给下一个人别重走）：
- **整分区物化**：有/无 `PARTITION BY` 一样。
- **窗口自身的分配**：CTE 先物化再窗口 = 20ms/37MB ⇒ 窗口免费。
- **计划形状 / 谓词下推**：`QSDB_PLAN_DUMP` 打的计划**完全一致**（`Window { input: Scan { predicate: Some(Lt) } }`），谓词都在 Scan 上。
- ★ **channel 在途队列**：我一度判定是它（`threads×2` 批），并实现了"字节预算 + 背压"闸门
  —— **实测把它证伪了**：把预算压到 1MB（远小于一个批）内存**纹丝不动**
  （窄表 137→136MB、宽表 648→647MB），而且闸门对**宽表也零效果**。
  ⇒ 队列不是主项，那个机制**没挣到位置，已撤掉**（"减法设计优先"）。
  **不要**再走这条路。

**修正后的判断**：钱花在**每个 worker 自己的解码缓冲**上（≈8.5MB/worker，
量级 ≈ 一个 row group 解压后的列块）。它随线程数线性、不进内存账本，
**但它同时也是 5–6× 速度的来源**（串行 408ms vs 并行 97ms）。

⇒ 这与"低占用 vs 速度"是**同一个取舍的两面**，不是 bug。下一步要么**给它一个旋钮**
（让部署自己选天平），要么**减小单 worker 的解码粒度**（按更小的块解压，
但那要先证明 parquet 读侧支持）。**两条都还没做，别当成已经有方案。**

> ⚠️ **同批修掉一个死开关**：`QSDB_SCAN_SERIAL=1` 在 `par_scan.rs` / `scan.rs`
> 两处文档里都叫"诊断/对照开关"，但 **`ParScanExec::new` 从不检查它** —— 只有
> 公开 `scan()` API 那条路认。于是设了它照样起 16 个扫描线程，**任何人做这个
> A/B 都会得到"并行没有影响"的假结论**（我先踩了一次：拿它"排除"了并行，
> 回头才发现在空跑）。已在 `make_scan` 收口。

### ⚠️ 仍未解释（有数、无因，别编）

`cache_probe` 实测：**峰值 RSS ≈ 基线 + 1.5–2.8 × 缓存 `used`**（64MB 预算 → 持有 57.7MB
却涨 163MB；256MB → 持有 252.5MB 却涨 377MB）。缓存记账是准的（`used` 守预算），
**但进程峰值涨得更多**。原因未定位 —— 记在这里，别当成已解释。

**我们内存大赢的一侧**（别只看输的）：`import_csv` **99MB vs 1147MB（1/11.6）**、
`import_parquet` **108MB vs 317MB（1/3）**、`export_parquet` 1178 vs 1599。

### 二之二、这一轮的根因（全是**退化**，不是"少核"）

> **方法论上的教训**：三个根因里**没有一个**是"算子写得不够快"。
> 两个是**绑定/规划层静默走了错路**，一个是**输出侧的 O(n) 对象风暴**。
> 它们的共同特征是**结果逐行正确**——所以值断言全绿、只有耗时和内存露馅。
> §三.5 那条"聚合用例必须校验值"只挡住了**错值**这一类；**退化**这一类要靠
> **形状断言**（`tests/join_plan_shape.rs`）与**分配次数断言**
> （`tests/literals_to_array.rs`）——两者都是本次新加的。

#### 根因 1：多表 join 静默退化成叉积（`89036a7`）→ `complex_three_way` 113× → 9.9×

**两个 bug 互相掩护**，所以三张表以上的 join 一直"能跑"：

| # | 位置 | 症状 |
|---|---|---|
| ① | `translate_select_inner` join 循环 | 左侧宽度取「**非限定**列数」。第二次 join 起左侧含上次带进来的限定列（`d.cat`）⇒ 两个 ON 操作数都被判成"右侧" ⇒ `split_equi_condition` 报错 ⇒ 落到 `CrossJoinFilter`（叉积 + 过滤）。**结果对，代价 = 左行数 × 右行数** |
| ② | `plan_output_columns` | 遇 `LogicalPlan::Join` **直接报错**，而 `exec_builder` 构建 `Join` 时正要用它拿左输入宽度 ⇒ **被正确识别成等值 join 的多表查询根本绑不出来** |

合起来：**只有退化那条路能跑通**，谁都没从"正确那条路"撞见 ①。

**取证**（`t JOIN d ON t.a=d.a JOIN d2 ON d.c=d2.c`，500k 行，**右表体积 ×10、结果行数不变**）：
耗时 8.5×（叉积特征）⇒ 修复后 1.2×，绝对耗时 1446ms → **5ms**。

**回归**：`tests/join_plan_shape.rs`——**计划形状**断言（不靠计时）：三表/四表链式必须
全为 `Join` 节点且叉积计数为 0；真非等值 `ON` 仍走 `CrossJoinFilter`（对照组，
防止一刀切把叉积删了）。

#### 根因 2：`literals_to_array` 逐行建数组（`77b654d`）

原实现是「**每行建一个单元素 Arrow 数组，再 `interleave` 拼起来**」——
n 行 = n 个数组，每个自带 `ArrayData` + buffers + `Arc` 链。

    SELECT count(*) FROM (SELECT DISTINCT gs FROM t)   250 万去重组
      修前 9.03s / 4441MB  →  修后 6.49s / 1065MB
    （**组表本身账上只有 449MB** —— 差的那 4GB 全在这一处）

诊断靠新加的 `QSDB_AGG_PROF`（组件级占用剖析）：它把"组表胖"拆成
`key_arena`/`by_hash`/`group_lits` 等分量，**一眼看出不在组表**（此前只能靠猜）。

改为 typed builder 一趟构建；**不精确对应的类型（decimal / Binary / 带时区 ts /
需要隐式 cast 的混合字面量）一律退回原路径**（那里有无条件 cast，语义一致）——
**宁可慢，不许悄悄换语义**。

#### 根因 3：`DistinctExec` 输出做了一次行式转置（`77b654d`）

`group_keys()` 把列式的 `group_lits` 转置成 `Vec<Vec<Literal>>`（**每组一个 Vec
堆对象** + 一次 Literal 克隆），交给 `build_output_batch` 再转回列式——一进一出纯白扔。
改为列式的 `build_output_batch_cols`（与 `GROUP BY` 侧一直在用的 `finalize_table`
同款循环），并**删掉 `group_keys`/`build_output_batch`**：留着就是留一个陷阱。

    DISTINCT gs（字符串）  → 6.20s / 588MB
    DISTINCT v（500 万 int）→ 0.16s / 136MB   （原 0.55s / 569MB）

#### 两把**歪尺子**（先修尺子，否则后面的数字全是错的）

1. **bench 的断言跑在计时区间里**。`simple_count/filter/group/distinct` 的值断言都是
   **一条同形状的真实查询**，放在 `t0` 与 `elapsed()` 之间就等于把"查询 + 校验"
   一起计时。实测 `simple_distinct` 报 **12.12s**，同一查询单独跑是 **6.0s**——
   **正好两倍**（校验又跑了一遍完整的 `SELECT DISTINCT`）。
   ⚠️ 这个偏差**永远指向"把自己说慢"**，是"宁可信其有"的反面：它会让我们去优化
   一个不存在的问题。现在：**断言一律在计时区间之外**（导入用例本来就是这样写的）。
   *（修的过程中 bench 自己的值断言又抓到我一次失误：`rows_of` 对聚合恒回 1 行，
   拿不到去重结果——断言确实在干活。）*
2. **`manifest` 格式版本**：F26 给持久化结构尾部加了 `epoch` 却没升 version，
   旧数据被读成 `corrupt manifest … Hit the end of buffer`。postcard **不自描述**，
   `#[serde(default)]` 对它**无效**（只对 JSON 那类生效）；报错说"损坏"而真相是
   "版本不同"，把人往磁盘/GC 方向带。见 `crates/qsdb/src/manifest.rs` 的
   `MANIFEST_VERSION`（含 v1 兼容读 + 4 条回归）。

#### ★ 2026-10-14 第三批：`simple_distinct` 的靶子定位（**只测量，未改码**）

融合计数落地后 `simple_distinct` 仍是 2.407s。按纪律先量再改，一次量出三件事：

**① 扫描不是瓶颈**（推翻"少核"的直觉）：

| 查询 | 时间 |
|---|---|
| `SELECT count(*) FROM t`（元数据短路） | 0.000s |
| `SELECT count(gs) FROM t`（**全量扫描 + 解码 500 万字符串**） | **0.042s** |
| `SELECT count(DISTINCT gs) FROM t` | 2.437s |

⇒ **扫描 1.7%，去重 98.3%**。改扫描/并行扫描对这一格毫无意义。

**② 代价随「不同组数」走，不随「行数」走**（同一份 500 万行数据）：

| 查询 | 不同组数 | 时间 |
|---|---|---|
| `count(DISTINCT g)`（Int64） | 10 万 | 0.339s |
| `count(DISTINCT v)`（Int64） | 100 万 | 0.913s |
| `count(DISTINCT gs)`（String） | 250 万 | 2.437s |
| `count(DISTINCT id)`（Int64） | 500 万 | 2.136s |

**③ 真正的开销是「每行对 `key_arena` 的一次随机访问」**——由这组对照钉死：

| 同一份数据（`DISTINCT v`，100 万组） | 命中判定 | 时间 |
|---|---|---|
| 旧的 `DistinctExec` + `fast_slots_inline` | 键**存在槽里**，不碰 arena | **0.168s** |
| 融合节点（count-only，禁用内联） | 走 `by_hash` + `key_of` 比真值 | **0.913s** |

⇒ 差 5.4×，差别**只在**"要不要去 arena 取一次真值"。不是哈希桶形态、不是分配。
（`count(DISTINCT id)` 同理：0.613s vs 2.136s，3.5×。）

##### ⚠️ 一个**被实测否决**的猜想（别再走）

看到上面这组数，第一反应是"`by_hash`（`HashMap<u64, Vec<u32>>`）按低基数设计，
高基数下每组一个 `Vec` 堆分配拖垮了"——于是给 count-only 加了一张**通用开放寻址槽表**
（槽 = `(hash, gid)`，命中再比 `key_of`）。**实测全面变慢**：

| | `by_hash`（改前） | 通用槽表（改后） | |
|---|---|---|---|
| `DISTINCT g` | 0.339s / 63MB | 0.813s / 58MB | 2.4× **慢** |
| `DISTINCT v` | 0.913s / 170MB | 1.616s / 107MB | 1.8× **慢** |
| `DISTINCT gs` | 2.437s / 374MB | 3.354s / 315MB | 1.4× **慢** |
| `DISTINCT id` | 2.136s / 602MB | 3.642s / 519MB | 1.7× **慢** |

内存按预期降了，**时间四个点全变慢**（不是噪声）。**错在哪**：`fast_slots_inline` 快的
原因是**键存在槽里**，不是"开放寻址 vs 哈希桶"——我照搬了寻址方式，却仍要走
`key_of(gid)` 比真值（这条**不能省**：只信哈希是有碰撞概率的**静默错值**），
于是既没消掉那次随机访问，又往每行的关键路径里塞了一个更冷、更大的平坦数组
（800 万槽 × 16B = 128MB）。**已回退。**

**正确的方向**：**让命中判定不碰 arena** —— 把 `fast_slots_inline` 的"键存槽内"
推广开。定宽键（≤8 字节）直接内联；变长键（字符串）在槽内内联**前缀 + 长度**。

##### ✅ 第四批：定宽键内联**已验证**（`b6da01a`，整型去重 8.9× → 1.30×）

先在**定宽键**（count-only + 单 Int64 列）上把"键存槽里"做了出来：

| 查询（5M 行） | 改前 | **改后** | |
|---|---|---|---|
| `DISTINCT v`（100 万组） | 0.902s / 278MB | **0.147s / 107MB** | **6.1×** |
| `DISTINCT id`（500 万组） | 2.136s / 602MB | **0.486s** | **4.4×** |
| `DISTINCT g`（10 万组） | 0.339s / 63MB | **0.034s** | **10×** |
| `DISTINCT gs`（字符串） | 2.437s | 2.518s | 不变（还没做） |

bench：`simple_distinct_int` **0.902s / 278MB · 8.9× → 0.132s / 249MB · 1.30×**。
（比**旧的** `fast_slots_inline` 还快——count-only 顺带省了 literal 与输出物化。）

**三点与 count-only 绑定**（写在这里免得后人重踩）：
1. **NULL 走专门的槽**——不能用键值哨兵，`i64::MIN` 是合法值；
2. `key_arena` 里仍写**规范编码**（溢出分区路由按它算）⇒ 内联槽是**缓存**，
   随时可按 arena 重建；
3. ⚠️ **走不走这条路必须类型驱动**（"分组是单列 Int64"），**不能逐批判定**
   （"这批有没有 NULL"）——逐批会让同一个值在两种编码下各建一次组（**静默多数**）。

⚠️ **本批自己踩的坑**：第一版把探测用的 `mask` 提到了行循环外，而表会在那个
循环里扩容 ⇒ 扩容后按老宽度取模、探测只在老区间走 ⇒ **已有键一律找不到、每行
新建组**（`.14` 上 500 万行直接跑到超时）。既有代码本来就逐行重取，我"顺手优化"
掉了。**本地测试没拦住**：整型去重用例都太小（不扩容），会扩容的那几条用的是
**字符串**列（走不到内联槽）⇒ 补 `int_slot_growth_keeps_counts_correct`
并**把 bug 放回去验证过它会挂**。

##### ⚠️ 第五批：字符串的槽内内联前缀 —— **实测大幅变慢，已回退**

按上面的方向给字符串也做了内联槽（`StrSlot{gid,len,h,inline[16]}`：长度 ≤ 16 的键
命中时完全不碰 `key_arena`；长键回 arena 比真值）。**实测否**：

| | 改前（`by_hash`） | 改后（字符串内联槽） |
|---|---|---|
| `count(DISTINCT gs)`（250 万组） | 2.443s / 586MB | **8.954s** / 482MB ← **3.7× 慢** |

**同一个结构，整型赢 6–10×、字符串输 3.7×** —— 判别不是算法，是**能不能塞进缓存**：

| | 组数 | 槽表大小 | 结果 |
|---|---|---|---|
| 整型 `v` | 100 万 | ~32MB（24B 槽 × 2M） | **赢 6.1×** |
| 字符串 `gs` | 250 万 | **~235MB**（28B 槽 × 8.4M） | **输 3.7×** |

槽表一旦超出 LLC，**每次探测都是一次 DRAM 访问**；而 `by_hash` 的
**控制字节数组是 1 字节/项**（8.4M 项 ≈ 8MB，基本驻留 L3，且一次 SIMD 比 16 项）
—— 高基数下它反而更省。⇒ **`by_hash` 对高基数变长键本身就是好结构，不要再换。**

⚠️ 同一批还试过"通用寻址槽表（只存 hash+gid）"，同样是字符串变慢（2.437→3.354s）。
**三次尝试全指向同一结论**：这一格的剩余差距不在"索引结构"，在别处。

##### ✅ 已按热点修掉（`62a0170`）：`by_hash` 的值改内联一格的桶

```rust
enum Bucket { One(u32), Many(Vec<u32>) }
```
高基数走 `One`（gid 直接放桶里 ⇒ **不分配**、与键同一条 cache line）；
低基数才退 `Many`，行为不变。

**实测（0 FAIL）**：`simple_distinct` 2.462s/586MB → **1.921s/562MB**；
`count(DISTINCT gs)` 2.443s/374MB → **1.896s/317MB**（内存 −15%）；
相对 DuckDB **12.1× → 9.5×**。`count(DISTINCT v)`（整型内联槽）无回归；
`simple_group`（`Many` 路径）在噪声内。

**改完再剖一次 —— 与预测完全对上**：

| 占比 | 位置 | 改前 |
|---|---|---|
| **41.09%** | `hashbrown` 查找（`eq`） | 36.65% |
| **23.76%** | `group_id` 循环体 | 16.71% |
| 7.01 / 4.12 / 2.64% | `rustc_entry` / `insert` / `reserve` | 6.41 / 3.55 / 2.02 |
| **消失** | `malloc_consolidate` 7.40 / `free` 5.07 / `malloc` 3.32 / `_int_free` 3.07 | 合计 **18.86%** |

⇒ **那 18.9% 的分配器整块没了**（掉到 1.5% 阈值以下）。
剩下的 **79% 全是哈希表本身**。

##### ⚠️ 三次尝试：把 `Bucket` 再压小（`Many(Box<Vec<u32>>)` 40→24 字节/条）

推理：桶数组 140MB，按 40 字节一条 cache line 只装 1.6 条，24 字节能装 2.6 条 ⇒
探测链跨桶时省 miss。**实测：测不出差别** —— `simple_distinct` 1.921 → 1.896s
（5 轮中位，spread 7.7%，1.3% 在噪声内），代价是 `Many` 多一次间接。
**已回退。**

⇒ **"把它变小应该更快"在这个结构上连着两次没兑现**（前一次是把表换成平坦
开放寻址）。共同点：**每次查找本来就只碰一条 cache line**，压缩条目尺寸省的是
TLB/带宽，不是 miss 数。**下次别再往这个方向试。**

##### ★ 下一步：把命中判定那一次 arena 随机访问也去掉

`group_id` 占 23.76%，其中含**每次命中都要回 `key_arena` 比一次真值**
（`key_of(gid) == key`）——那是又一次随机内存访问。5M 行里约 250 万次命中
⇒ 约 250 万次 DRAM 往返。

**这一条不能省**：只信哈希 = 有碰撞概率的**静默错值**。但可以在**桶里内联键的
一段**（哈希匹配之后先比内联段，只有内联段也相同才回 arena）。⚠️ 长键
（`gs` 是 14 字符）装不下 ⇒ 需要"够宽的槽"，那正是字符串内联槽那次失败的地方
（表被撑大变冷）——**但这次是往已有的桶里加内容，不是新建一张表**，
形态不同，**必须先小规模实测再铺开**。

##### ★ 热点指向的修法：`by_hash` 的值改成**内联一格的小向量**

`HashMap<u64, Vec<u32>>` 在**高基数**下每个桶只有一个 gid，却要付：
① 一次 `Vec` 堆分配（≈19% 的分配器）；② 查找时多追一次指针（`Vec` 的数据在别处）。

```rust
enum Bucket { One(u32), Many(Vec<u32>) }   // 高基数走 One：不分配、且与键同一条 cache line
```
低基数（多 gid 同桶）仍走 `Many`，不回退。**两个热点一起打**：
省掉 per-group 分配，查找少一次随机访问。

##### ★ 字符串那格还剩什么可做（按证据排序）

1. **按哈希分区 + 各分区独立去重**（计数可直接相加，**不需要并集** —— 与
   §「行分片」那条不同，那条输在并集上）。代价：每行一次散列写入 + 5M 行键列的

2. **减少每行的探测次数**（当前 `by_hash` 命中约 4 次随机访问：控制数组 → 桶 →
   `Vec` 载荷 → arena）。
3. **什么都没做成也别硬做** —— 这一格已连否三次，说明手感不可靠；
   要么先上 profiler（`perf`）拿到真实热点，要么转到短板表里**确定性更高**的那些
   （导出 4.4×/3.7× 是纯结构缺口，P0② 单线程写段）。

槽里放 `(hash, gid, len, inline[N])`：`len ≤ N` 时比较**结论就在槽里**；

代价是槽 16 → 32 字节（内存换时间），**必须实测权衡**——但方向已有两组数据背书

**这一格的期望**：字符串 2.443s → 同量级收益下约 **0.3–0.5s**，即 12× → **2× 量级**。

##### ⚠️ 第二个被实测否决的猜想：**分片并行 + 键并集**

由"这场子内存延迟受限、并行能藏延迟"推出"分片各建一张表再求并集"。**实测否**：

| | 单线程 | 分片 4 路 | |
|---|---|---|---|
| `DISTINCT gs`（250 万组） | 2.437s / 374MB | **2.912s** / 773MB | 慢 + 内存翻倍 |
| `DISTINCT v`（100 万组） | 0.913s / 170MB | **1.413s** / 537MB | 慢 |
| `DISTINCT g`（10 万组） | 0.339s / 63MB | **0.228s** / 79MB | **快 1.5×** |

**根因**：分片切的是**行**、不是**键** ⇒ 分片之间大量共享键（`gs` 那格每片各含
125 万个不同值，全局只有 250 万）⇒ **并集那一步要串行重灌 500 万个键**，把并行
省下的又吐回去，还多占一倍内存。只有**低基数**（并集便宜）时才真赚。
（真要按这个方向做，得让分片按**键哈希**切——但那是 shuffle，每行都要多一次
路由；收益未验证，**不做**。）

⇒ **两次尝试（通用槽表、行分片）都指向同一件事**：它们都没碰到那个
**每行的随机内存访问**本身。结构换法救不了它。

##### ⚠️ 同时暴露：**上一批给整型 DISTINCT 引入的回归**（bench 没抓到）

`count-only` 为了"溢出重分区两侧键编码一致"**禁用了 Int64 内联快路径**
（内联键是裸 8 字节、通用路径是 tag+值）。后果：`count(DISTINCT int_col)` 从

**bench 抓不到**：`simple_distinct` 只测 `gs`（字符串走不了内联路径，两边都是

修法：让内联路径在 count-only 下也生效，并把溢出路由的键编码按**该表实际用的编码**

#### 二之三、顺带挖出的**既有**静默错值：列裁剪的"索引空间"（`4cba9fe`）

做 `count(DISTINCT)` 时撞上的，**先于这批改动就存在**（已用 `git stash` 在 HEAD 上复现确认）。

`exec_builder` 的列裁剪把「表列序 → 扫描投影序」重映射一遍，判断一个 `Column`
是不是表列时**按列名猜**（`all.contains(name)`）。于是在「上下两层列名相同、但列空间
不同」的形状上，会拿**外层的列位置**去查**表空间的映射**，**静默指到隔壁那一列**：

```sql
-- t(id, g, x, s)，外层用不到 id ⇒ 裁剪必然发生（映射非恒等）
SELECT g, x FROM (SELECT DISTINCT g, x FROM t)
-- 修复前实际回 (1,1),(1,1),(2,2),(3,3),(3,3)：x 列整个变成了 g 列
SELECT g, count(x) FROM (SELECT DISTINCT g, x FROM t) GROUP BY g
-- 修复前回 2|1、3|2（正确 2|0、3|1）：NULL 组被算进了 count
```

不报错、不打日志。⚠️ **10-13 那条"等价写法"建议本身就是错的**——它恰好只在
`count(*)`（无列引用）形态下侥幸能对。

**同类前科**：`Sort` 的排序键踩过同一个坑（见 `exec_builder` 的 `Sort` 臂注释，
回归 `tests/order_by_prune.rs`）。**修法**：改成看**结构性事实**——「该节点自身
表达式是否按表列序编号」（`exprs_are_in_table_space`），说不清的空间一律原样保留。

**过程中两次漏认，被既有测试当场抓住**（这条"穷举清单"现在写在注释里）：
漏 `ExternalScan`/`CsvScan` → `external_parquet.rs` 4 例炸；漏 semi join
（其输出 = **左** schema）→ `subquery.rs` 4 例 `index out of bounds`。

**让它可断言**：新增 `exec_builder::prune_decision()`（纯函数，回"表全列 / 实际要读的列"）。
这个优化已经**三次**因索引空间静默出错，而"结果对不对"**根本看不出它有没有白跑**
（少裁一列只是变慢，不是变错）⇒ 现在可以断言"裁剪仍然发生"。

### ★ 现在的短板排序（下一轮打这些）

| 排名 | 用例 | 相对 | 病灶 |
|---|---|---|---|
| 1 | simple_distinct | **11.9×** | 原生 `count(DISTINCT)` **已实现**（P1⑩，2026-10-14）：绑定层等价改写 + `DistinctCountExec` 融合计数，不物化去重结果。2.900→**2.407s**、767→**586MB**。**剩下的 11.9× 全在"每行哈希/编码成本"**——去重 500 万行字符串这个动作本身我们比对手慢一个数量级，不是"少干活"能解决的 |

#### P0③ 前半已落地（`1ab56af`）：join 之后的分聚合真并行了

`try_shard_source` 此前只穿透 **semi 族** join，INNER/LEFT 之后整条管线退回单线程。
现在分片带上整棵 join 子树（`ShardScope`：线程局部、取用一次即失效的"表名→分片"覆盖），
**结果**：`complex_join_group` 0.702→**0.481s**、`complex_three_way` 1.203→**0.674s**
（并行度实测 3.3–3.8×）。

**但还没到头。**分片数曲线（5M 行，`QSDB_SHARDS` 旋钮）：

| 分片 | `t×d` 聚合 墙钟 / CPU / 峰值RSS | 10 万组聚合 墙钟 / CPU |
|---|---|---|
| 1 | 1.29s / 1.29s / 307MB | 0.34s / 0.39s |
| 4 | **0.53s** / 1.74s / 419MB | **0.20s** / 0.72s |
| 8 | 0.47s / 2.63s / 530MB | 0.21s / 1.23s |
| 16 | 0.45s / **5.78s** / **746MB** | **0.26s（回退）** / 2.69s |

4→16 片只再快 1.2×，而 **CPU ×3.3、RSS ×1.8**，高基数聚合还回退。
（顺带：上限 4 这条**旧结论在并行 merge 之后重测依然成立**，见 `shard_count` 的文档表。）

#### ⚠️ 一处**被实测推翻的猜想**（写在这里免得后人重走）

我一度把"每片固定成本 B"归因于**每片各建一次建侧 hash 索引**，并据此打算做"共享建侧"。
加 `[join-build]` 插桩直接量了（`QSDB_JOIN_PROF=1`）：

    [join-build] 200000 行 / 3 列，耗时：N=1 是 18.8ms · N=4 是 ~30ms/片 · N=16 是 ~65ms/片

**每片建侧只有 19–65ms**。共享建侧在 N=4 最多省 ~30ms（**6%**）、N=16 省 ~65ms（14%）
——**不是 1.4×**。而且 `simple_group`（**根本没有 join**）在 N=4 之后同样饱和回退，
说明饱和的根源在**分片机制本身**（并行 CPU 膨胀 ×3.3：16 个线程各建一份组表、
各自随机探测同一张 build 表 → 缓存/带宽争用），不在建侧。

**结论：共享建侧的性价比不足，不做。** 真正的靶子在下面。

#### 附带干掉的一个平方级热点：`estimated_bytes()` 每批全量遍历 `by_hash`

**线索**：同数据同去重，`DISTINCT v`（500 万 **int** 组）只 0.16s，而 `DISTINCT gs`
（250 万 **字符串**组）6.20s —— **组数少一半却慢 39 倍**。整数键走 `fast_slots_inline`，
`by_hash` 基本是空的；只有字符串键走 `by_hash` ⇒ 问题在**只对 `by_hash` 成立的那一项**。

**根因**：`estimated_bytes()` 里 `by_hash.values().map(...).sum()` 是 **O(组数)**，
而 `DistinctExec`/`HashAggExec`/`run_partial_fused` **每批都调一次** ⇒ 成本 = 组数 × 批数。
250 万条 × 32 字节 = 每次流过 **80MB**，610 批 ⇒ **约 48GB 内存流量 ≈ 5 秒**。

#### ★ 2026-10-14 第二批：原生 `count(DISTINCT)` + 融合计数（`4cba9fe` / `753a330`）

**从"能力缺口"到"同实现对照"**。此前 `count(DISTINCT x)` 在绑定层被**显式拒绝**
（再往前是静默当 `count(x)` 跑 = 回错数字），bench 只好跑等价改写
（`SELECT DISTINCT` 子查询 + `count(*)`）——那是**能力对照**，不是同实现对照。
现在两步都落地：

1. **绑定层等价改写**（`translate::rewrite_distinct_aggs`）：
   `count(DISTINCT x)` → `aggregate{aggs:[count(x)], input: Distinct{[x]}}`。
   **NULL 语义分两种处理**（最容易写错的一处）：无分组时先去重**之前**滤 `x IS NOT NULL`
   再把 `count(x)` 收紧成 `count(*)`；**有分组时绝不能滤**——某组可能只有 NULL 的 x，
   滤掉会让**整组消失**（正确结果是该组回 0，不是没有这一行）。
2. **融合计数节点**（`exec::DistinctCountExec`）：认出
   `Aggregate{group:[], aggs:[count(*)]} ← Distinct ← X` ⇒ 单遍数完，
   不产出中间批、不跑第二遍聚合，组表**不存 literal**（那是"组表仍胖"的大头）。

**bench 尺子也跟着换了**：`simple_distinct` 现在两侧都跑原生 `count(DISTINCT gs)`
⇒ 这一格从"能力对照"升格为**同实现对照**。
⚠️ **换过尺子 ⇒ 与 10-13~10-14 期间的该格数字不可直接比**（那期间跑的是等价改写）。

**实测**（`.14`，`suite-h6.log` / `duck-h6.log`，闸门 **0 FAIL**）：

| | 改前（等价改写） | 改后（原生+融合） | 变化 |
|---|---|---|---|
| `simple_distinct` | 2.900s / 767MB | **2.407s / 586MB** | 1.20× / −24% |
| 相对 DuckDB（0.2029s） | 14.3× | **11.9×** | |

**11.9× 还差在哪**：剩余成本几乎全是"把 500 万行字符串编码 + 哈希 + 进组表"这个
**逐行动作本身**——与对手是每行 3–4× 的常数差（`complex_three_way` 那格同源）。
融合节点能省的（中间批、第二遍聚合、literal）都省掉了。

**同一批顺带挖出并修掉一处既有静默错值**（列裁剪的索引空间，见 §二之三）。

---

**判据**（不靠猜）：时间应随规模**超线性**。实测 1M 0.81s → 2M 2.26s → 5M 5.98s
（数据 5× 而时间 7.4×）—— 正是"线性 + 一个尚未完全主导的平方项"。

**改法**：`payload_bytes` 增量维护（`bucket_push` 在两处插入点累加），`estimated_bytes` 直接加它。
**实测**：5M **5.98→2.83s（2.1×）**，1M→5M 的时间倍率从 7.4× 回到 **4.2×（近线性）**。
基准 `simple_distinct` **6.097→2.900s（30×→14.3×）**。
守卫：单测 `incremental_payload_matches_full_recompute`（三条路径都与全量重算逐字节相等）——
它驱动**溢出决策**，算错就是"该落盘没落盘"。

#### ★ 真正的靶子：join 输出**把没人读的列也 materialize 了**

同一份数据单线程拆解（`RAYON_NUM_THREADS=1`）：

| 查询 | 墙钟 / CPU | 说明 |
|---|---|---|
| `count(gs) FROM t`（只扫一列） | 0.14s / 0.11s | 5M 行扫描 ≈ 22ns/行 |
| `count(*) FROM t JOIN d ON t.g=d.g` | 0.10s / 0.08s | 走 `count(*)` 融合路径，几乎不干活 |
| `count(*) … JOIN … WHERE t.v>=0` | 0.99s / 0.96s | **一旦要真列，融合失效** |
| 基准那句（`GROUP BY d.cat` + `sum(t.v)`） | 1.27s / 1.24s | |

**对照 DuckDB 同一条：0.12s 墙钟 / 0.36s CPU** —— 我们单线程 CPU 就是它的 **3.9×**。

成本在哪：`d` 是 `g = i % 100_000` ⇒ **每个 g 两行** ⇒ 那句 join 实际产出
**1000 万行**。而 `exec/join.rs::join_batch` 对**每一行**都 `take`：
**全部 probe 列（7）+ 全部 build 列（3）**，其中 **4 列是字符串**——
可上面那句聚合**只读 2 列**（`t.v`、`d.cat`）。1.27s 里约 **0.85s（67%）** 花在
"物化 1000 万行 × 10 列，然后由聚合丢掉 8 列"。

**为什么没被裁剪**：列裁剪 `build()` 只在 `plan_scan_def(plan)` 有值时才生效，而它
**遇非 semi 的 Join 就返回 `None`**（`Aggregate(Join(…))` 拿不到单表 def）⇒
`try_shard_source` 那条路之外，**join 之上没有任何投影下推**。
（semi 族有：`plan_scan_def` 穿透 semi join；非 semi 没有。）

#### P1⑥ 第一步已落地（`join-proj`）：join 只物化下游真读的列

做法：`Aggregate` 之下的 join 链被标注"**只需物化这几个位置**"
（`LogicalPlan::Join::needed`），其余位置由 join **填 NULL**——列还在、schema 不变、
**索引一概不动**。标注逻辑（`exec_builder::annotate_join_needs`）只在
"join 输出**唯一**的读者可枚举"时动手（`Aggregate` + 恒等透传的 `Filter`），
遇 `Project`/`Sort`/`Window`/semi join **就地停手**（= 今天的全列行为 = 不优化）。

**实测（`QSDB_JOIN_NO_PROJ=1` 开关对照，同一二进制）**：

| | 开 | 关 | 收益 |
|---|---|---|---|
| `t×d` 聚合 N=1 墙钟 / CPU | 1.19s / 1.17s | 1.31s / 1.28s | **9%** |
| 同上 16 核 墙钟 / CPU | 0.49s / 1.76s | 0.55s / 1.93s | **11%** |
| 峰值 RSS | 417MB | 431MB | 3% |

基准：`complex_join_group` 0.481→**0.432s**、`complex_three_way` 0.674→**0.548s**。

> **⚠️ 但它没拿到预期的 2×，原因值得记下来**：省下的只是"**列拷贝**"，
> 而"每行 × 每列"的拷贝本来就不是大头 ——
> 主导成本是**按行数**的那部分（探测、10M 条 `probe_idx`/`build_idx`、
> 批构造、聚合摄入）。宽表实验里那 0.70s 差值的大头其实是**扫描解码**
> （`tn` 少读 5 列，含 2 个字符串列），而这一步**没有**顺手做掉。

**下一步（P1⑥ 继续）**：把两侧的**扫描**也收窄 —— **已落地（`b49b20e`）**，见下。

#### P1⑥ 第二步已落地（`b49b20e`）：只解码下游真读的列

第一步只拿到 ~10%，因为**列拷贝本来就不是大头**。量过才清楚：

    同一张 5M 行表：只读 2 列 0.18s · 读 4 列 0.38s · 读全 7 列 0.63s
    （扫描代价几乎线性于**解码列宽**；而那句 join 1.19s 里扫描占 0.63s = 53%）

做法与第一步同源，但下沉到 Scan：`proj_src` 加第三态 `ProjSrc::Null`
= **本列不解码、按 NULL 产出**（`Scan::restrict_read`）。**列还在、列序不变 ⇒
上层索引一个字都不用改** —— 这正是它比"收窄投影"（要重映射全部索引）安全的地方。
标注复用同一条自顶向下的传播（`annotate_join_needs` 本来就在算每段要哪些列）。

**实测（`QSDB_JOIN_NO_PROJ=1` 开关对照）**：

| | 开 | 关 | 收益 |
|---|---|---|---|
| `t×d` 聚合 N=1 墙钟 / CPU | **0.67s / 0.63s** | 1.29s / 1.27s | **1.93× / 2.0×** |
| N=1 峰值 RSS | **103MB** | 301MB | **2.9×** |
| 16 核 墙钟 / RSS | **0.28s / 155MB** | 0.49s / 417MB | 1.75× / 2.7× |

基准（0 FAIL）：`complex_join_group` **0.263s（2.16×）**、`complex_three_way`
**0.336s（2.77×）**；峰值 RSS 从 1.08–1.09GB 掉到 **374MB / 227MB**（对手 42/36MB）。

> ⚠️ **踩到一个被既有测试抓住的真 bug，值得后人警醒**：
> `SELECT round(sum(score)) FROM t` 挂了 —— `build()` 的**单表列裁剪会把整棵计划的
> 索引重映射到裁剪后的空间**，而我把那些位置拿去查 `def.columns`（**全表序**）
> ⇒ 取到**别的列**（`cnt` 当成 `score`）⇒ 扫描读空 ⇒ 聚合回 NULL。
> **"同一个计划里位置属于哪个空间"是这个优化最容易错的地方**（掩码那步也差点栽）。
> 修法：闸门 `allow_scan_read = scan_proj.is_none()`（有值 ⟺ 已被外层裁剪）。

#### ⚠️ 读内存那一列之前，先扣掉**热段缓存**（约 300MB）

上表的"我们 RSS"**不是工作集**：默认热段缓存 1GB（`--cache-mb` 可调、**可挤兑**），
且 bench 每个用例在**同一进程跑 3 轮**，缓存填得比单跑更满。同一台机同一查询实测：

| 用例 | 默认 | `--cache-mb 0` | DuckDB |
|---|---|---|---|
| complex_join_group | 515MB | **215MB** | 42MB |
| complex_three_way | 519MB | **218MB** | 36MB |
| simple_group | 270MB | **155MB** | 414MB（**比我们高**） |

**结论**：剔除缓存后，join 类是 215MB vs 对手 36–42MB（**5–6×**，不是 25×）；
`simple_group` 反而**比对手省**。所以"1GB vs 42MB"这种比法**会把自己说胖**——
与 §二之二 那把歪尺子同族（都是**用不同口径比**）。要真正压工作集，得看 215MB 里
的构成（join build 侧 + 组表），那是 P0③/P1⑥ 的事；**别把缓存算进"物化开销"**。

**★ 结论**：**闸门 0 FAIL**，"全面领先"还差第 1 名（**能力缺口**：原生聚合 DISTINCT）
与第 2、3 名的**后半段**（P0③ 共享建侧）。第 4-6 名是各自独立的一块（导出/窗口/CSV）。

> **单线程成本才是天花板**：`t×d` 聚合 1 片时 **1.29s**，而 DuckDB 全部 0.12s（16 线程）
> ——即便我们铺满 16 核，`1.29/16 ≈ 0.08s` 也要跟它的**每核效率**比。
> 所以并行到 4 片只是把"浪费掉的核心"捡回来一部分；**真正的差距在每行成本**，
> 那是 P1⑥（探测批量化）之类的事。

其余对照（同轮实测，详见 §一 与 §四）：

|---|---|---|---|
| import_csv | 6.03s | 3.63s | 1.7×（我们 100MB vs 对方 **1180MB**） |
| import_parquet | 2.06s | 1.86s | 1.1× |

**结论：内存不是分析查询的瓶颈。** 给到 2GB 预算 + 1GB 缓存，全部用例变化在 ±5%
以内——因为**我们默认本来就不限内存**（`memory_budget_bytes` 不设 = 池不限）。
差的 2-6 倍在**算子执行策略**（join 探测、窗口整分区物化），不是内存。

## 二之二、与 PostgreSQL 18.4 的同形状对照（`192.168.1.13`，Docker `some-postgres`）

用户问"5M 行导入不该这么慢"。用**同数据、同语句形状**在 PG 上实测：

| 通道 | QSDB | **PG 18.4** |
|---|---|---|
| **5000 条 × 1000 行 autocommit INSERT**（= `import_insert` 形状） | **81.3s** | **49.5s**（默认 `synchronous_commit=on`） |
| 同上，`synchronous_commit=off`（免每次提交 fsync） | （我们默认就不 fsync） | **39.0s** |
| **批量通道**：我们 `append` / PG `COPY FROM CSV` | **4.03s** | **7.95s** |
| CSV → 管理表 | **5.44s** | **7.95s**（COPY FROM CSV） |
| 导出 CSV（扫描 → CSV） | **4.61s** | **2.55s**（`COPY … TO … WITH CSV`） |

**读法**：
- SQL 文本通道**天生就是几十秒级**——PG 同样形状也要 39-50s；且 PG 的 fsync 开关只差
  10s，说明大头在**逐条语句的解析/绑定/执行**（与我们一致）。我们慢 1.6-2×，
  **同一量级**，不是"哪坏了"。
- **批量通道我们比 PG 快 2×**（4.03s vs 7.95s）；CSV→表也比 PG 的 COPY 快。
- 导出上 PG（2.55s）比我们（4.61s）快——差距来源见 §四。

## 三、`import_insert` 为什么 81s（定性：不是内核缺陷，是通道形态）

**与 DuckDB 同形状对照（同一份 605MB SQL 文件、5000 条 × 1000 行）**：

| 库 | 耗时 |
|---|---|
| **QSDB** | **81s** |
| **DuckDB 1.1.3**（`duckdb file.db < ins.sql`） | **484s** |
| PG 18.4 | 49.5s |

→ **这条通道上我们比 DuckDB 快 6×**（DuckDB 每条 INSERT 一次事务，纯 OLAP 引擎在这条路上很痛），
比 PG 慢 1.6×（PG 的解析器更快）。**所以 `INSERT VALUES` 不是我们相对 DuckDB 的短板。**


5000 条独立 `INSERT INTO t VALUES (…1000 行…)`，本机拆解（同形状语句）：

| 行数/语句 | 纯解析 | 解析+执行 | 解析占比 |
|---|---|---|---|
| 1000 | 7.4ms | 19.3ms | 39% |
| 10000 | 77ms | 117ms | **66%** |

→ 5000 × 19ms ≈ 95s ✓ 与真机 81s 吻合。**成本几乎全在"每条语句的解析+绑定+提交"**。

- 普通 RDBMS 批量灌 5M 行也是几秒级——但那走的是 **COPY / LOAD DATA / 批量绑定**
  （**批量通道**），不是 5000 条 autocommit 语句。PG 上同样形状也要几十秒。
- 我们的批量通道是 `append` / HTTP IPC：**同数据 4s（20×）**。qsdb-jdbc 已把这条
  写进 javadoc，我们两边口径一致。
- 结论：**这条用例是"SQL 文本通道基线"，不作为达标项**；要更快得改解析/绑定
  （性价比低）或让调用方走 IPC（已文档化）。

## 三之二、`import_csv` 的 1.78× 定位：**不是"单线程"，是每字节一次虚调用**

### 先拆时间（新增诊断用例 `import_csv_parse_only`）

| | 时间 | 占比 |
|---|---|---|
| **`import_csv_parse_only`**（`SELECT sum(v) FROM read_csv(…)`，只解析） | **3.263s** | **解析 53%** |
| `import_csv`（解析 + 写段） | 6.111s | 写段 ~47% |
| `import_parquet`（对照：读 parquet + 同一个写段） | 2.190s | — |

> 用 `sum(v)` 而不是 `count(*)`：后者可能被元数据短路，那测的是"短路有多快"
> 而不是"解析有多慢"。

### 解析慢在哪：**每个字节一次 trait 虚调用**

`crates/qsdb/src/csv.rs` 的字节源：

```rust
fn bump(&mut self) -> Result<Option<u8>> {
    let b = self.r.fill_buf()?;      // ← BufRead 的 dyn 调用，每字节一次
    match b.first().copied() {
        Some(c) => { self.r.consume(1); Ok(Some(c)) }
        None => Ok(None),
    }
}
```

`next_record` 是逐字节状态机，每个字节都走 `bump()`。CSV 文件 **535MB**
⇒ 约 **5.35 亿次虚调用**；按 ~5ns/次算 **≈2.7s**——与实测 3.26s 基本吻合。

**再加上每字段两次堆分配**：`Vec<u8>` + `field()` 里的 `String::from_utf8`。
5M 行 × 7 列 = **3500 万字段 ⇒ ~7000 万次分配**；另有每行一个
`Vec<Option<String>>`（5M 次）。

⇒ 这一格的病根**不是"只用一个核"**（那是并行化能解决的），而是
**把最多 5.35 亿次调用与 7500 万次分配放在了每行的必经之路上**。
并行只是把常数摊到多个核上；**先把这个常数降下来**收益更大，而且不需要任何
对缓存/延迟的猜测。

### ✅ 修法已落地（2026-10-14，`9db1ec1` + `4f97230`）

| 查询 | 最初 | 换字节源后 | **改分配后** |
|---|---|---|---|
| `import_csv_parse_only` | 3.263s | 2.857s | **0.953s** |
| `import_csv` | 6.111s | 5.780s | **3.518s** |

同轮 DuckDB `import_csv` = **3.231s** ⇒ **1.78× → 1.08×**（基本追平）。
（bench 全量：`import_csv` 3.489s，闸门 **0 FAIL**。）

**两条改动的实际贡献**（值得记，因为归因错过一次）：

| 改动 | 解析耗时 | 说明 |
|---|---|---|
| 字节源：`fill_buf()+consume(1)` → 自有缓冲 + 游标 | 3.263 → 2.857s | 只削掉每字节的循环开销 |
| **字段字节写进记录级 arena（去掉每字段两次分配）** | 2.857 → **0.953s** | **主因** |

⚠️ **归因更正**：换字节源那批我写的"每个字节一次 trait **虚调用**，5.35 亿次
≈2.7s"是**错的** —— `ByteSrc<R: BufRead>` 是**泛型**，单态化后是静态调用，
`BufReader::fill_buf` 就是一次边界检查、编译期内联，**根本没有 dyn 派发**。
真正的 2.7s 在 **约 7000 万次堆分配**（`Vec<u8>` + `String` 每字段各一次）。
⇒ 教训：**"看起来像虚调用"不等于有虚调用**；泛型参数上的 trait 方法要先看单态化。

### ⚠️ P0②（并行写段）的前提**实测不成立**（2026-10-14）

路线图写"段编码（parquet+zstd）单线程 —— 是导出/导入的共同天花板"。**两条都不对**：

1. **写段本来就是并行的**：`write_segments`（`write.rs`）按 `PARALLEL_SEG_ROWS`
   切块后 `into_par_iter()`，5M 行一次提交 = 16 块（打满 16 核）。
2. **导出那 95% 压根不在内核**：见 §四（DuckDB 跑 `COPY … TO` 内核原语，
   我们跑 bench 工具里 arrow 的单线程 writer）。

**新增诊断用例 `import_append_once`**（造数在计时外 + **一次调用 = 一次提交**）
量出"纯写段"：

| | 时间 |
|---|---|
| `import_append_once`（纯写段，5M 行一次提交） | **1.72–1.90s** |
| `import_parquet`（读 parquet + 写段） | 2.175s ⇒ 读 ≈ 0.45s |
| `import_csv` | 3.592s |

⇒ 写段 1.72s 对 DuckDB 的约 1.4s 只差 ~1.2×，**不是大缺口**。

#### ⚠️ 一个被实测否决的改动：调小 `PARALLEL_SEG_ROWS`

观察到 `sql::INSERT_FLUSH_ROWS = 512k` ⇒ 5M 行分 **10 次提交**，而每次提交只有
`512k / 256k = 2` 块 ⇒ 16 核里只用 2 个。于是把 `PARALLEL_SEG_ROWS` 256k → 64k
（每次提交切 8 块）。**实测几乎没有收益**：`import_csv` 3.689 → 3.580s
（±噪声，同批 spread 10.9%），`import_append_once` 纹丝不动（本来就 16 块）。
**代价是段文件数 ×4** ⇒ 已回退。⇒ 并行度不是这里的瓶颈。

#### ⚠️ 一把歪尺子（自己造的）：`import_csv_parse_only` 只读了 1 列

该用例原本是 `SELECT sum(v) FROM read_csv(…)` —— 聚合只引用**一列** ⇒
列裁剪生效、**其余 6 列根本不解析** ⇒ 把 0.95s 当成了"解析成本"，
而 `import_csv` 减掉写段后还剩 **~1.8s**，两边对不上。
改成 `sum(id)+sum(g)+sum(v)+count(gs)+count(s)+count(dt)`（7 列全碰、无法裁剪）
之后读数 **1.469s** —— 账才平：**解析 1.47 + 写段 1.72 + 管线 ~0.4 = 3.59s** ✓

⇒ 同族第**四**把尺子（前三次：断言进计时区间、RSS 含热缓存、导出比内核原语）。
**规律很一致：每次"两个数对不上"，先怀疑尺子。**

### 原先列的修法（按收益/风险排序，留档）

1. **去掉每字节的虚调用**：字节源持一块 `&[u8]` + 游标（`pos`），`bump` 变成
   一次数组索引，只在跨块时 `fill_buf`。**这一条覆盖 ~2.7s 里的大部分。**
2. **去掉每字段的两次分配**：`field()` 改成从**复用的字节缓冲**取切片，
   Arrow builder 直接吃 `&[u8]`（`StringBuilder` 支持 `append_value(&[u8])` 之类），
   不再为每个字段造 `String`。
3. **（之后）再谈并行**：按行边界切段并行解析。**排在 1、2 之后** —— 常数没降下来
   之前并行只是分摊同一个常数。

⚠️ 这是**正确性敏感**的重写（引号态、`
`、BOM、字段宽度校验、非法 UTF-8
必须报错不能 lossy），`crates/qsdb/src/csv.rs` 现有 711 行；动手前先把
`tests/read_csv.rs` 覆盖的边界过一遍，并**先补引号内换行/CRLF/空字段的用例**。

## 四、导出为什么还慢：**大部分不在内核**（2026-10-14 定位）

### 先把时间拆开（新增诊断用例 `export_scan_only`）

| | 时间 | 占导出 |
|---|---|---|
| **`export_scan_only`**（纯扫描 5M 行 × 7 列，不写） | **0.139s** | **4.6%** |
| `export_parquet` | 3.053s | 写占 **95.4%** |
| `export_csv` | 4.164s | 写占 **96.7%** |

**内核扫描只占 4.6%** —— 导出的耗时几乎全在"写段"这一步，而这一步**不在内核里**。

### ⚠️ 所以这一格是**第三把歪尺子**

| | 实现 |
|---|---|
| DuckDB 侧 | `COPY (SELECT …) TO '…' (FORMAT PARQUET)` —— **内核原语**（并行、自带压缩调优） |
| 我们侧 | 内核 `db.scan()`（并行）**+ bench 工具里 arrow-rs 的通用 `ArrowWriter` 单线程写** |

`crates/qsdb-bench/…/bench_suite.rs` 的 `scan_to_parquet` / `scan_to_csv` 就是
"拿流式扫描结果喂给 arrow 的 writer"。也就是说这 4.4× 里绝大部分是
**"DuckDB 的生产导出原语 vs 我们测试工具里的朴素 writer"**，不是内核差距。

同族前两次：**断言跑在计时区间里**（把自己说慢一倍）、**RSS 里含 1GB 热段缓存**
（把缓存算成物化开销）。三把尺子的共同点是**量的东西与想说的东西不是一回事**。

### 但它**不是**"我们其实不慢"——用户体感就是慢

我们没有导出原语（`docs/生态工具升级通知.md` F9）：任何调用方（qsdb-sync / jdbc /
odbc）**都得自己写 writer**，拿到就是 arrow-rs 单线程的水平。所以真正的修法不是
"调 bench"，而是**把导出原语做进内核、并让它并行**：

- parquet：按 row-group 分块，各块**并行编码**（含 zstd），再顺序落盘（parquet
  文件本就是"row group 序列 + footer"）；
- CSV：按批并行格式化，顺序写。

⇒ **这一格从"性能调优"重新归类为"能力缺口（F9）"**，与 P0② 原来写的
"段编码并行"不是一回事（那条讲的是**导入**侧的写段）。

## 四之零、导出侧的原始记录（已定位，未修）

**先修了我自己的测量错误**：CSV 导出的 6.4s 里有相当一块是 harness **逐值
`array_value_to_string`**（3500 万次 `String` 分配），换成 arrow 的批量 CSV writer
后 → **4.61s**（修正前后对比见 §一）。剩下的差距是引擎侧：

- ~~扫描是单线程~~ **已修**：并行扫描（`ParScanExec`）现在对 `db.scan()` / 普通
  `SELECT` **透明生效**（`QSDB_SCAN_SERIAL=1` 可关）。**剩下的天花板在写侧**：段编码
  （parquet + zstd）单线程——导出 = 并行扫 + 串行写，所以 3.7-5× 的差距挪到了这里
  （路线 P0②"并行写段"，导入侧已落地、导出侧还没接）。
- **压缩档与对手不同**：我们段文件写的是 **zstd**；DuckDB 的 `COPY` 默认 **snappy**
  （更便宜）。导出 = 读 zstd + 写 zstd，这条差异会直接体现在吞吐上。
  要公平比"吞吐"就该同压缩档比；要追平就得给导出侧更便宜的档（或并行压缩）。
- 以上都不是"内存不够"：给到 2G+1G 缓存，导出数字几乎不变（§二）。
  **当前导出落后的主因是"写侧单线程 + 压缩档更贵"**（PG/DuckDB 的 `COPY` 是多线程
  且默认 snappy）。

## 四之一、无依赖批量通道（`qsdb-bulk` / `csv`）—— 5M 行实测

生态工具（尤其 Java）不想引 arrow-java（JDK 11+ + FlatBuffers/Jackson）就拿不到 IPC
快通道。补上两种**零依赖**编码后的实测（`http_bulk`，服务端 `qsdb server`）：

| HTTP 写通道 | body | 耗时 | 客户端依赖 |
|---|---|---|---|
| `format=ipc` | 544MB | **0.94s** | Arrow 库 |
| **`format=bulk`**（列式二进制，[规范](bulk-format.md)） | 540MB | **1.93s** | **零** |
| `format=csv`（文本） | 536MB | 28.3s | **零** |
| （对照）SQL 文本逐条 INSERT | — | 81s | 零（但慢 42×） |

- **`bulk` 是"列式生产者"该用的**（手上已经有列式数组的 Rust/Arrow 侧）：比逐条 SQL
  快 **42×**，只比 IPC 慢 2×（差在解码要逐列建 builder）。
  **按行取值的驱动请用 `rows`**——同一台机上更快（见 §四之二）。
- **CSV 写**慢在"每个单元格一次 `Literal`"（与 `INSERT … VALUES` 同一个根因，
  见 `docs/超越DuckDB路线.md` P1⑨）——文本通道先当"能用"，优化排在后面。
- 读侧同理：`/query` 支持 `"format":"bulk"|"csv"|"ipc"|"json"`。

## 四之二、行式通道 `qsdb-rows`（驱动向）—— 5M 行实测

同一台机、同一份数据、同一个 server（`http_bulk`，body 均 535-544MB）：

| 通道 | ① 整批（1 请求） | ② 流式（76 请求 × 65536 行） | ③ 读（`SELECT *`） | 客户端依赖 | 客户端内存 |
|---|---|---|---|---|---|
| `format=ipc` | 1.055s | 2.800s | 1.155s | Arrow 库（Java 需 JDK 11+） | O(全量) |
| **`format=rows`**（行式） | **1.037s** | 3.583s | 1.142s | **零** | **O(一块)** |
| `format=bulk`（列式） | 1.997s | 2.971s | 1.052s | **零** | O(全量) |
| `format=csv` | 27.7s | 28.5s | 2.221s | **零** | 流式 |

**这张表回答了驱动侧的选型问题**：行式不但**实现最省**（边收边写、零转置），实测还
**与 IPC 持平、比列式 `bulk` 快 ~2×**（整批）。于是"最省事的格式"恰好也是"最快的
格式"，驱动不必在易用性与性能之间取舍。

- **写入侧的四个通道落库数据逐列校验和一致**（`count/sum/min/max` 对齐，
  整批与流式各一遍）——通道是等价的，只差编码。
- **② 流式反而比 `bulk` 慢**：`bulk` 把整份负载解成**一个 5M 行的批**，服务端后续
  再切；`rows` 是**逐块批**（65536 行），分帧即分块。两者都正确，但 `rows` 更贴近
  驱动"攒够就发"的形态（72 次 65536 行的请求，客户端内存与总量无关）。
- ③ 读的 `rows` 与 `ipc`/`bulk` 同档，`csv` 慢 2×（文本膨胀 + 逐值格式化）。
- **跨语言互操作已实证**：qsdb-jdbc 的 Java `QsdbBulkWriter`（照 `docs/rows-format.md`
  独立实现）打到内核真 server，`BulkChannelIntegrationTest` **6/6 绿**（全类型往返含
  DECIMAL/BINARY/TIMESTAMP 与 NULL、分块跨多次请求、并发装载、空写 no-op、缺表/类型
  不符的清晰报错）。**两个独立实现按同一份文档对死**——这是格式冻结该有的验证。

## 四之三、生态工具该怎么导（**wire 层不是瓶颈，SQL 文本才是**）

用户关切：生态工具（导入/导出工具、ODBC/JDBC 桥）必然多一层 wire，
"内核直接操作都没达标，再加中间层不敢想"。—— 实测下来**这个担心不成立**：

| 通道（5M 行） | 耗时 | 说明 |
|---|---|---|
| **HTTP 导入 `/api/v1/write`（IPC 一次 544MB 整批）** | **2.18s** | 生态工具/驱动桥该走的 |
| HTTP 导入 逐批（76 个请求 × 65536 行） | 3.31s | 工具按自己节奏流式推 |
| **HTTP 导出 `/query?format=ipc`** | **0.58s** | 比 DuckDB 导 parquet（0.87s）还快 |
| HTTP 导出 `/query?format=json` | 5.18s | JSON 文本膨胀，别用于大批量 |
| 嵌入 `db.append()` | 4.03s | 同一档 |
| SQL `INSERT … SELECT FROM read_parquet` | 2.06s | 同一档 |
| **SQL 文本 5000 条 INSERT** | **81s** | ← **唯一的慢通道** |

**结论（直接指导生态工具设计）**：

1. **批量进出走二进制（IPC）通道，不要走 SQL 文本**——差 37 倍（81s vs 2.18s），
   而且这个差距是**任何数据库都有的**（PG 同样形状 49s）。
2. **wire 本身的代价几乎为零**：544MB IPC 过 loopback + 内核 append = 2.18s，
   与嵌入直连同档；导出 IPC 0.58s。
3. 因此：**ODBC/JDBC 桥的批量写应实现为 `/write` 的二进制通道**，而不是把 N 条 SQL
   语句发过去（驱动的 `executeBatch` 目前是后者）。**选哪个格式**：驱动按行取值 →
   `format=rows`（零依赖、与 IPC 同速、客户端内存 O(一块)，见 §四之二）；手上是
   列式数组 → `format=bulk`；有 Arrow 库 → `format=ipc`。导出侧同理（`/query` 的 `format`）。
4. 真正的短板仍在内核算子层（§二/§四），与 wire 无关。

## 五、跑基准的姿势（把"看数字"变成"过闸门"）

```bash
# 全部用例，默认 10s 闸门（超时即 FAIL + exit 1）
bench_suite --dir /home/qctc/qsdb-suite --rows 5000000 --all --max-seconds 10
# 单用例 / 诊断
bench_suite --dir DIR --case import_parquet --rounds 3
bench_suite --dir DIR --sql "INSERT INTO t SELECT * FROM read_parquet('…')"
# 对照 DuckDB（读同一份源文件）
bench_suite --dir DIR --gen-duckdb-sql && python3 runner.py DIR/results/duckdb.sql
```

可用旋钮：`--budget-mb`（内存预算）/ `--cache-mb`（扫描缓存）/ `--per`（造数批大小，
**仅供对照实验**——正常使用不该关心它）。

**环境变量旋钮**（同样是**对照实验**用，别在部署里调）：
`QSDB_SCAN_SERIAL=1` 关并行扫描 · `QSDB_SHARDS=N` 指定聚合分片数（默认
`clamp(核数,1,4)`，上限依据与实测曲线见 `exec_builder::shard_count`）·
`QSDB_JOIN_PROF=1` / `QSDB_JOIN_SHARD_PROF=1` / `QSDB_AGG_PROF=1` 打诊断到 stderr ·
`QSDB_JOIN_NO_PROJ=1` **关掉 join 输出投影**（有风险的优化必须能关掉，也用于 A/B 对照）。

**判定列的含义**：`PASS` 过闸门 · `FAIL` 超时（会让 bench_suite 退出码非 0）·
**`BASE` = 非达标项**（照测照印，但**不进闸门**）。`BASE` 目前只有 `import_insert`：
它走「SQL 文本逐条 INSERT」这条**任何人都不该用**的通道（比二进制通道慢 37×，
PG/DuckDB 同形状一样慢），耗时取决于 SQL 解析与语句往返、**与内核算力无关**。
**为什么要有这一档**：闸门的价值全在"绿 = 没退步"；一个**恒定超时**的用例会把闸门
变成**恒红**，而恒红的闸门等于没有闸门——真回归会淹没在常驻噪声里。
入这一档的标准是**"这条通道本身不是产品目标"**，不是"这条慢"。

**三条纪律**（都踩过坑，见 §二之二）：

1. **断言不许进计时区间**。校验用的都是同形状的真实查询，放进 `t0`/`elapsed()`
   之间就是把"查询 + 校验"一起计时（`simple_distinct` 曾因此虚高一倍）。
2. **改 bench 的造数形状 = 让已有数字作废**。`gs` 从全局唯一改成半数重复就作废过
   一整格；改之前先在文档里标清楚哪一格要重测。
3. ⚠️ **推源码到远端后要 `touch`，再确认二进制真的重建了**。用 tar/scp 推源码会
   **保留 mtime**，若新文件的 mtime 比上次构建**更旧**，cargo 判"新鲜"⇒ **不重编**
   ⇒ 你测的是**旧二进制**（2026-10-14 实测：`Finished in 0.32s`，二进制里没有刚推的改动）。
   自查办法：`grep -a '<改动里的一个新字符串>' <二进制>`，或看构建是否真的跑了 2-3 分钟。
   **尺子歪了比被测物歪更危险——而且这一种歪得最隐蔽（数字全对，测的是别人）。**
