# 真机基准对账（vs DuckDB 1.1.3）

> 机器：`192.168.1.14`（CentOS 7 / 16 核 / 62G / `/home` 582G 可用），数据在
> `/home/qctc/qsdb-suite`。工具：`crates/qsdb-bench/src/bin/bench_suite.rs`（本仓）
> + `/root/bench/duckdb`（CLI v1.1.3，官方新版二进制要 GLIBC 2.23，这台是 2.17）。
> 两侧读**同一份源文件**（同一份 CSV / Parquet），每用例 3 轮取中位、独立子进程
> （峰值 RSS 用 `/proc/self/status` 的 `VmHWM`）。
>
> **口径警告**：这台机上有 Hadoop/Spark/Docker 在跑（load ≈1.2/16），且**第 1 轮是
> 冷缓存**（离散度一度到 100%）。故数字**看量级与相对关系**，别当精确值。

## 一、导入 / 导出（5M 行，7 列）

| 用例 | 修复前 | **修复后** | DuckDB | 相对 | 我们内存 / 对方 |
|---|---|---|---|---|---|
| import_parquet（parquet→管理表） | 103s | **2.06s** | 1.78s | **1.16×** | 181MB / 313MB |
| import_csv（CSV→管理表） | 81.8s | **5.44s** | 3.11s | **1.75×** | 101MB / **1151MB** |
| import_append（内存批直写） | 10.5s | **4.03s** | — | — | 29MB |
| export_parquet（扫描→parquet） | — | **3.62s** | 0.87s | 4.2× | 1.87GB / 1.60GB |
| export_csv（扫描→CSV） | 6.44s | **6.42s** | 0.89s | 7.2× | 1.72GB / 1.21GB |
| import_insert（SQL `INSERT VALUES` 批量） | 81s | **81.3s** | — | — | 33MB |

**内存这一列的说明**：我们这轮给的是 `--budget-mb 2048 --cache-mb 1024`（用户要求的
"放大到 2G 对比"），RSS 里的 1.7-1.9GB **基本就是那 1GB 扫描缓存 + 工作集**。
不给缓存时导入只有 100MB 上下（见 §二"导入"行）。

### 修复前为什么慢 26-58 倍（三个根因，都不是"哪都不行"）

1. **默认耐久档在做 fsync**：`Durability::ProcessCrash` 文档承诺"页缓存即持久"，
   实现里 `write_atomic_opts(sync=false)` 仍调 `f.sync_all()`。一次 `db.append` =
   段 + manifest + idx，其中**两次**走这里 → `.14` 实测 **45ms × 2/次**。
2. **切片批的字节数虚高 61 倍**：`RecordBatch::get_array_memory_size()` 按底层缓冲
   **容量**算——500k 行父批切出 8192 行仍报 4,000,096 字节（逻辑 65,536）。后果：
   攒批阈值"每批都超"→ 每批提交一次；**记账也虚高** → 配额下过早落盘/误报
   `MEMORY_PRESSURE`（"明明装得下"）。
   修法：`memory::batch_bytes()`（切片感知）+ INSERT 攒批改**行数为主**（512k 行）。
3. **`Qsdb::append` 按"批"提交而不是按"调用"提交**：传 13 个批 = 13 次提交
   （13 个段 + 13 次 manifest + 13 次索引）。`INSERT … SELECT` 的源按 8192 行一批
   扫出 → 5M 行 **610 次提交**；同数据按 65536 行一批传进来只要 10s。
   修法：**一次调用 = 一次提交**（按分区归并后 concat 成一个段；超 256MB 切块）。
   **这一条是主因**，也是"用户不该知道批大小"的落点。

## 二、分析查询（5M 行）

| 用例 | 我们（无预算） | 我们（2G+1G 缓存） | DuckDB | 相对 |
|---|---|---|---|---|
| simple_count | 0.001s | — | 0.021s | **快 20×** |
| simple_filter | 0.048s | — | 0.041s | 持平 |
| simple_group（10 万组） | 0.204s | 0.217s | 0.183s | 1.11× |
| simple_topn | 0.033s | — | 0.041s | **快 1.2×** |
| simple_distinct（高基数） | 0.032s | 0.033s | 0.223s | **快 7×** |
| complex_join_group | 0.693s | 0.709s | 0.122s | 5.7× |
| complex_cte | 0.167s | 0.185s | 0.122s | 1.4× |
| complex_window | 0.096s | 0.097s | 0.041s | 2.3× |
| complex_three_way | 待重测 | — | 0.122s | — |

**结论：内存不是分析查询的瓶颈。** 给到 2GB 预算 + 1GB 缓存，全部用例变化在 ±5%
以内——因为**我们默认本来就不限内存**（`memory_budget_bytes` 不设 = 池不限）。
差的 2-6 倍在**算子执行策略**（join 探测、窗口整分区物化），不是内存。
而且**我们的内存占用普遍比对手小**（简单查询 3-30MB vs 21-450MB）。

## 三、`import_insert` 为什么 81s（定性：不是内核缺陷，是通道形态）

5000 条独立 `INSERT INTO t VALUES (…1000 行…)`，本机拆解（同形状语句）：

| 行数/语句 | 纯解析 | 解析+执行 | 解析占比 |
|---|---|---|---|
| 1000 | 7.4ms | 19.3ms | 39% |
| 10000 | 77ms | 117ms | **66%** |

→ 5000 × 19ms ≈ 95s ✓ 与真机 81s 吻合。**成本几乎全在"每条语句的解析+绑定+提交"**。

- 普通 RDBMS 批量灌 5M 行也是几秒级——但那走的是 **COPY / LOAD DATA / 批量绑定**
  （**批量通道**），不是 5000 条 autocommit 语句。PG 上同样形状也要几十秒。
- 我们的批量通道是 `append` / HTTP IPC：**同数据 4s（20×）**。qsdb-jdbc 已把这条
  写进 javadoc，我们两边口径一致。
- 结论：**这条用例是"SQL 文本通道基线"，不作为达标项**；要更快得改解析/绑定
  （性价比低）或让调用方走 IPC（已文档化）。

## 四、导出为什么还慢 4-7 倍（已定位，未修）

- **单线程 + zstd**：我们 `db.scan()`（单线程迭代器）+ `ArrowWriter`（zstd）逐批复压缩；
  DuckDB 的 `COPY` 是**多线程 + snappy**（默认更便宜）。
- **CSV 是逐值 `array_value_to_string`**（每个值一次 `String` 分配），DuckDB 是批量
  格式化。5M 行 × 7 列 = 3500 万次分配 → 6.4s（≈180ns/值）。
- 两条都不是"内存不够"，各自是独立工作项：① 非聚合查询的并行扫描（`ParScanExec`
  目前只在并行聚合路径里用）；② 导出侧的批量格式化 / 更便宜的压缩档。

## 五、跑基准的姿势（把"看数字"变成"过闸门"）

```bash
# 全部用例，默认 10s 闸门（超时即 FAIL + exit 1）
bench_suite --dir /home/qctc/qsdb-suite --rows 5000000 --all --max-seconds 10
# 单用例 / 诊断
bench_suite --dir DIR --case import_parquet --rounds 3
bench_suite --dir DIR --sql "INSERT INTO t SELECT * FROM read_parquet('…')"
# 对照 DuckDB（读同一份源文件）
bench_suite --dir DIR --gen-duckdb-sql && python3 runner.py DIR/results/duckdb.sql
```

可用旋钮：`--budget-mb`（内存预算）/ `--cache-mb`（扫描缓存）/ `--per`（造数批大小，
**仅供对照实验**——正常使用不该关心它）。
