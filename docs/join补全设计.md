# join 补全设计（把"常用的那些"补齐）

> 起因（2026-10-15）：问"我们到底支持哪几种 join"。摸底探针
> （`crates/qsdb/tests/join_common_probe.rs`）跑出 **8 条缺口**，其中**两条是最阴的
> 那一类**：值全对、计划**静默退化成叉积**（结果逐行相同 ⇒ 值断言永远绿，
> 只有计划形状能抓到）。那两条正是 `complex_three_way` 113× 的同一家族。
>
> 本文只写**怎么做与为什么这么做**；做完后把探针转成断言，结论回写
> `docs/SQL支持面.md`。

---

## 一、现状（实测，不是读代码猜）

`l(k, m)` = (1,10) (2,20) (3,30)；`r(k, m, v)` = (2,20,200) (3,35,300) (4,40,400)
（刻意让**复合键**与**单键**答案不同：`k=3` 的 `m` 两侧不等）。

| 形态 | 期望行数 | 实测 | 计划 Join/Cross | 性质 |
|---|---|---|---|---|
| `INNER JOIN … ON l.k = r.k` | 2 | 2 ✓ | 1/0 | 好 |
| `INNER JOIN … ON l.k = r.k AND l.m = r.m` | 1 | 1 ✓ | **0/1** | ⚠️ **静默退化** |
| `INNER JOIN … ON l.k = r.k AND r.v > 250` | 1 | 1 ✓ | **0/1** | ⚠️ **静默退化** |
| `LEFT JOIN … ON l.k = r.k` | 3 | 3 ✓ | 1/0 | 好 |
| `LEFT JOIN … ON l.k = r.k AND r.v > 250` | 3 | **ERR** | — | 缺口 |
| `LEFT JOIN … ON l.k = r.k AND l.m = r.m` | 3 | **ERR** | — | 缺口 |
| `RIGHT JOIN … ON l.k = r.k` | 3 | **ERR** | — | 缺口 |
| `FULL OUTER JOIN … ON l.k = r.k` | 4 | **ERR** | — | 缺口 |
| `CROSS JOIN r` | 9 | **ERR** | — | 缺口 |
| `JOIN r USING (k)` | 2 | **ERR** | — | 缺口 |

**为什么"静默退化"必须优先**：`ON a.x = b.x AND a.y = b.y` 是分析场景里几乎每天
都写的形态。今天它**不报错、不警告**，只是把两侧行数乘起来算——两张 500 万行的表
就是 2.5×10¹³ 次比较。"结果对"让它躲过了所有既有测试。

## 二、要做哪些（按"常用度 × 危害"排序）

| # | 项 | 为什么排这里 |
|---|---|---|
| **P0-1** | **复合等值键**（`AND` 串起来的多个等值） | 常用到近乎默认写法；今天是**静默退化** |
| **P0-2** | **等值 + 残留谓词**（键之外的条件） | 同上；且 **LEFT 上直接报错**（表达力缺口） |
| **P1-1** | **`RIGHT [OUTER] JOIN`** | 标准三件套之一；可**换边**实现，代价低 |
| **P1-2** | **`FULL [OUTER] JOIN`** | 标准三件套之一；**唯一没有换边写法**的 |
| **P1-3** | **`CROSS JOIN`** | 今天的替代写法是 `ON TRUE`（能用但反直觉） |
| **P2-1** | **`USING (cols)`** | 语法糖；BI 工具常生成。**NATURAL 不建议做**（隐式按列名匹配，是静默错列的高发区） |
| **P2-2** | **非等值 `LEFT/RIGHT`**（range join） | 区间连接/ASOF 类需求；今天明确拒 |

**不做**：`SEMI/ANTI JOIN` 关键字（`IN`/`EXISTS` 已覆盖语义）、`NATURAL JOIN`
（隐式匹配 = 静默错列）、`LATERAL`/`CROSS APPLY`。

## 三、逐项做法（含**语义陷阱**——写错就是静默错值）

### P0-1 复合等值键

**改哪**：`translate.rs::split_equi_condition` 现在只认**单个**等值（返回一对键），
要改成把 `ON` 按 `AND` 拆开、逐项判定，返回 `Vec<(PhysExpr, PhysExpr)>`。

**执行层不用改**：`LogicalPlan::Join { left_keys: Vec<..>, right_keys: Vec<..> }`
本来就是向量；`HashIndex::int_ok` 只在 `keys.len() == 1` 时走 i64 免编码快路径，
多键自动落到 `HashIndex::Bytes`（编码后比较）✓。

⚠️ **陷阱**：`ON a.k = b.k AND a.m = a.m` —— 第二个合取项**两侧同源**，不是 join 键。
不能因为"是等号"就当键：那会造出一个恒真键（还把同侧的列编码进哈希）。
**规则**：合取项的两侧必须**分属左右**才算键；同侧的等值**降级为残留谓词**
（P0-2 的机制），既不是键也不丢。而"任一侧都无法判定归属"（如 `l.k + r.k = 5`）
→ 整体走残留。

### P0-2 等值 + 残留谓词

**语义**：`ON` = 键（参与哈希匹配） + 残留（对**匹配上的对**再判）。

⚠️ **头号陷阱：LEFT 的残留不能提到 `WHERE`**：

```sql
SELECT count(*) FROM l LEFT JOIN r ON l.k = r.k AND r.v > 250;   -- 正确：3 行
-- 若把 `r.v > 250` 提成 WHERE：只剩 1 行 —— 未匹配的左行被**整体丢掉**了，
-- 而 LEFT 的语义要求它们**补 NULL 保留**（k=1 无匹配、k=2 被残留否掉，各留一行）
```
⇒ 残留必须在 **join 内部**、对"匹配对"求值；判否**只丢弃那个对**，
不影响左行的"是否算未匹配"。

**对 INNER**：残留提到 join 之上的 `Filter` 是**等价**的（INNER 没有补 NULL 那一半），
这是允许的优化——**但两条路的语义要在代码注释里写清楚**，别让后人以为可以照搬。

**落点**：
- `LogicalPlan::Join` 增 `residual: Option<PhysExpr>`（对**合并 schema** 求值）；
- `HashJoinExec` 的 probe 循环里、`take` 之后判残留；判否则该对不发射；
- LEFT 的"是否匹配过"标记**只在残留通过时**才置位。

### P1-1 `RIGHT [OUTER] JOIN`

**做法**：换边 —— 规划成 `left=r, right=l, join_type=LeftOuter`，再在**上面加一层
Project 把列序换回 `l.* ++ r.*`**（用户写的顺序）。

⚠️ **陷阱（老熟人：索引空间）**：`LogicalPlan::Join` 的输出恒为
`probe(左) ++ build(右)`；换边后它是 `r.* ++ l.*`，与用户看到的列序不同。
这一层投影**必须同时**：
① 把列序换回来；② 保住**限定名**（`l.k` / `r.k` 都还在，否则外层 `r.k` 绑到错的列）。
列裁剪那次的教训同源：**位置属于哪个空间**是这个优化最容易错的地方。

`RIGHT` 与 `LEFT` 的区别只有"哪侧保留未匹配行"，故**非等值 RIGHT 同样不支持**
（与 LEFT 对齐），报错文案要指路（换成 LEFT 写法）。

### P1-2 `FULL [OUTER] JOIN`

**做法**：`HashJoinExec` 加 `JoinType::FullOuter`：
① 建索引时给 build 侧行打"已匹配"位图；
② probe 阶段发射匹配对（残留通过时置位）；
③ probe 结束后，把**未置位的 build 行**左侧补 NULL 发射一轮。

⚠️ **陷阱：与并行分片的关系**。`try_shard_source` 按**行**切分片；FULL 的两侧
"未匹配"必须在**同一片内**判定（同一行的左右两侧要落进同一片）。当前 `ShardScope`
是"表名→分片"，两侧各取一次即可；但既有闸门 `JOIN_SHARD_MAX_BUILD_ROWS = 2M`
（每片各建一次索引 ⇒ 内存 ×N）对 FULL 同样适用，**且 FULL 的收尾轮要多持一份
build 侧匹配位图**。落码时先确认：**分片路径 + 非分片路径结果逐行一致**。

### P1-3 `CROSS JOIN`

`JoinOperator::CrossJoin` 的约束是 `JoinConstraint::None`（不是 `On`），
当前在"必须有 ON"那一步就被拒。做法：识别 `CrossJoin` → 直接造
`CrossJoinFilter { predicate: TRUE }`。**顺带**：`CROSS JOIN … ON <cond>` 是
非标准写法，按非等值 INNER 处理即可（或明确拒绝，二者都要有测试钉）。

### P2-1 `USING (cols)`

改成 `ON l.c = r.c AND …` + **输出列合并**（`USING` 的 `SELECT *` 只出一列 `c`）。

⚠️ **合并列的取值语义**（按 SQL 标准，别猜）：
- INNER → 两侧相等，取谁都行；
- LEFT → 取**左**（未匹配时左行有值、右为 NULL）；
- RIGHT → 取**右**；
- FULL → `COALESCE(l.c, r.c)`。

**NATURAL JOIN 明确不做**：它按"同名同类型列"隐式匹配，两侧加一列就可能**静默
改变连接语义**——与本仓"拼错就报错"的纪律相反。文档里写"不做"，并说明理由。

### P2-2 非等值 `LEFT/RIGHT`

`CrossJoinFilter` + 未匹配左行补 NULL（LEFT）。代价天然是 O(n×m)，**必须在文档
与错误文案里点明**，别让人以为和等值 join 一样快。优先级最低。

## 四、验收（每条都要能分辨**对与错**）

1. **探针转断言**：`join_common_probe.rs` 的 10 条变成 `assert`（值 + **计划形状**）。
   计划形状断言是 P0 的关键：退化叉积**值也是对的**，只断言值等于没测。
2. **必须配"错实现会红"的对照**（每条至少一个）：
   - P0-2/LEFT：把残留误推成 `WHERE` → 会得 **1 行而非 3 行** ⇒ 用例能分辨；
   - P0-1：复合键只用第一个键 → 会得 **2 行而非 1 行** ⇒ 能分辨；
   - P1-1/RIGHT：漏掉列序重排 → `SELECT l.k, r.k` 取到**对调的列** ⇒ 能分辨；
   - P1-2/FULL：漏掉收尾轮 → 少 **1 行**（未匹配的 build 行）⇒ 能分辨。
3. **分片路径**：FULL/RIGHT 在**并行分片**与**串行**下结果逐行一致
   （照 `join_agg_parallel.rs` 的做法：同数据跑两遍对比）。
4. **闸门**：`sh tools/check.sh` ALL GREEN；`.14` bench 不受影响
   （基准全是等值 join；P0-1/P0-2 会**让它更快**，不会更慢）。
