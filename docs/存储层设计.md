# QSDB 存储层设计（v1 草案）

> 版本：v0.1（2026-10-11，M6 设计输入）
> 状态：**草案**——定案项标 ✅，待定案项标 ⏳，评审后冻结
> 上位文档：`QSDB设计开发文档.md`（总体架构）、`format-spec.md`（表格式冻结规范，
> 本文档不改变任何 on-disk/on-object 格式，只定义格式之上的访问协议）

---

## 一、目标与非目标

### 目标

1. **多后端**：存储层支持 本地文件系统（默认）/ S3 及兼容（MinIO/OSS/COS/R2…）/ HDFS，
   以及任何能映射到对象原语的后端（Blob/Azure Blob 等）。
2. **本地零回退**：本地后端保持现状性能（读写红线不变）——抽象层不得在本地热路径
   引入虚调用、额外拷贝或协议开销。
3. **远端可管理表**：远端后端不只是「读外部数据」，而是完整承载 QSDB 表格式
   （建表/写入/提交/compaction/GC 全生命周期）。
4. **崩溃一致性**：任何后端上，kill -9 / 网络中断 / 并发写者冲突后，无脏数据可见、
   无需人工修复（孤儿数据由 GC 回收）。

### 非目标

- **跨后端联邦/搬移**：一张表的数据文件不跨后端分布（缓存副本除外）；
  表级搬迁是生态工具（qsdb-sync 类）的职责。
- **远端低延迟点查**：对象存储单次 GET 延迟 10-50ms，点查红线只在本地/缓存命中
  口径上承诺。
- **分布式事务**：跨分区无事务（与 v1 一致）；远端多写者一致性靠租约 + 乐观并发，
  不引入协调服务（ZooKeeper/etcd）。
- **改表格式**：`format-spec.md` 冻结的目录布局、manifest 结构、编码全部不变；
  远端只是把「文件」变「对象」。

## 二、设计原则

| # | 原则 | 含义 |
|---|------|------|
| P1 | **本地是最快路径** | 抽象按「能力协商」分层而非「接口统一榨平」；本地走静态分发分支，红线不回退 |
| P2 | **不可变优先** | segment 文件天然不可变（UUID 命名、单次写入）——不可变对象的写入不需要原子性协议，普通 PUT + 幂等重试即可 |
| P3 | **真值单一** | 每个分区唯一的 manifest 对象是真值（与 v1 相同）；「不被 manifest 引用 = 不存在」——这让删除、崩溃恢复、并发冲突的推理全部简化为对单一对象的推理 |
| P4 | **能力协商，不猜** | 后端能力（原子 rename / 条件写 / 锁）显式声明并启动期探测校验，协议按能力集选择实现；能力不足直接报错而非静默降级 |
| P5 | **读远端 = 裁剪后拉取** | 远端读必须先 range-GET footer 做分区/统计/row-group 裁剪，只传输选中的 row group 字节区间——「先裁剪后传输」是远端吞吐的第一杠杆 |

## 三、现状盘点（v1 本地实现的文件调用面）

存储相关操作收口在以下模块（抽象时的改造面）：

| 模块 | 文件操作 | 依赖的本地语义 |
|------|---------|---------------|
| `catalog.rs` | `_catalog/{db}.postcard` 读写、`table.json` 读写、目录枚举 | 原子替换（tmp+rename）、catalog 锁 |
| `fsutil.rs` | `write_atomic`（tmp+rename）、`PartitionLock`（flock）、`move_to_trash`、`tmp_sibling` | **rename 原子性、文件锁** |
| `manifest.rs` | `manifest.postcard` 读 + 原子替换 | **rename 原子性** |
| `write.rs` | segment 写（tmp+rename）、分区目录 mkdir、manifest 追加提交、`_trash` | **rename 原子性、分区锁** |
| `scan.rs` | parquet File::open/read、footer 读、分区目录枚举（发现） | 随机读、readdir |
| `compact.rs` | 同 write（锁内合并） | 锁 + rename |
| `index.rs` | 表级分区索引（内存态、可重建） | — |

**核心结论（此前分析已确认）**：数据文件路径（不可变对象）可无痛迁移；
**manifest 的读-改-写**与**分区互斥锁**是仅有的两处强依赖本地语义的协议点，
本设计的主体就是这两点的远端化。

## 四、总体架构

```
┌────────────────────────────────────────────────────────────┐
│  表格式协议层（backend 无关）                                │
│  提交协议 CommitLocal / CommitOCC / CommitHdfs（能力选择）   │
│  租约与围栏 · 分区发现（索引优先）· GC 引用扫描               │
├────────────────────────────────────────────────────────────┤
│  存储抽象层 StorageBackend                                  │
│  enum Store { Local(LocalStore), Remote(ObjectStore) }      │
│  原语：get / get_range / put / put_if_absent /              │
│        put_if_etag / delete / head / list(prefix)          │
│  能力集：Capabilities（启动期探测校验）                       │
├────────────────────────────────────────────────────────────┤
│  后端实现                                                   │
│  LocalStore（std::fs，静态分发零开销）                        │
│  S3Store（object_store::AmazonS3，含 MinIO/OSS/R2 兼容）     │
│  HdfsStore（社区 object_store 兼容实现，⏳选型见 §13）        │
├────────────────────────────────────────────────────────────┤
│  数据缓存层（远端后端启用）                                   │
│  本地段文件缓存（磁盘 LRU，path+ETag 校验）                   │
│  内存批缓存（现有 SegmentCache，预算/8 收集上界）             │
└────────────────────────────────────────────────────────────┘
```

**派发设计（P1 落地）**：`Store` 是 enum 而非 `dyn Trait`——本地分支
`match` 静态派发 + 单态化，与 v1 代码路径等价；远端分支统一走 object_store。
热路径（scan 读列）不经过本层抽象的逐字节包装：本地直接 `File` 读（现状），
远端走 range GET + 段缓存路径。

## 五、对象模型与 Key 布局

远端 key 与本地路径一一映射（`/` → key 分隔符）：

```
s3://bucket/qsdb-prod/                 ← root prefix（配置）
├── _catalog/default.postcard           ← db 表名清单（单对象，OCC 更新）
├── default/t/table.json               ← 表定义
├── default/t/dt=2026-10-09/
│   ├── manifest.postcard               ← ★ 分区真值（OCC 更新）
│   ├── seg_0192f3a1-….parquet          ← 不可变对象
│   └── seg_0192f3bc-….parquet
├── default/t/_index/partitions.postcard  ← 分区发现索引（新增，见 §9）
└── default/t/_trash/…                  ← 远端不使用（见 §12 GC）
```

规则（继承 format-spec §6）：

- 「目录」仅是 key 前缀；分区名 percent-encoding 规则不变。
- `_` 前缀的 key（`_catalog`/`_index`/`_trash`）不参与分区发现。
- manifest / segment / table.json 的字节格式与本地**完全一致**（postcard/parquet/json）。

## 六、存储后端抽象

### 6.1 原语

```rust
pub enum Store {
    Local(LocalStore),                    // 静态分支
    Remote(std::sync::Arc<object_store::ObjectStore>), // object_store 统一实现
}

pub struct BackendCaps {
    pub atomic_rename: bool,        // rename 到已存在目标 = 原子替换或失败（不允许部分可见）
    pub put_if_absent: bool,        // 条件创建（不存在才写）
    pub put_if_etag: bool,          // 乐观并发替换（ETag 匹配才写）
    pub range_get: bool,            // 字节区间读
    pub native_lock: bool,          // 文件锁（flock）
}
```

| 原语 | Local (std::fs) | S3/兼容 | HDFS |
|------|-----------------|---------|------|
| get / get_range | ✅（File+seek） | ✅ Range GET | ✅（seek 读） |
| put（覆盖写） | ✅ tmp+rename | ✅ 单对象 PUT 原子 | ✅ create+overwrite |
| put_if_absent | ✅ rename（目标存在即失败） | ✅ If-None-Match:*（2021-12 起原生支持） | ✅ create(overwrite=false) |
| put_if_etag | ✅（stat+rename，窗口内本进程互斥兜底） | ✅ If-Match（412 冲突） | ⏳ HDFS 无 ETag——用 `.etag` 辅助对象模拟或走 rename 协议 |
| delete | ✅ | ✅ | ✅ |
| list(prefix) | ✅ readdir | ✅ ListObjectsV2（分页、慢） | ✅ listStatus |
| native_lock | ✅ flock | ❌ | ❌（⏳ HDFS 咨询锁可模拟，不做） |

### 6.2 能力探测（P4 落地）

启动时对配置后端做一次探测（写探测对象 → 条件写 → rename（若声明）→ 清理），
声明能力与实测不符直接启动失败并报错（如 MinIO 旧版不支持 If-Match 时，
`CommitOCC` 不可用需显式配置降级路径，见 §7.4）。

### 6.3 选型

- **object_store crate**（Apache Arrow 生态，与 arrow/parquet 同步维护）：S3/GCS/Azure/
  本地/HTTP 均有实现，条件写原语齐全。✅ 定案采用。
- **HDFS**：✅ 定案（M6-5，2026-10-11）：**hdfs-native**（纯 Rust RPC）+
  hdfs-native-object-store 0.17（object_store 0.14 同版对齐）；CAS 由
  LockingStore 锁对象模拟；Hadoop 3.1.3 真实集群 e2e 验证。

## 七、提交协议（核心）

所有协议共享同一语义骨架：**segment 全部落盘 → manifest 单对象原子切换 → 提交点**。
差异只在「manifest 原子切换」与「互斥」的实现。

### 7.1 ProtocolLocal（本地，现状保持）✅

分区 flock → 写 segment（tmp+rename）→ manifest tmp+rename 原子替换 → 释放锁。
零改动。

### 7.2 ProtocolOCC（S3 及兼容对象存储）✅ 定案

**segment 写入**（不可变，无协议）：
```
put(seg_key, bytes)          # UUID 名，永不冲突；失败幂等重试
```

**manifest 提交**（唯一 CAS 点，乐观并发循环）：
```
loop (≤ N=8 次):
    (etag, cur) = get(manifest_key)        # 不存在 → etag = ABSENT
    new = build(cur ∪ {本次 segments})      # 基于**重读的最新 cur**重放本次提交
    ok = put_if_etag(manifest_key, new, etag)   # ABSENT 时用 put_if_absent
    if ok: 提交完成，break
    else: 412/冲突 → 重试（重新拉取 cur 后**重放**，而非报错——
           重放保证提交语义是「至少一次加入」，重试对上层透明）
重试耗尽 → 报错（并发写者过多的显式信号）
```

要点：
- **无锁**：不依赖任何锁对象；并发写者靠 OCC 收敛，最后写者胜出且不丢
  对方的 segment（重放基于最新 cur）。
- ** fencing（多写者安全）**：manifest 内新增 `writer_epoch: u64`
  （postcard 尾部字段，`#[serde(default)]`，本地旧 manifest 兼容）。
  写者持租约时获得 epoch，提交时写入；**后提交者的重放总是基于最新 cur 构建**，
  天然不存在 ABA 丢写——epoch 仅用于 GC 与诊断（识别过期写者留下的孤儿）。
- **崩溃窗口**：segment 上传后、manifest 提交前崩溃 → 孤儿 segment，
  不被引用即不可见 → GC 回收（§12）。manifest 提交是唯一可见点，单对象原子。

### 7.3 ProtocolHdfs（HDFS）⏳

HDFS rename 单对象原子（NameNode 串行化）→ 直接复用 ProtocolLocal 的
tmp+rename 骨架，仅把「flock 互斥」替换为 manifest rename 的原子性兜底
（rename 到已存在目标失败 → 读目标确认是否自己内容 → 重放）。
HDFS 分期在 S3 之后（§16）。

### 7.4 协议选择

| 后端能力 | 协议 |
|---------|------|
| atomic_rename（local/HDFS） | ProtocolLocal / ProtocolHdfs |
| put_if_etag（S3 系） | ProtocolOCC |
| 两者皆无（极老的对象存储） | 不支持：启动报错（不提供静默降级） |

## 八、并发与锁

| 场景 | 本地 | S3 |
|------|------|-----|
| 进程内多线程写同分区 | 分区锁（flock，现状） | `tokio`/std Mutex per partition（进程内串行化后走 OCC，进程内无冲突重试） |
| 多进程写同表（本地） | 分区 flock | — |
| 多进程/多实例写同表（S3） | — | **v1 远端 = OCC 无锁多写者**（§7.2，任何写者可提交，重放保证不丢）；租约单写者模式作为**可选**配置（`writer_lease`，减少重试冲突），v2 再考虑强制租约 |

✅ 定案：远端 v1 不实现租约强互斥——OCC 重放已给出正确性；
租约是「减少冲突」的可选优化，不是正确性依赖。这避免了心跳、脑裂、
fencing 语义证明等一整类复杂度，代价是高并发同分区写时重试次数上升
（每次冲突多一次 GET+PUT，S3 延迟量级，可接受）。

## 九、元数据与分区发现

**问题**：远端分区发现不能靠 list（慢、分页、每分区一次 stat 更慢）。

**设计**：表级分区索引对象 `_index/partitions.postcard`（新增，format-spec §7.2 增补）：

```
PartitionIndex {
    version: u32,
    partitions: Vec<PartitionEntry>,   // (分区值, segment 计数, 行数, 字节数, 更新时间)
}
```

- **写入**：每次 manifest 提交成功后 best-effort 更新（OCC，失败不影响正确性——
  索引只是加速结构）。
- **读取**：分区裁剪路径优先查索引（单对象 GET，热缓存 <10ms）；
  索引缺失/过期（校验：索引 mtime 落后某 manifest）→ 回退 list 前缀 + 重建。
- **重建**：`qsdb admin refresh-index`（现有命令语义不变）。
- 本地后端：索引保持现有内存态实现（不落盘），行为不变。

## 十、读路径（远端）

### 10.1 三级裁剪不变 + 第四级（传输裁剪）

1. 分区裁剪：索引/manifest（§9）
2. segment 统计裁剪：manifest 列 min/max（manifest 已在本地/缓存）
3. **row group 裁剪：range GET 读 parquet footer（文件尾 ~8-64KB）**，
   footer 统计裁剪（现有 `prune_row_groups` 复用）
4. **传输裁剪：只对选中的 row group 发 range GET**（按 footer 里的字节偏移）

### 10.2 段文件缓存（远端专用）

```
{root}/_filecache/{path_hash}/{etag}/{file_name}   ← 本地磁盘 LRU
```

- 键含 ETag：对象被覆盖/重写（理论不应发生，segment 不可变）自动失效。
- 预算 = `file_cache_mb`（默认 1GB，0 = 关闭）；LRU 与内存批缓存同款治理。
- 命中 → 走本地扫描路径（零网络）；未命中 → 边下边缓存（先 footer，再选中 RG）。
- 内存批缓存（SegmentCache）在段缓存之上不变。

### 10.3 并行

- 并行单位 = 对象（分区/文件），与现状一致；单文件内 row group 级并行读
  （S3 高并发小 GET 吞吐优于单流）→ `range_get_concurrency`（默认 8）。

## 十一、写路径（远端）

**嵌入模式**：WriteBuffer 攒批（现状）→ flush 时直接 `put` segment（远端）
→ OCC 提交 manifest。攒批天然把对象存储的 per-PUT 延迟摊薄。

**server 模式增强**：本地 staging 目录暂存（写盘即 ACK，低延迟）
→ 后台上传线程批量 PUT + OCC 提交（`staging_dir` 配置，默认关）。
崩溃恢复：staging 里已写未传的 segment 启动时补传（按 manifest 引用对账）。

compaction：读路径拉全分区（走段缓存）→ 本地合并写新 segment → manifest OCC
提交（新 manifest 不再引用旧 segment → 旧对象待 GC）。与本地语义完全一致。

---

## 十二、GC 与空间回收

**原则**：远端不使用 `_trash` 前缀做移动式回收（对象存储无原子移动）。
改为**引用扫描式 GC**：

1. GC 周期（server 模式）或 `qsdb admin gc`（手动）：
   `list` 表前缀全部 segment 对象 → 逐分区读 manifest（真值）→ 
   未被引用且 `mtime` 超过安全期（默认 1h，覆盖在途上传与 OCC 重试窗口）→ delete。
2. 安全期内的孤儿**绝不删**——这是崩溃窗口与 GC 之间的唯一协议约定。
3. 本地后端：现有 `_trash` 机制不变（移动成本为零）。

## 十四、性能预算与红线（远端口径）

| 指标 | 本地（现状不变） | S3（10Gbps 网络） | HDFS（⏳定） |
|------|----------------|-------------------|--------------|
| 扫描吞吐（解压后） | 现红线 | ≥ 800 MB/s（缓存命中=本地；冷读≥网络 80%） | ≥ 500 MB/s |
| 分区裁剪（万级分区，索引热） | < 50ms | < 10ms（索引单对象） | < 20ms |
| 点查（等值分区+主键列） | 元数据短路 <1ms | 缓存命中 <5ms；冷 <100ms（显式不承诺低延迟） | <50ms |
| 批量写 | ≥ 1M rows/s | ≥ 300K rows/s（per-PUT 摊薄后） | ≥ 500K rows/s |
| manifest 提交延迟 | <1ms | <50ms（1-2 次 GET+PUT） | <20ms |
| 二进制增量 | — | object_store 依赖进 cli feature `s3`（**默认关**，红线不受影响） | 同左 |

**本地零回退验收**：接入抽象层后，本地后端跑全套现有 bench（duckdb_vs /
mem_vs / write）数字不劣化超过噪声（±5%）。

## 十五、崩溃一致性与故障矩阵

| 故障点 | 本地 | S3 | 恢复 |
|--------|------|-----|------|
| segment 写一半崩溃 | tmp 残留，不可见 | 分片上传未 complete，对象不存在 | 均不可见；本地 tmp 清理 / S3 自动回收分片 |
| manifest 提交瞬间崩溃 | rename 原子：旧或新 | PUT 原子：旧或新 | 无中间态 |
| 上传成功但 manifest 未提交 | — | 孤儿对象 | GC 安全期后删除 |
| 并发写同分区 | flock 串行 | OCC 冲突→重放重试 | 不丢任何一方的 segment |
| 读到正在覆盖的对象 | 不发生（rename） | 不发生（segment 不可变；manifest PUT 原子） | — |
| 段缓存损坏/过期 | — | ETag 校验失败 → 重新拉取 | 自动 |
| GC 误删风险 | trash 兜底 | 安全期 + manifest 引用双校验 | `refresh-index` 可全量重建清单 |
