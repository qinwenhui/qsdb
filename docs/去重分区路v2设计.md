# `count(DISTINCT)` 分区路 v2 —— 零拷贝条目 + 排序去重（设计稿，2026-10-17，第十三批）

> **缘起**：`simple_distinct`（`count(DISTINCT gs)`，500 万行 / 250 万组，VARCHAR）
> 对 DuckDB **3.2×**（648ms vs ~203ms）。这是当前全部基准格里**最大的单格缺口**。
>
> **本批前先纠正一个旧说法**：性能冲刺记忆里写的"方向：按键哈希分区去重"
> **早就落地了**（P1⑪ `PartitionedDistinctCountExec`，648ms 就是它的成绩）。
> 剩下的差距不是"没分区"，是**分区路每行的固定开销**。本批打的就是这个。
>
> **给接手的人**：§一 症状与拆账（**本批最值钱的新事实**）、§二 设计、
> §三 正确性钉子、§四 验收、§五 已否决/不做清单。前情见
> `去重计数性能设计.md`（§八 已否决清单**先读**：开放寻址槽 / 行分片并集 /

## 一、症状与拆账（2026-10-17，基准机实测）

`QSDB_DISTINCT_PROF` 加了相拆账计时（本批顺手落的，env 后面、零侵入），
`bench_suite --case simple_distinct --rounds 3`，三轮几乎不动：

| 相 | 墙钟 | 形态 | 干的活 |
|---|---:|---|---|
| 相 1 路由 | **~228ms** | **纯顺序**（单线程吃输入） | 每行：`encode_key_row` 编进 buf（**拷 1**）→ fxhash → 拷进分区 arena（**拷 2**） |
| 相 2 建组 | **~420ms** | 16 线程并行 | 每行：`insert_raw_key` **再哈希一遍** → 探哈希表 → 比键 → `push_group` **又拷进组表 arena（拷 3**） |
| 合计 | ~648ms | | 与基准读数吻合 ✓ |

**两条读出来的事实**：

1. **相 2 是随机访问墙**：420ms × 16 线程 ≈ 6.7 CPU 秒 / 500 万行 ≈
   **1.3µs/行**——250 万组插哈希表，每次插入 5-13 次 cache miss，
   16 线程也藏不满这个延迟（`distinct_parts()` 注释"去重是内存延迟受限的"
   说的就是它）。符号层归因见 `真机基准对账.md`：**分布很平、无单点**——
   钱摊在"三拷两哈"上，没有一刀能切掉一半，**得整段换干法**。
2. **相 1 顺序吃掉 35% 墙钟**：228ms 里含扫描解码（`count(gs)` 地板
   ~35-57ms）+ 编码/哈希/拷贝。它不并行化，相 2 再快墙钟也有 228ms 托底。

**⇒ 设计由拆账直接定死**：相 2 换**排序去重**（随机→顺序），
相 1 换**零拷贝条目**（不搬键字节）+ **扫描分片并行**。

**投影**：相 1 分片 ~15-30ms + 相 2 排序去重 ~30-50ms ≈ **50-80ms**，
对比 DuckDB ~203ms —— 有机会**反超**。估算按 2× 误差兜底也应 ≤160ms。

## 二、设计

### 2.1 适用面（gate，宁可少改）

只动**融合计数**这条路（`distinct_fuse_applies`：无分组 + 单 `count(*)` +
`Distinct` 输入），且**单键列且类型 Utf8**。三处闸门按序：

```
distinct_fuse_applies && !QSDB_NO_DISTINCT_FUSE
  ├─ 单定长键（Int8/16/32/64/Date32）→ DistinctCountExec（现状不动，int_slots 快路）
  ├─ 单 Utf8 键 && !QSDB_NO_DISTINCT_V2 → ★ v2（本批新增）
  │     ├─ 输入可分片（剥 Project*/Filter* 到 Scan）→ 相 1 分片并行
  │     └─ 否 → 相 1 顺序（仍是 v2 零拷贝+排序）
  └─ 其余（多键/混合键）→ v1 PartitionedDistinctCountExec（现状不动）
```

- `QSDB_NO_DISTINCT_V2=1`：A/B 开关，回 v1 分区路（bench 对照与回归测试用）。
- 有分组（`count(DISTINCT x) GROUP BY g`）走的是**物化** `DistinctExec` +
  普通聚合，**不在本批范围**。
- 运行期键列实到不是 Utf8（比如字典编码）→ 逐批 `arrow::compute::cast`
  一次（罕见路，不设静默回退）。

### 2.2 相 1：零拷贝条目（不再搬键字节）

```rust
struct Entry { h: u64, br: u64 }        // br = (batch_idx << 32) | row，16 字节定长
// 每分片：parts: Vec<Vec<Entry>>（nparts 个）；key_cols: Vec<StringArray>（Arc 引用保活）
```

每行：取 `value(i)` 字节切片（**零拷贝**）→ `h = fxhash(tag ++ bytes)`
（两段流式哈希：tag `0`=NULL 无字节、`1`=非空有字节，**不物化编码 buf**）→
`p = Lemire(h, nparts)`（`(h as u128 * n as u128) >> 64`，免除法）→
`parts[p].push(Entry)`。批循环里把键列 `StringArray`（Arc 克隆）存进
`key_cols` —— 条目引用的行字节全在箭头缓冲里，**一份键字节都不复制**。

- **内存**：条目 16B × 行数（500 万 = 80MB）+ 键列缓冲（~55MB，今天
  本来就要读的）≈ **135MB**，比现行 216MB 分区缓冲**还小**（相 2 组表
  arena+by_hash 的 ~155MB 峰值直接消失）。预检沿用 `行数 × 32B`
  （保守方向不变），相 1 逐批按实记账（条目容量 + 键列字节数）。
- **分片并行**：照搬 join 分片路的既定套路——`try_shard_source` 剥到
  `Scan` 拿 `scan.shard(threads, false)` 的行不相交分片；每片
  `ShardScope::set(table, shard)` + `build_inner(完整输入子树)`
  （Project/Filter 逐行保序 ⇒ 对行不相交分片可分配送）`into_par_iter`
  各片独立路由。`try_shard_source` 返回 `None`（有 join/集合/窗口等）
  → 单节点顺序相 1，**行为与今天等价，不引入新失败模式**。
- 分片条目在主线程**拼接 + 批号全局重编号**（`br += base << 32`，
  一次 16B/条线性扫）后交给相 2。

### 2.3 相 2：排序去重（随机→顺序）

```rust
parts.into_par_iter().map(|mut es| {
    es.sort_unstable_by_key(|e| e.h);          // 312k × 16B ≈ 5MB/分区，L3 内
    let mut kept: Vec<u64> = Vec::new();       // 同哈希 run 里的"留样"行引用
    let mut count = 0u64;
    // 线性扫：同哈希必相邻；run 内逐个与留样比**真字节**
    ...
})
```

排序后线性扫：同哈希相邻成 run；run 首 entry 记 `count += 1`；
后续成员与 run 内**已留样的代表**比字节（`bytes_eq`：都 NULL ⇒ 相等；
一方 NULL ⇒ 不等；否则 `value(row)` 切片 memcmp）——等 ⇒ 丢弃；
不等（**哈希碰撞**）⇒ 留样 +1。分区之间键集不相交（路由哈希同一函数）
⇒ `count` **直接相加**。

- 为什么排序赢哈希表：312k 条目的 5MB 排序全程 L3（pdqsort ~15-30ms）；
  线性扫顺序读条目，唯一随机访问是**留样比字节**的首次触碰
  （~156k 次/分区，不可避免的地板）。对比哈希表插入的 5-13 次
  **结构性随机 miss**/行。
- `kept` 常态长度 1；真碰撞（同哈希不同值）才有第 2 个。病态全碰撞
  数据是 O(k²)，但那需要 2^64 级构造，与 v1 的桶行为同级，可接受。

### 2.4 顺手收的账

- 相 2 不再建 250 万组的组表（arena + by_hash）——**峰值内存省 ~155MB**；
- `QSDB_DISTINCT_PROF` 补打 v2 行（分片数/条目数/缓冲 MB/相耗时），可断言。

## 三、正确性（钉死四条）

1. **哈希碰撞必须比真字节**：排序去重只在同哈希 run 内丢行，且逐个与
   **全部留样**比字节 ⇒ 不同值永不被吞（静默少数/多数是这类优化的
   失败模式，只看"跑得通"看不出来）。
2. **NULL 是一个独立值**：tag 区分；NULL 与 NULL 相等（去重合一）、
   与任何非空不等。融合计数路 NULL 已在上游滤掉，但**物化对照路**
   （`count(*) FROM (SELECT DISTINCT gs)`）NULL 会真到这——两者
   必须同值（NULL 计 1）。
3. **空串是合法键**：`''` 非空 tag、零长字节，参与去重且 ≠ NULL。
4. **路由一致性（v2 内部自洽即可）**：同一逻辑键的哈希只算一次、存进
   条目、路由与排序用**同一个存下的 h** —— 不存在"两处哈希口径"问题
   （对比 v1 的 route/insert 两套）。v1/v2 是两条互不混用的完整路。

## 四、验收

1. **双路对撞**（本地单测，照搬 `去重计数性能设计.md` §7 的纪律）：
   同一查询在 `QSDB_NO_DISTINCT_V2`（v1）/ 缺省（v2）/
   `QSDB_NO_DISTINCT_FUSE`（物化基线）三个开关下**逐值相等**。
   用例表必须覆盖：重复键、NULL、空串、多字节 UTF-8、全部同值、
   1 万随机串（碰撞路径日常 exercising）、0 行、1 行。
2. **闸门**：`cargo test -p qsdb -p qsdb-cli` EXIT=0；
   既有 `tests/distinct_count_fused.rs` 等不得红。
3. **基准**（基准机，5M 行，3 轮中位，DuckDB 同轮）：
   - `simple_distinct`：648ms → **≤160ms**（目标 ~80ms）；
   - `simple_distinct_int` **不得动**（定长键闸门在前，本批碰不到它）；
   - 全量 19 例 0 FAIL（防误伤）。
4. **真实语料零回归**：154 块行数逐块一致（server 模式跑数）。
5. **诊断可断言**：`QSDB_DISTINCT_PROF` 打印 v2 选中与分片数。

## 五、不做 / 已否决（别重走）

| 项 | 处置 |
|---|---|
| W1b 变长键基数自适应（真表 `unit_id` 1.5×） | **不在本批**——机制是"单线程起跑、组数越限切换"，与 v2 独立；v2 落地后它的"切换目标"可以换成 v2，另批做 |
| 定长键进 v2 | **不做**：int_slots 快路单线程已 6ns/行，分区一律亏 ~2×（两批实测），闸门保持在前 |
| 行分片 + 键并集 | **已否决**（1.19× 倒退）：分片切行 ⇒ 并集串行重灌。v2 相 1 的分片**只用于路由**，键仍按哈希全域分区，两回事 |
| 只存 64 位哈希不比字节 | **已否决**（静默错值纪律）：v2 排序去重**必须**在同哈希 run 内比真字节 |
| 相 2 排序换"哈希表 + 直通 hasher" | 备选未取：仍是随机探表，治不了 miss 墙；排序把随机变顺序，是结构性差异 |

## 六、风险

- **排序常数**：pdqsort 对 16B 元素、312k 条目按估算 15-30ms；若实测
  排序本身吃掉相 2 大头，退路是**分片内先排再归并**或 radix 排 u64——
  先量再定，不预先做。
- **分片重建子树的成本**：每片 `build_inner` 一次（join 分片路同款），
  表级元数据开销，毫秒级；分片数由 `shard_count()` 定，沿用现行封顶。
- **内存预检偏紧**：135MB 实际 vs 32B/行×行数=160MB 预检 ⇒ 预检仍是
  保守方向（预检 ≥ 实际），要不到额度的查询照旧走单线程路，无新失败模式。
