## 三之二、★ F25（qsdb-sync 反馈）—— ✅ **已闭环**（2026-10-13，`000c0e7`）

**现象**（对方复测 F24 时发现）：脑裂后两边**独立演进到同一个 generation** →
replica 判据 `src == dst` 误判 up_to_date，而内容不同 → **静默分歧**。
**根因**：`generation` 是**计数器**不是内容指纹，防脑裂只是**单向**保证
（`dst > src` 拒绝），`dst == src` 不蕴含内容一致。

**定案（采纳对方建议 ①）+ 落地**：新增 `PartitionManifest.epoch`（**写者身份代**）——
与既有的 `writer_epoch`（随机、只作诊断、**不参与正确性**）**刻意分开**：后者已发布
语义就是"不参与正确性"，复用等于改已发布语义；且它是随机的，复用会让旧 manifest 的
随机值被当成"某一代写者"。

- `QsdbOptions::writer_epoch`（默认 0）+ `--writer-epoch`（server/query/shell）；
- **每次提交盖章**——⚠️ 这里原本写"四条路径全覆盖"，**是错的**（漏了两条，
  见 §三之三 F26）；正确口径是「凡产生一次分区提交的路径都既校验又盖章」；
- **内核自己也不许回退写**：盘上 epoch > 本配置 → 新码 **`STALE_WRITER`**
  （409 / `retry=no` / `40001` / gRPC ABORTED），检查点在**锁内、写段之前**，
  被拒的写不动数据；
- 生态判据换成 `(epoch, generation)` 复合序 → 撞值不可能，且**不需要每轮读内容摘要**；
- 建议 ②（`manifest_digest` 内容摘要）**不进常规判据**，留给对账/巡检，对方要做再加。

默认全 0 时两项都是 no-op（旧 manifest 缺字段即 0），**现存部署行为不变**。
回归 `tests/writer_epoch.rs`（3 例）+ 码表文档逐字对账；已回写 qsdb-sync（`e0d1baa`）。

## 三之三、★ F26（qsdb-sync 复测）—— ✅ **已闭环**（2026-10-13，`accc70b`）

**对方现象**（F25 落地后复测）：文档说"四条路径全覆盖"，探针显示 **overwrite 那条
把 epoch 擦回 0**，于是 `stale append(epoch=0)` 畅通 —— 防线被一次覆盖抹掉。

**根因确认**（内核侧）：`occ_replace_entries`（远端 overwrite + **staged overwrite**
共用）签名里没有 `epoch`，闭包内 `PartitionManifest::new()` 建新 manifest（epoch 初值
0）只设 `generation`。**盖章缺失比漏校验更重**：它不是"没拦住"，而是把盘上身份代
**降级成既成事实**，此后老进程全线畅通。

**顺带自查出同族另外三条**（对方只点了两条远端路径 —— 我按"所有提交点"重扫了一遍）：

| # | 洞 | 性质 |
|---|---|---|
| 1 | `occ_replace_entries`（远端 overwrite + **staged overwrite**）不校验不盖章 | 反馈 F26 主条 |
| 2 | `clear_partition_remote`（远端 TRUNCATE/清分区）不校验 | 反馈附条 |
| 3 | **本地 compact** 只盖章不校验 → 同样能降级（`compact.rs` 内联 OCC） | 自查 |
| 4 | **本地清空分区**、**无分区表 TRUNCATE**（`clear_unpartitioned`）不校验 | 自查 |

**修法**：`occ_replace_entries` 加 `epoch` 参数（与 `occ_append_entry` 同形），闭包内
**先 `check_writer_epoch` 再盖章**（顺序不能反）；本地 compact / 两处清空补校验；
`clear_unpartitioned` 顺带重写（见下）。

**回归**：`tests/remote_managed.rs` 新增 2 例（非 staging / staging 两条远端路径，
各自覆盖"盖章 + 过期写者被拒 + 被拒不动数据"）；`tests/unpartitioned.rs` 新增 3 例。
**做法照惯例先反向验证**：关掉盖章后两例精确红在 `left: 0, right: 1`（正是 F26 现象）。

> **qsdb-sync 已复测确认 ✅**：按原探针形状落地回归
> `remote_overwrite_stamps_and_enforces_writer_epoch`（远端覆盖后 `manifest.epoch == 1`
> 且 generation 推进；epoch=0 句柄 append 被拒且数据不变），F25 撞值回归**从 append
> 路径扩到 overwrite 路径**，replica 远端 e2e **8/8 绿**。F26 全闭环。

### 三之三附、同一轮自查出的**两条更重的**无分区表 bug（已修）

排查 F26 时按"真值来源是否唯一"重扫，发现无分区表被当"退化特例"处理，三处代码各自错开：

| # | 现象 | 级别 |
|---|---|---|
| **B2** | `TRUNCATE TABLE`（无分区表）直接搬 parquet 而**不动 manifest** ⇒ manifest 继续引用已搬走的段，`SELECT` 从此**永久报 open failed**（表搞坏，之后 INSERT 只是往坏 manifest 上再挂一段） | **高**（表不可读）|
| **B3** | `count(*)`（无分区表）按**列目录**求和，`SELECT` 按 **manifest** ⇒ 两个真值来源。写路径"延迟回收"留在原地的旧段被算进去：`INSERT OVERWRITE` 后 `SELECT *`=1 行而 `count(*)`=**3** 行 | **高**（静默错值）|

**共同根因**：`write::pdir()` 对空分区键返回 `table_dir` —— 无分区表**有 manifest，
就在表目录下**，与分区表同一套提交协议；而 `clear_unpartitioned` 的注释断言
"无分区表没有 manifest"（错的），`scan_metadata_count` 则绕开 manifest 列目录。

**修法**：`clear_unpartitioned` 重写为「提交空 manifest（继承 generation + 身份校验/
盖章）+ 旧段留给 GC」，与分区路径完全同构；`scan_metadata_count` 无分区分支改读
manifest（**manifest 是唯一真值**）。顺带：远端无分区表的 TRUNCATE 从"暂不支持"
改为走 OCC 空替换（append 能写就该能清）。

**影响面**：B3 影响**每一张做过 overwrite 的无分区表**的 `count(*)`；B2 影响无分区表
的任何一次 TRUNCATE。两者都在 `tests/unpartitioned.rs` 钉住。

## 三之四、★ 聚合契约两条 + 零数据列表定案 + 聚合 `DISTINCT` 显式拒绝（2026-10-13，`12130cb`）

起因：追问"零数据列的分区表该修还是该拒"时先做**跨产品调研**，途中在自己引擎上
连撞三个 bug；三个都属"合法 SQL、悄悄给错结果"这一类。

### (b) 零数据列的分区表 → **DDL 层显式拒绝**（已定案）

`catalog.rs::validate` 原只数**总列数**（`columns.is_empty()`），而分区列的值存在
**目录名**里、不进数据文件——于是"只有分区列"的表能建出来，数据文件是**零列**的。
实测三重后果：① 参考实现根本读不了它（DuckDB：`Need at least one non-root column
in the file`，拿我们自己的段文件亲验）；② 我们自己也读不回行数，**除 `count(*)`
外每个查询都静默回空**；③ 主流一律在 DDL 层拒。故补齐 guard：**分区表至少要有一个
非分区列**。

**跨产品依据（调研结论）**：拒是主流——DuckDB（解析层）、Hive（
`at least one column must be specified`，文档化 workaround 是加 dummy 列）、
**Spark（SPARK-38216 专门为"所有列都是分区列"加早失败）**、Delta（`TABLE_NO_COLUMNS`）、
ClickHouse/MySQL/Oracle/SQLite/Trino/Vertica。**PostgreSQL 是唯一例外**，理由是不能让
`ALTER TABLE DROP COLUMN` 卡在最后一列——**本仓没有 `DROP COLUMN`，不适用**。
技术机制上 zero-column 批完全可表达（Arrow 格式 `RecordBatch.length`、arrow-rs
`RecordBatchOptions::row_count`、DuckDB 自己的 `DataChunk.count`），故 (a) 也做得到
（我原文档里写"arrow 表达不了"是**错的**，已更正）——**选 (b) 是因为内部一致性
（无分区零列我们本来就拒）+ 主流一致 + 零列文件跨工具不可读**，不是因为成本。

### ★ Bug C：空输入的无 `GROUP BY` 聚合此前**零个批**

```
SELECT count(a) FROM t WHERE <不匹配>   -- 应有 1 行 0；实测 0 个批
                                         -- 网线上就是空数组，BI 计数器渲染成空白
SELECT sum(a)/avg(a)/min(a) FROM 空表    -- 应有 1 行 NULL；实测 0 个批
```

根因：`GroupTable::is_empty()`（零组）→ `HashAggExec::next` 直接吐 `None`。而
`ingest` 对零行批 early-return、`try_global_fast` 也只在有行时 `push_group`，
于是空输入时**一组都没有**。**藏了这么久是因为 `count(*)` 走元数据短路**——
那条路径恰好是对的（而且 `ALL`/`NOT IN` 这类空输入场景恰好多走短路）。

修法：`GroupTable::seed_global_group`（按**计划里的参数类型**建状态列再建唯一空组）
+ `finalize_agg`/`finalize_or_none`/`finalize_global_empty` 三个收尾入口，
**四处收尾点全部收口**。注意**分片路径**：全局聚合只落在一个分片上，**不能各片各补
一行**（会拼出 P 行），故分片内一律返回 `None`，由外层一次性补。

### 零行结果 → 一个空批 + 完整 schema（兑现 `对接契约.md` §二）

`sql/mod.rs` 的 SELECT 收口处：`batches` 空则补一个 `RecordBatch::new_empty(schema)`。
此前零行 = **零个批**，schema 只在 `SqlResult::query.schema` 里，逐批消费的调用方
（含网线各格式）拿不到列名，靠 server 侧特判补（J15 那批）。**可观测变化**：ipc
流的批数从 0 变 1（空批），行数仍为 0（`http_contract` 断言已改到**行数口径**）。

### ★ 聚合参数 `DISTINCT` 此前被**静默丢弃**（回错数字）

`try_bind_agg` 从不读 `duplicate_treatment` ⇒ `count(DISTINCT a)` 当 `count(a)` 执行：
`{1,1,2,3,3,3}` 上回 **6**（应 3）、`sum(DISTINCT a)` 回 **13**（应 6）、
`count(DISTINCT a) WHERE a>1` 回 **4**（应 2）。**现在绑定层显式拒绝**并给出等价改写
（`SELECT count(*) FROM (SELECT DISTINCT …)`，已验证正确，带 `GROUP BY` 的改写也对）。
**原生实现另立**（真值去重、可与其它聚合混用、走溢出）——见 §4.4。

**连带撤回过一个对外数字**：基准的 `simple_distinct` 就是 `count(DISTINCT gs)`，
那个"高基数 `count(distinct)` 快 4×"是拿我们的 `count(gs)` 比对方的
`count(DISTINCT gs)` 得来的，**无效**（已从 §4.1 与本文件撤回）。
bench 侧已改为等价改写 + **补值断言**（此前只比时间与结果行数，聚合恒 1 行
⇒ 值错也全绿）。

**回归**：`tests/agg_contract.rs`（3 例：空输入聚合逐函数、零行批与 schema、
DISTINCT 拒绝与改写）；`subquery::not_in_null_semantics` 从"按现状断言错语义"
翻正（该用例注释里当初就把这条记为**已记录的后置项**）；`cte_window` 里那张
"只有分区列"的夹具表加了数据列。

## 三之五、★ F27 `#[non_exhaustive]`（qsdb-sync 反馈）—— ✅ **已闭环**（2026-10-13，`08df0ce`）

**反馈原话**：J12 给 `SqlResult::Ok` 加两个字段，HTTP 面向后兼容，但 **Rust API 面
不是**——嵌入方穷尽匹配直接 E0027 编译中断（qsdb-sync 两处 + 内核自己的 bench 两处）。
"这是我们作为首个嵌入方的**实测代价**，不是揣测。"

**落地**（规则见 `对接契约.md` §二之二）：按「内核产出、嵌入方只消费」划线。

| 标 | 不标（会挡外部构造 ⇒ 格式工具没法用） |
|---|---|
| `SqlResult`（枚举 + `Query`/`Ok` **变体级**）、`QsdbError`（枚举 + `NotFound`/`WriteConflict` 变体级）、`WriteResult`、`CompactResult`、**`PartitionStat`** | `Literal`、`LogicalType`、`ScanRequest`、`QsdbOptions`、`Predicate`、`SegmentEntry`、`PartitionManifest` … |

**实测的语义细节（本轮用两个小 crate 端到端验的，别"优化"掉）**：

1. **枚举级标注防不住"给变体加字段"**——它只强制外部加通配臂（E0004）；外部若把
   变体字段列全了（无 `..`），加字段照样 **E0027**。**必须同时标在变体上**，变体级
   才强制外部写 `..`（E0638）。**这正是 F27 那个实际中断的唯一解法**。
2. 变体级标注会**禁止外部用结构体字面量构造**该变体（E0639）——所以第二类不能标。
3. **端到端验证**：变体级标注后给变体加字段，**外部一字未改、照样编译通过**。

**`PartitionStat` 尤其该标**：反馈里正提到"check 报告因 `PartitionStat` 未透出
`epoch` 而需读 src manifest 才能判复合序"——即**加字段在即**，标了那次就不打断他们。

**一次性适配**（只此一次，之后内核加变体/加字段都不再打断）：外部匹配加通配臂
（**放最后**，放前面会让上面的臂不可达——本轮 clippy 就抓到我这处）+ 具名变体写
`..`。工作区 12 处已改（`qsdb-cli` 2 处通配臂、`bench_suite` 1 处、tests 9 处 `..`）。

> ### ⚠️ 共享建侧（原定 #30）**被实测否决**
>
> 原计划是"每片各建一次建侧 hash 索引 ⇒ 共享它"。加 `[join-build]` 插桩直接量：
> 每片建侧只有 **19–65ms**（N=1/4/16），共享最多省 **6–14%**——不是模型里的 1.4×。
> 且 `simple_group`（**没有 join**）同样在 N=4 后饱和回退 ⇒ 饱和的根源在
> **分片机制本身**（并行 CPU 膨胀 ×3.3），不在建侧。**已否决，不做。**
> （这条留在这里：**又一次"先量再做"救了一次**——和今晚那把"断言进计时区间"的歪尺子同族。）

**真正的大头（P1⑥）**：`exec/join.rs::join_batch` 对**每一行**都 `take` **全部
probe 列 + 全部 build 列**。基准那句 join 实际产出 **1000 万行**（`d` 每个 g 两行）
× **10 列**（含 4 个字符串列），而聚合**只读 2 列** —— 1.27s 里约 **0.85s（67%）**
花在"物化 10 列然后丢掉 8 列"。成因：列裁剪只在 `plan_scan_def` 有值时才跑，
而它**遇非 semi 的 Join 返回 `None`**（semi 族穿透，非 semi 没有）。

> **对照 DuckDB 同一条：0.12s 墙钟 / 0.36s CPU**（我们单线程 CPU **3.9×**）。
> 所以：**并行只是把浪费的核心捡回来一部分，真正的差距在每行成本。**
> ⚠️ 这块属于**"算错就静默错值"**那一类（少物化一列 = 那列读出垃圾），
> 必须先有"引用列集合"的强断言 + 逐值对照测试。

> ⚠️ **RSS 那一列要先扣掉热段缓存**（约 300MB；`--cache-mb` 可调、可挤兑）：
> 剔除后 join 类是 **215MB** vs 对手 36–42MB（5–6×，不是 25×），
> 而 `simple_group` 反而**比对手省**（155MB vs 414MB）。
> 详见 `docs/真机基准对账.md` §二之二——**别把缓存算成"物化开销"**，
> 那是"用不同口径比"，与 bench 断言进计时区间是同族错误。

### 4.6 ✅ cancel 的**生效延迟**已修（2026-10-15）

**症状**：取消"看着全对"（`POST /queries/{id}/cancel` 回 200、查询也回了
`QUERY_CANCELLED`），但**省下的时间是 0**——比不取消还慢。

**根因**：`CrossJoinExec::next()` 的粒度。非等值 ON 走 `CrossJoinFilter`
= `CrossJoinExec` + `Filter`，而它**一次 `next()` 展开 `n_left × n_right` 行**，
`ctx.check()` 只在入口查一次 ⇒ 5000×5000 全在**一次调用里**跑完（顺带一次性
物化了 25M 行 + 两份 25M×4B 的索引向量）。

**修法**：**分块展开**——`cur: Option<CrossCursor>` 跨调用保留游标，
一次最多吐 `CROSS_CHUNK_ROWS = 64K` 行；块内每 `CROSS_CHECK_EVERY = 16K` 次
再查一次取消。索引按 `(l, r) = (k / n_right, k % n_right)` 递增推进，
**不预先物化整批索引向量**。

**实测**（判据都是**比值**，不是绝对秒数）：

| 口径 | 修复前 | 修复后 |
|---|---|---|
| 内核层（7000 行非等值 join，49M 对） | 基线 5.76s / **取消生效 1.91s** | 基线 4.99s / **取消生效 5.02ms** |
| 端到端走 HTTP（5000 行，含字符串列） | 基线 13.2s / **取消 19.74s** | 基线 13.2s / **取消 26.9ms** |

**纪律**：用例先跑出**红**（1.91s 那版）再修；判据用比值（`latency * 10 < baseline`）
——绝对秒数写死就是造一条会 flaky 的尺子。另：基线那遍断言的是精确值
`n(n-1)/2`，49M 对会被切成 ~750 块 ⇒ **切块边界算错就和不上**，
所以这条用例同时是"多块展开正确性"的回归。

### 记账缺陷家族（四条，同源：**逃生通道的准入门槛**）—— 全部闭环

1. 峰值/双份预留（排序尾块、join build 侧）用 `?` 上抛 → 查询被打死（`6d91004` 修）。
2. `SortExec` 的 `chunk_bytes` 与预留不同步：**已证伪**（插桩 500 批恒等）——不是 bug。
3. `PartSpill` 的分区数/缓冲上界不看全局预算 → 小预算下溢出开不起来（`PartSpill::plan` 修，§二）。
4. join 键索引 `res.grow(rows*16)?` 硬 `?`（隐藏最深的一条：**只在"行装得下、索引装不下"
   的窗口里触发**，前三条的表现都盖在它前面）→ 同样改为转溢出。

**共性结论**：凡"本算子有溢出能力、额度却先要不到"的地方，**一律改降级或转溢出，不许上抛**；
反过来，真正的算子固有需求（join 建索引、窗口排序要整分区）**必须如实报错**，别用降级假装能跑。

### 两条工程教训（都踩过）

- **"用例其实是空的"比 bug 更难发现**：`sql_collect` 走 `benign()` 让两个"全局预算"
  验收用例全程没让预算生效（其中一个还被 `count(*)` 下推改成没有溢出分支的算子）。
  对策：像 `spill_path_is_really_taken` 那样**用可观察量证明被测路径真被走到**。
- **多代理共用一棵工作树 + 默认 `target/` 会互相破坏**：
  ① 谁跑一次 `git checkout/stash` 就能静默抹掉别人的未提交改动（已发生一次）；
  ② 并发 cargo 会让 `cargo run` 拿到**过期二进制**，误判"改动没生效"。
  对策：**每条并行流独立 worktree + 独立 `CARGO_TARGET_DIR`**，并禁止共享树里的
  git 写操作（只读命令随便用）。
