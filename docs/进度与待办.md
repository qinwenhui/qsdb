## 二、待办中的"缺口"（原"在途"已落地，见提交历史）

**缺口③（唯一挡住两条用例的）**：`exec/agg_spill.rs` 的 `PartSpill` 分区数固定 `clamp(2,16)`、
单分区上界 `part_cap_for` 只看 `ctx.memory_limit`（`None` → 4MB）→ 16×4MB=64MB 缓冲需求
撞上小全局预算（128KB 级）→ **逃生通道自己先被预算掐死**，查询报 `MEMORY_PRESSURE` 而不是落盘完成。

- 影响：`tests/agg_spill.rs::global_budget_pressure_also_spills` 与
  `tests/join_spill.rs::join_spills_under_global_budget_too` ——**已标 `#[ignore]` 并注明原因**
  （红灯不留仓里，规格也不丢）。修完删掉 `#[ignore]` 即闭环。
- 修法（已被修复流按数字验证可行）：分区数与单分区上界都从 `min(每查询配额, 全局预算)` 推——
  `eff=256KB → nparts=2, cap=64KB，总缓冲 128KB ≤ 256KB`。
- **实现陷阱（务必注意）**：`PartSpill::new` 内部写死 `default_nparts()`，而
  `part_cap_for(ctx, nparts)` 需要同一个 nparts —— 两处各算必漂。应收成一个
  `PartSpill::plan(ctx) -> (nparts, cap)`，`new()` 显式收参（调用点 3 处：
  `AggSpill::new`、join `enter_spill` 的 build+probe、window `enter_spill`）。

**同类隐患（同族第 4 处，未修）**：`exec/join.rs:410` 的键索引记账 `res.grow(table.num_rows()*16)?`
也是硬 `?` —— 索引是常驻而非瞬时双份，但同样会打死"本可溢出完成"的 join（修法同形：
`vec![table]` 交 `enter_spill`）。

## 三、★ F23（qsdb-sync 反馈，**主条未修**，高优先级）

反馈原文：`D:\qinwh\code\myself\RustWorkspace\qsdb-sync\docs\QSDB对接反馈.md` §F23。

**问题**：两处写路径用**本地文件锁原语**，在远端 Store（S3/HDFS）上直接炸
（`fs::create_dir_all("s3://bucket/_catalog")` → os error 123）。已逐条验证属实：

| # | 位置 | 现状 |
|---|---|---|
| 1 | `users.rs:174` `UserStore::write_all` | `PartitionLock::acquire(store.root()/_catalog/.lock)` —— **无条件调用**（无 `is_local()` 守卫）→ **远端库 `CREATE USER` 整体不可用**（影响面不止 qsdb-sync） |
| 2 | `index.rs:74` `PartitionsIndex::upsert` | `PartitionLock::acquire(table_dir/_index.lock)` —— 内核写路径的调用点在 `is_local()` 分支内（`write.rs:499`），但**函数本身对远端不设防** → 外部调用方（qsdb-sync replica）一调就炸 |
| 3 | `fsutil.rs:122` `PartitionLock` | 只认本地：`create_dir_all` + `OpenOptions` + `lock_exclusive`，**无后端分派** |

**修法方向**（反馈建议 + 贴合本仓风格）：`PartitionLock` **按后端分派**——
Local 走 flock（行为不变）；Remote 走**进程内 mutex**（`remote.rs::with_partition_mutex`
已有此形态，catalog OCC 路径在用）或 LockingStore CAS。
工程细节：现有用法是 `let _guard = PartitionLock::acquire(...)` 的 RAII 形态，而进程内
mutex 的守卫要与 `Arc<Mutex<()>>` 同寿命（自引用问题）→ 两个选择：
① 把两处改成**闭包形态** `with_lock(store, path, || { … })`（`write_all` 一个写语句、
`upsert` 一段读改写，都好包）；② `PartitionLock` 变 enum，Remote 臂持有
`Arc<Mutex<()>>` + 用 `parking_lot`（**新依赖 ✗ 违背红线**）。
→ 倾向 ①。**修完后**：远端用户面写入 + 远端 idx 维护收口，qsdb-sync 的
`--users × 远端 dst` 那个显式报错可以翻转。

**已被 F23 尾条覆盖的部分**（已完成 ✅）：`feature hdfs` 编不过（`f21b8fd`）
+ `feature s3` 编不过（随 `0cfa9e4` 落地）——见上表"已提交"。

### 记账缺陷家族（三条，同源：**逃生通道的准入门槛**）

1. 峰值/双份预留用 `?` 上抛 → 查询被打死（修复流在修）。
2. `SortExec` 的 `chunk_bytes` 与预留不同步：**已证伪**（插桩 500 批恒等）——不是 bug。
3. `PartSpill` 的分区数/缓冲上界不看全局预算 → 小预算下溢出开不起来（修复流在修）。

### 两条工程教训（都踩过）

- **"用例其实是空的"比 bug 更难发现**：`sql_collect` 走 `benign()` 让两个"全局预算"
  验收用例全程没让预算生效（其中一个还被 `count(*)` 下推改成没有溢出分支的算子）。
  对策：像 `spill_path_is_really_taken` 那样**用可观察量证明被测路径真被走到**。
- **多代理共用一棵工作树 + 默认 `target/` 会互相破坏**：
  ① 谁跑一次 `git checkout/stash` 就能静默抹掉别人的未提交改动（已发生一次）；
  ② 并发 cargo 会让 `cargo run` 拿到**过期二进制**，误判"改动没生效"。
  对策：**每条并行流独立 worktree + 独立 `CARGO_TARGET_DIR`**，并禁止共享树里的
  git 写操作（只读命令随便用）。
