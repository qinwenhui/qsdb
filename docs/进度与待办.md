## 二、缺口③ **已闭环**（2026-10-13，随"批次 1 正确性"提交）

- ✅ 收成 `PartSpill::plan(ctx) -> (nparts, cap)`：有效额度 = `min(每查询配额, 全局预算)`，
  `cap = eff/4/nparts` 夹在 `[64KB, 4MB]`；`new()` 显式收 `(nparts, cap)`（3 个调用点统一）。
- ✅ **两条会失败的路径改成降级**：`push_routed` 要不到额度 → 先落已缓冲的行、再试；
  仍要不到 → 该批单独落一个 run（**push 永不因额度失败**）。取回侧新增
  `PartSpill::for_each_partition`（逐 run 流式，峰值 = 一个 run），聚合/去重/exec_builder
  三处收尾改用它；join 建索引与窗口排序要整分区，仍走 `take_partition`（放不下如实报错）。
- ✅ **`nparts` 不再随额度收窄**（早先缩到 2 是错的）：分区数决定**物化消费者**的单分区
  足迹，缩分区数会让小额度下的 join **必然**失败（实测 256KB 预算 + 2 万行 build 侧：
  `nparts=2` → 单分区 330KB 装不下；`nparts=16` → 40KB 装下）。被动缓冲有降级路径兜底。
- ✅ 同族第 4 处一并修：`exec/join.rs` 键索引 `res.grow(rows*16)?` → 要不到就 `enter_spill(vec![table])`。
- ✅ 两条 `#[ignore]` 已解除，**双双转绿**；另加白盒用例
  `push_degrades_instead_of_failing_when_budget_is_exhausted`（用 **run 数**证明降级路径真被走到，
  不是"恰好够用"——§五 教训的直接应用）。
- 顺带：`MemoryPressure` 错误信息从 MB 改 KB（MB 会把小预算三个数全抹成 0，排障瞎眼），
  并加上 cache/可挤兑量；`yieldable_bytes` 走只读 `used_bytes`（**不能**走 `yield_bytes`——
  那会真去挤兑，拼错误信息顺手清空缓存）。

## 三、★ F23（qsdb-sync 反馈）—— **主条已闭环**（2026-10-13）

**修法**：新增 `fsutil::with_dir_lock(store, path, f)` —— 锁入口**按后端分派**：
Local 走 `PartitionLock::acquire_local`（flock，语义不变）；Remote 走进程内
同路径互斥（`remote::with_partition_mutex`，跨进程/多实例由对象存储条件写收敛）。
取**闭包形态**而非 RAII guard：Remote 臂的 `Arc<Mutex<()>>` 存在全局表里，guard 会
自引用；闭包两臂同形，调用点也没有"忘 drop"的余地（也避免了 `parking_lot` 新依赖）。

## 三之二、★ F25（qsdb-sync 反馈）—— ✅ **已闭环**（2026-10-13，`000c0e7`）

**现象**（对方复测 F24 时发现）：脑裂后两边**独立演进到同一个 generation** →
replica 判据 `src == dst` 误判 up_to_date，而内容不同 → **静默分歧**。
**根因**：`generation` 是**计数器**不是内容指纹，防脑裂只是**单向**保证
（`dst > src` 拒绝），`dst == src` 不蕴含内容一致。

**定案（采纳对方建议 ①）+ 落地**：新增 `PartitionManifest.epoch`（**写者身份代**）——
与既有的 `writer_epoch`（随机、只作诊断、**不参与正确性**）**刻意分开**：后者已发布
语义就是"不参与正确性"，复用等于改已发布语义；且它是随机的，复用会让旧 manifest 的
随机值被当成"某一代写者"。

- `QsdbOptions::writer_epoch`（默认 0）+ `--writer-epoch`（server/query/shell）；
- **每次提交盖章**（append / overwrite / 远端 OCC / compaction 四条路径全覆盖）；
- **内核自己也不许回退写**：盘上 epoch > 本配置 → 新码 **`STALE_WRITER`**
  （409 / `retry=no` / `40001` / gRPC ABORTED），检查点在**锁内、写段之前**，
  被拒的写不动数据；
- 生态判据换成 `(epoch, generation)` 复合序 → 撞值不可能，且**不需要每轮读内容摘要**；
- 建议 ②（`manifest_digest` 内容摘要）**不进常规判据**，留给对账/巡检，对方要做再加。

默认全 0 时两项都是 no-op（旧 manifest 缺字段即 0），**现存部署行为不变**。
回归 `tests/writer_epoch.rs`（3 例）+ 码表文档逐字对账；已回写 qsdb-sync（`e0d1baa`）。

| `spill_distinct`（DISTINCT + 16MB 配额） | 4.84s / **峰值 RSS 3.03 GB** | 6.44s / **473 MB**（内存 1/6.4，代价 +33% 时间） |
| `spill_group_by`（GROUP BY + 64MB 配额） | 0.29s / 470 MB（**配额形同虚设**：分片聚合路径当时不记账） | 0.87~1.0s / 215 MB（**慢 3 倍，待优化**：分区数/缓冲/落盘文件数） |

### 记账缺陷家族（四条，同源：**逃生通道的准入门槛**）—— 全部闭环

1. 峰值/双份预留（排序尾块、join build 侧）用 `?` 上抛 → 查询被打死（`6d91004` 修）。
2. `SortExec` 的 `chunk_bytes` 与预留不同步：**已证伪**（插桩 500 批恒等）——不是 bug。
3. `PartSpill` 的分区数/缓冲上界不看全局预算 → 小预算下溢出开不起来（`PartSpill::plan` 修，§二）。
4. join 键索引 `res.grow(rows*16)?` 硬 `?`（隐藏最深的一条：**只在"行装得下、索引装不下"
   的窗口里触发**，前三条的表现都盖在它前面）→ 同样改为转溢出。

**共性结论**：凡"本算子有溢出能力、额度却先要不到"的地方，**一律改降级或转溢出，不许上抛**；
反过来，真正的算子固有需求（join 建索引、窗口排序要整分区）**必须如实报错**，别用降级假装能跑。

### F24 连带挖出的两个 bug（2026-10-13）

| # | 症状 | 根因 | 回归 |
|---|---|---|---|
| 1 | **远端 overwrite 不推进 `generation`**（本地正常） | `occ_replace_entries` 只写 `generation = cur`，漏了 `+1`（`occ_append_entry` 与本地 `commit()` 都有）→ ① F24 的 CAS 在远端形同虚设；② **生态以 generation 为增量判据者会漏掉远端 overwrite**（qsdb-sync 契约） | `tests/remote_managed.rs::remote_overwrite_advances_generation` |
| 2 | **HTTP `mode=overwrite` 一直 400** `batch lacks partition column` | CLI 分支先把批按分区**剥**好，再交给 `Qsdb::overwrite_partition`（其约定是**全列批**、库里自己剥）→ 双重剥离。embed 用户传全列批故从未暴露；契约文档却写着该端点可用 | `tests/http_contract.rs::http_overwrite_mode_works` |

**教训**：契约文档写"可用"的端点，必须有契约测试钉着——本仓 `http_contract.rs` 覆盖了只读/取消/参数严格性，**唯独没覆盖 overwrite 的正向路径**，于是它坏了很久没人知道。

### ORDER BY 两个静默错误（本批 3 修，2026-10-13）

| # | 症状 | 根因 | 回归 |
|---|---|---|---|
| 1 | `SELECT v, w FROM t ORDER BY v, w` 并列**不按第二键排**（无报错、顺序错） | `rewrite_plan` 拿排序键 idx（**输入输出序**）去查"表列序→投影序"映射 → 两键塌成一列 | `tests/order_by_prune.rs` |
| 2 | `SELECT v FROM t ORDER BY w` 给客户端回**两列**（多 `__sort_1`） | 隐藏排序列追加后没被收回 | 同上 |

**共性**：两者都只在**列裁剪真的生效**（投影是表的真子集）且**有并列/NULL**时才暴露，
所以既有用例全绿。写 TopN 用例时按"能区分对错"构造（并列值 + 列数断言）才把它们顶出来。

### 两条工程教训（都踩过）

- **"用例其实是空的"比 bug 更难发现**：`sql_collect` 走 `benign()` 让两个"全局预算"
  验收用例全程没让预算生效（其中一个还被 `count(*)` 下推改成没有溢出分支的算子）。
  对策：像 `spill_path_is_really_taken` 那样**用可观察量证明被测路径真被走到**。
- **多代理共用一棵工作树 + 默认 `target/` 会互相破坏**：
  ① 谁跑一次 `git checkout/stash` 就能静默抹掉别人的未提交改动（已发生一次）；
  ② 并发 cargo 会让 `cargo run` 拿到**过期二进制**，误判"改动没生效"。
  对策：**每条并行流独立 worktree + 独立 `CARGO_TARGET_DIR`**，并禁止共享树里的
  git 写操作（只读命令随便用）。
