# 大结果集分页与截断 —— 设计规范（2026-10-19，第十七批设计稿）

> **缘起**：十六批 §七 并发实测立题——同一台 .14、同一张 500 万行基准表，
> 1 行结果（`count(*)`/点查）远程 **~3400 qps**，10 万行结果（10 万组 GROUP BY）
> 远程 **~5 qps**：**680× 的差距全部来自"把行搬给客户端"这一段**，与计算无关
> （引擎侧同款聚合只要几十毫秒）。本文定稿问题边界、业界对照、契约形态与分期。
>
> **纪律**：契约**只增不改**（新码/新字段，零行为变更的默认值）；**显式拒绝
> 优先于静默截断**（本仓 F 系列一以贯之：截断曾让 SHOW TABLES 静默丢表）；
> 减法——不为"可能有人要"预建有状态机制；唯一真源（`docs/error-codes.md`、
> `docs/configuration.md` 同步纪律）。

---

## 一、问题定义（三层，都是实测/实代码，不是推测）

| 层 | 问题 | 证据 |
|---|---|---|
| **传输** | 10 万行结果远程 ~5 qps；500 万行 `SELECT *` 的 JSON body 约数百 MB、秒级传输——带宽与连接被单条查询独占 | 十六批 §七：同机 1 行结果 3400 qps vs 10 万行 5 qps |
| **服务端内存** | JSON 通道**先物化后序列化**：`batches_to_json` 把全部行攒成 `Vec<Vec<Value>>`（server.rs:2917）才开始输出——500 万行的中间体是**行数 × 列数个 `serde_json::Value`**（每个 ~24B 起，含装箱），服务端 RSS 跟着结果体量走尖峰 | 代码现状（上列行号） |
| **客户端** | 驱动/BI 一次拿全结果进宿主堆：JDBC 无 fetch-size 分块协议可依 → JVM OOM；BI"浏览数据"裸跑 `SELECT *` 即整表搬迁 | 场景推演；MySQL/PG 均有对应机制（见 §二） |

**现状：三层都没有任何护栏**——`/api/v1/query` 对结果体量零上限，"没有闸"在
并发实测里已经被证明是排队无界的同族问题（并发闸默认 0 的教训同款）。

## 二、业界对照（普查与取舍）

| 系统 | 机制 | 形态 |
|---|---|---|
| **PostgreSQL** | 扩展查询协议 `Execute(max_rows)`：驱动设 fetch-size，**同一游标多次往返**取批 | 协议级流式（有连接状态） |
| **MySQL** | ① `sql_select_limit` 会话变量 = **服务端隐式 LIMIT**（截断式护栏）；② `max_allowed_packet` 包上限；③ Connector/J `useCursorFetch` 服务端游标 | 旋钮 + 流式 |
| **Oracle** | OCI prefetch/ARRAYSIZE：客户端按批拉取，服务端游标保持 | 协议级流式 |
| **SQL Server** | ODBC `SQL_ATTR_MAX_ROWS` 语句属性 → 服务端隐式 LIMIT | 截断式护栏 |
| **ClickHouse** | `max_result_rows` + `result_overflow_mode = throw \| break`：**throw 报错、break 返回部分** | 护栏（两种语义可选） |
| **Spark** | `spark.driver.maxResultSize`（默认 **1GB**，超限 **fail**，不给部分结果） | 护栏（throw 式，默认开） |
| **DuckDB** | `SET max_result_size`（结果物化内存上限，超限报错） | 护栏（throw 式） |
| **BigQuery** | REST `maxResults` + `pageToken`：结果对象**存服务端**（24h），按页取 | 协议分页（**有状态**） |
| **Snowflake** | 结果按 chunk 切（每块独立 URL），JDBC 分块下载 | 协议分页（**有状态**） |

**三条结论（定案依据）**：

1. **驱动系数据库（PG/MySQL/Oracle）没有"协议分页"这回事**——它们是
   **长连接上的 fetch-size 流式**（同一游标多次往返）+ **服务端 LIMIT/包上限旋钮**。
   我们对应物：`ipc`/`rows`/`bulk` 本就是**分块流式编码**（单响应内客户端可增量
   消费），缺的是护栏旋钮。
2. **云仓库（BigQuery/Snowflake）的 pageToken/分块 URL 依赖服务端保存结果对象**
   ——有状态、要 TTL/GC/结果存储面。这与本仓"减法 + 无状态 HTTP"的定位相反，
   **v1 明确不做**（§3.4 留位）。
3. **分析系（ClickHouse/Spark/DuckDB）的答案收敛于"溢出护栏"，且三家主流
   （Spark/DuckDB/ClickHouse-throw）全部选 throw 式**。ClickHouse 的 `break`
   （返回部分数据 + 标记）是可选语义——本仓纪律（静默部分数据的教训）⇒
   **只做 throw，不做 break**。

QSDB 定位（嵌入式/单机分析库 + HTTP/驱动双面）⇒ **采 1 + 3，不采 2**。

## 三、设计（三层 + 一留位）

### 3.1 层一：结果护栏（截断，throw 式）——本批主体

**两个旋钮**（与并发闸/预算同族，热更，默认 **0 = 关**，零行为变更）：

| 旋钮 | CLI | 热更 | 语义 |
|---|---|---|---|
| `--max-result-rows` | 启动期 | ✅ `PUT /api/v1/config`（键 `maxResultRows`） | 单次查询结果**行数**上限（精确，执行后即知） |
| `--max-result-mb` | 启动期 | ✅（键 `maxResultBytes`，MB→字节） | 单次查询结果**体量**上限（估算，见下） |

**判定点与语义**：

- **检查点在执行完成之后、序列化之前**——行数精确已知（`Σ batches.num_rows()`）；
  字节用 Arrow 数组内存量估算（`get_array_memory_size()` 含缓冲区）。⚠️ JSON
  序列化后体积可达估算值的 1.5~3×（字符串转义/数字展开）——`rows` 上限是
  **精确**护栏，`bytes` 上限是**估算**护栏，文档如实标注，部署者按需选。
- 超限 → **恒定拒绝，绝不返回部分数据**：
  **`400 RESULT_TOO_LARGE`**（SQLState `54000` program_limit_exceeded，
  `retry=no`，类别 `query`——与 `QUERY_MEMORY_LIMIT` 同构："改查询（加 LIMIT /
  换流式格式）才有用，重试无用"）。error 文案带**实际行数/估算体量与上限**，
  并提示"加 LIMIT 或改用 ipc/rows/bulk 流式格式"。
- **只作用于 `SqlResult::Query`**（结果集）；DML 回执（恒小）、`COPY TO`
  （服务端写盘，不是结果集）、嵌入面（宿主自治，M7-A 边界）、Flight
  （本就是流，v1 不设闸）不适用。
- **每请求覆盖**（与 `X-QSDB-Timeout-Ms` 同款形态，双向覆盖）：
  body 可选字段 `"maxRows": N`（camelCase 别名 `max_rows`；0 = 本次不限）+
  请求头 `X-QSDB-Max-Rows`；头与 body 同时给时 **body 优先**（与 `database`
  字段同理）。护栏意识明确的部署把查询面只暴露给可信客户端（本就有 grants）。
- **观测**：`qsdb_queries_rejected_total{reason="result_size"}` 计数器
  （既有拒绝计数族加一档，标签值只增）。

**为什么 throw 不 break**（ClickHouse 有 break=返回部分+标记）：本仓两次被
"静默截断"咬过（SHOW TABLES 长表名被截 → 39 张表静默跳过；`&v[..21]` 按字节
切片 panic 看似查询失败）——**部分数据是最危险的失败形态**：消费方拿不完整
的行集出的报表没有任何异常信号。Spark/DuckDB 同判（fail，不给部分）。

### 3.2 层二：JSON 通道服务端内存有界化（流式序列化）

现状 `batches_to_json` 全量物化（§一层二）→ 改为**逐批流式输出**：
`axum::body::Body::from_stream` 按批产出 JSON 行片段，服务端驻留与单个批
（8192 行）相关、与总行数无关。

**契约不变**：响应仍是同一个 JSON 对象 `{"queryId", "schema", "rows": [...],
"rowCount", "elapsedMs"}`——对象**键序无关**（serde_json/任何 JSON 解析器
按名取值），流式只是把 `rows` 数组逐段吐出。契约测试逐字节断言行为不感知
实现差异（若有键序断言则修正测试，契约文档本就按"字段名"承诺）。

配套：`ipc` / `rows` / `bulk` / `csv` 四通道本就是流式/分块编码（rows 逐块、
ipc 逐批），已在同一响应内可增量消费——**不新增机制，文档明示**（§3.3）。

### 3.3 层三：大结果的正确姿势（契约文档化，不新增机制）

写进对接契约与部署模板，与业界同款话术：

1. **浏览/取数用 SQL 分页**：`LIMIT/OFFSET`（浅分页）；深翻页用 **keyset**
   （`WHERE id > $last ORDER BY id LIMIT n`，OFFSET 深页是 O(offset) 重扫——
   PG/MySQL 同款限制与同款建议）。
2. **程序化大结果走流式通道**：`format=ipc|rows|bulk`（三者的编码本就是
   分块的；`rows` 为驱动向逐块设计——`docs/rows-format.md`）。JDBC
   `fetchSize` 的对应实现 = **驱动按块增量消费 rows 流**，不必等整个 body
   落地（qsdb-jdbc 设计注记）。
3. **`json` 只给人看/小结果**（BI 图表、元数据探测）——护栏超限的文案同款提示。

### 3.4 明确不做（v1）：有状态结果游标（pageToken/分块 URL）

BigQuery/Snowflake 模式 = 服务端保存结果对象 + TTL + 结果 GC + 游标状态面
+ 集群语义。这是**另一个量级的子系统**，且与"无状态 HTTP + 减法"定位相反。
触发条件（留位判据，满足任一再立项）：
- 出现真实消费方需要**跨请求、可重连**地分页同一结果集（当前 JDBC/BI 均无此诉求）；
- 服务端结果缓存能顺带解决**重复聚合**（那是结果缓存/物化视图的题，不是分页的题）。

### 3.5 与既有语义的边界（三闸对照，写进错误码文档）

| 闸 | 管什么 | 触点 | 码 |
|---|---|---|---|
| 查询超时 | **计算时长** | 执行中 | `QUERY_TIMEOUT`（408） |
| 单查询内存配额 | **执行内存**（物化算子记账） | 执行中 | `QUERY_MEMORY_LIMIT`（400） |
| **结果护栏（本批）** | **结果传输体量** | 执行后、序列化前 | `RESULT_TOO_LARGE`（400，新） |

三者正交：一条查询可以算得快、省内存、但结果太大（护栏拦）；也可以结果小、
算得久（超时拦）。护栏检查点在执行后 ⇒ **不省计算**——纯护栏，不是熔断。

## 五、分期与验收

| 期 | 内容 | 验收 |
|---|---|---|
| **R1 结果护栏** | 码 + 旋钮（CLI/热更）+ 检查点（行/字节）+ 每请求覆盖 + metrics + 契约测试 | 单测：行上限精确触发、字节估算触发、`maxRows=0` 本次不限、覆盖优先级（body > 头 > 服务器）、DML/COPY 不受影响；契约：四格式（json/ipc/bulk/rows/csv 全体）超限恒 400 且不回部分数据、目录端点码表条数、`applied` 热更；**回归**：默认关 ⇒ 19 基准 + 154 语料原样 |
| **R2 JSON 流式** | `batches_to_json` 逐批流式输出 | 契约：JSON 形态逐字段不变（含 rowCount/零行/NULL/Decimal 字符串）；内存断言（大结果服务端 RSS 无行数线性尖峰——用 VmHWM 对照）；全量回归同 R1 |
| （v2 留位） | 有状态结果游标 | 触发条件见 §3.4；立项先出设计稿 |

每期独立提交、独立验收（成批闭环）；R1/R2 都动 server 面，内核零改动
（`SqlResult`/执行器不动）。

## 六、不做清单（v1 边界）

- **break 式部分返回**（ClickHouse 有）——静默部分数据是本仓红线
- 服务端结果对象/游标/TTL（§3.4）
- 会话级/用户级结果配额（§六·配置分层：留位不做，需求来了再加）
- Flight 面护栏（流式协议，客户端背压天然存在）
- OFFSET 深分页的引擎优化（keyset 文档化即可，PG/MySQL 同判）
