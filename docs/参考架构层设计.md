## 一、总体分层（推荐）

```
┌────────────────────────────────────────────┐
│ 接入层（Facade / Frontend）                │
│  SQL / HTTP / CLI / Arrow Flight           │
└───────────────────┬────────────────────────┘
                    │
┌───────────────────▼────────────────────────┐
│ 查询引擎层（Query Engine）                  │
│  Parser → Planner → Optimizer → Executor   │
└───────────────────┬────────────────────────┘
                    │
┌───────────────────▼────────────────────────┐
│ 执行运行时（Execution Runtime）             │
│  向量化执行 / Pipeline / 内存池             │
└───────────────────┬────────────────────────┘
                    │
┌───────────────────▼────────────────────────┐
│ 存储抽象层（Storage Abstraction）           │
│  Table / Partition / Segment / WAL         │
└───────────────────┬────────────────────────┘
                    │
┌───────────────────▼────────────────────────┐
│ 存储引擎层（Storage Engine）                │
│  Parquet / WAL / MemTable / Compaction     │
└───────────────────┬────────────────────────┘
                    │
┌───────────────────▼────────────────────────┐
│ I/O 适配层（I/O Backend）                  │
│  Local / HDFS / S3 / 对象存储              │
└────────────────────────────────────────────┘
```

## 二、接入层（Facade / Frontend）

**职责：对外暴露接口，不关心执行细节**

### 支持方式

| 接入方式 | 说明 |
|--------|------|
| SQL | 主接口，ANSI SQL 子集（SELECT / INSERT） |
| HTTP | REST API，适合 BI / 程序接入 |
| CLI | REPL，调试 & 运维 |
| Arrow Flight（可选） | 高性能跨语言查询 |

### 建议设计

- **统一内部表示：LogicalPlan**
- SQL / HTTP / CLI 最终都转成 `LogicalPlan`
- 接入层不做优化、不读数据

✅ 好处：
- 新接入方式成本极低
- 查询引擎完全解耦

---

## 三、查询引擎层（Query Engine）

**职责：把 SQL 变成可执行的计划**

### 子层划分

```
SQL Text
  ↓
Parser（sqlparser-rs）
  ↓
AST
  ↓
Binder（元数据绑定）
  ↓
LogicalPlan
  ↓
Optimizer
  ↓
PhysicalPlan
```

### 关键设计点

#### 1. Parser
- 直接用 `sqlparser-rs`
- 不要自己写 SQL 解析

#### 2. LogicalPlan
- 用 **关系代数节点**
- 示例：
```text
Scan
 └─ Filter
    └─ Projection
```

#### 3. Optimizer（轻量）
初期至少支持：
- 谓词下推
- 投影裁剪
- 分区裁剪

❌ 不建议：
- 复杂 CBO（代价优化）
- Join reorder（初期）

## 四、执行运行时（Execution Runtime）

**这是性能核心**

### 核心原则

- ✅ 向量化执行（batch）
- ✅ push-based pipeline
- ❌ 行级执行
- ❌ 大内存拷贝

### 推荐执行模型

```
PhysicalPlan
  ↓
ExecutionGraph
  ↓
Pipeline（算子链）
  ↓
Batch（Arrow RecordBatch）
```

### 内存控制重点

- 全局内存池
- 每个查询有 quota
- 溢出到磁盘（可选）

📌 建议：
- 执行层只操作 `RecordBatch`
- 算子无状态或局部状态

## 五、存储抽象层（Storage Abstraction）

**职责：屏蔽“数据在哪、怎么组织”**

### 核心抽象

| 抽象 | 说明 |
|----|----|
| Catalog | 库 / 表 / Schema |
| Table | 表逻辑视图 |
| Partition | 分区（时间 / hash） |
| Segment | 不可变数据块 |
| WAL | 写入日志 |

### 设计原则

- **Segment 是不可变单位**
- 查询只读取 Segment
- 写入只写 WAL + MemTable

## 六、存储引擎层（Storage Engine）

这是你“低占用 + 高性能”的关键。

### 写入路径（Write Path）

```
INSERT
 ↓
WAL（顺序写）
 ↓
MemTable（内存）
 ↓（达到阈值）
Flush
 ↓
Parquet Segment
```

### MemTable 建议

- 行存 or Arrow 列存
- 固定大小
- 写满即 flush

### Parquet 是核心格式

✅ 原因：
- 列存
- 原生 predicate pushdown
- 广泛生态
- 压缩友好

### Compaction（合并）

- 后台线程
- 小文件合并
- 不做 update / delete
- 可合并统计信息

## 七、I/O 适配层（I/O Backend）

**职责：让存储引擎不关心文件系统**

### 抽象接口（建议）

```rust
trait FileSystem {
  async fn read(&self, path) -> Bytes;
  async fn write(&self, path, data);
  fn list(&self, prefix);
}
```

### 支持后端

| 后端 | 场景 |
|----|----|
| Local FS | 单机 |
| HDFS | 大数据集群 |
| S3 / OSS | 云原生 |
| 内存 FS | 测试 |

📌 建议：
- 用 `object_store` crate
- 不要自己封装 HDFS / S3

## 八、元数据 & 事务（简化版）

你说：
> 不支持更新，也没有事务

那可以：

### 元数据设计

- 表结构（Schema）
- Segment 列表
- 分区信息

### 存储方式

- 本地 JSON / TOML（初期）
- 或 RocksDB（后期）

### 一致性模型

- WAL 保证写入不丢
- Flush 是原子切换
- 查询看到的是“最近一次 flush”

## 九、一个 INSERT + SELECT 的完整路径

### INSERT

```
SQL
→ Parser
→ LogicalPlan(Insert)
→ WAL
→ MemTable
```

### SELECT

```
SQL
→ Parser
→ LogicalPlan
→ Optimizer
→ PhysicalPlan
→ Pipeline
→ Parquet Scan
→ Filter / Project
→ RecordBatch
→ Arrow / JSON
```
