# 生态面功能补齐（**性能留最后**）

> **用户 2026-10-15 定的顺序**：先把**功能**补齐（缺的、异常的、协议说不清的），
> **性能排最后** —— 理由：性能没有卡住功能，而功能缺失会让生态工具直接没法用。
>
> **总原则**：**内部再乱，对外协议先钉死**。生态工具照协议开工，我们内部慢慢对齐；
> 进度差用一张**建设表**（§四）告诉生态"我要支持什么、协议长什么样、做到哪了"。

---

## 一、为什么是这个顺序（不是性能）

- **性能不卡功能**：慢一点的查询仍然**能跑完**，工具能出结果；
- **功能缺失卡死工具**：`ROWS BETWEEN` 拒了，Tableau 的移动平均就跑不了 —— 工具方
  没有任何绕路（等价改写是自连接，没人会那么在 BI 里写）；
- **协议的稳定性**比两者都重要：驱动/生态一旦按协议开工，我们**不能**因为内部
  重构就改协议面（`对接契约.md` §五已承诺"端点只加不改不删"）。

## 二、批次（每批自成闭环 + 过闸门 + 值级验收）

| # | 项 | 为什么排这里 | 现状 |
|---|---|---|---|
| **1** | **窗口帧 `ROWS BETWEEN …`** | 分析刚需（累计和/移动平均），且**无等价改写**；默认帧已是累计，缺的只是"自己指定帧" | **✅ 2026-10-15 已交付**（`58a9e8d`）—— 验收 `crates/qsdb/tests/window_frame.rs`（13 条）。**落地记要见 §三** |
| 1b | **`count(*) OVER (…)`** | 顺带挖出来的同族洞：报 `needs an argument`（把"没实现"说成"你写错了"），而支持面文档**声称**窗口 `count` 可用 | **✅ 2026-10-15 已交付**（`*` 与 `x` 用 `Option<PhysExpr>` 分开） |
| 2 | **`GROUP BY 1` 位置序号** | `ORDER BY 1` 是 ✅、`GROUP BY 1` 是 ✋ —— **不对称会反复踩** | ✋（2026-10-15 已把误导文案改成指名道姓）。**`ORDER BY` 有现成机制可抄** |
| 3 | **聚合 `FILTER (WHERE …)`** | 与 `DISTINCT` 同族，且此前是**静默忽略**（回全量 = 错值） | ✋ 显式拒绝 |

**不做（已定案）**：
- **`UPDATE`** —— **定位声明**，不是待办：这是分析库，**没有行级 UPDATE/DELETE**；
  换数据用 `INSERT OVERWRITE`（分区级原子替换）或重写表。要写成 `对接契约.md` 的
  **一等条目**，让 BI/ORM 知道该改写而不是等我们（见 §四的建设表）。

## 三、批次 1 交付记要：`ROWS BETWEEN`（**2026-10-15 已落地**，`58a9e8d`）

代码即真相（`exec/window.rs` + `sql/translate.rs`），这里只留**决策与偏差**。

### 落地形态

- `WindowFn` 的聚合变体带 `Option<RowFrame>`：`Some` = 用户写了帧（走滑窗路径），
  `None` = 默认帧（**原运行累加器一字不改**）。`RowFrame` = `{start, end}`，
  边界 `Unbounded | Preceding(n) | Current | Following(n)`。
- 求值：`sum/count/avg` 走**前缀和**（O(1)/行）；`min/max` 走**单调队列**
  （摊还 O(1)/行，帧两端都随行号单调不减是它能用的前提）。溢出路径逐分区算
  ⇒ 与内存路径走的是**同一段代码**（`run_window`）。
- 验收：`crates/qsdb/tests/window_frame.rs`，12 条逐值手算对照。

### ⚠️ 与原设计（本轮侦察稿）的**四处偏差** —— 都是"按标准/按纪律"改的

1. **空帧给 NULL，不是"夹到分区边界"。**
   原稿只写了"分区内行数 < 帧长 ⇒ 夹到边界"，漏了另一种：边界**整个落在当前行
   之外**（`ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING` 在分区首行）。回夹到分区首行
   会变成"取首行" —— 静默错值。PG / DuckDB 都给 **NULL**，故按标准来：
   帧 = `{j | i-a ≤ j ≤ i+b}` ∩ 分区，**可能为空**；空帧时 `count` = 0、其余 NULL。

2. **帧 + 无 `ORDER BY` ⇒ 显式拒**（原稿写的是"提示但不报错"）。
   本仓**没有 warning 通道**；而没有 `ORDER BY` 时行序由扫描决定（并行下会变），
   按行号分帧的值**不可复现** —— 那就是静默错值。例外：`ROWS BETWEEN UNBOUNDED
   PRECEDING AND UNBOUNDED FOLLOWING`（整分区，与行序无关）放行。

3. **默认帧的 NULL 口径一并修正**（0 / NaN → **NULL**）。
   不改的话，"显式默认帧"与"隐式默认帧"两种写法会给**不同的值** —— 恰是这批要
   消灭的东西，而且验收表里就有一条"两者必须逐值相同"。做法：主循环只多一个
   `else if cnt == 0` 的判空（**无 NULL 数据时一次都不 push，零额外分配**），
   真出现"帧内无值"时才付一次 `Vec<Option<T>>`。
   ⇒ 已生效的连带改动：`tests/limit_offset_nulls.rs` 里钉住旧行为 `0` 的断言
   改成 `NULL`（那条断言钉的正是错值）。

4. **`count(*) OVER (…)` 一并补**（原侦察没发现它压根不支持）。
   报的是 `needs an argument`（把"没实现"说成"你写错了"），而 `SQL支持面.md`
   声称窗口 `count` 可用 —— 与 F29 同一类。改法：`Count(Option<PhysExpr>, …)`，
   `None` = `*`（数**行**），与聚合那边同一套表示。**不要**用 `count(1)` 顶替：
   那样列名会变成 `count(1)`，与用户写的对不上。

### 另外一处**原侦察漏掉的必改点**

`window_spec_sig`（`collect_window_calls` 的去重键）**必须把帧算进去**。
原签名只有 `PARTITION BY` + `ORDER BY`：两个只差帧的窗口调用（`sum(x) OVER (…
1 PRECEDING …)` 与 `… 2 PRECEDING …)`）会被当成**同一个调用**去重 ⇒ 两列都拿
第一个帧的结果。数字只差一点，肉眼极难发现 —— 典型静默错值。

### 验收清单（原稿 12 条 → 落点）

| 用例 | 落点 |
|---|---|
| 居中三行和 / 移动平均 / 显式默认帧 == 隐式默认帧 | `居中三行和` / `移动平均` / `显式默认帧与隐式默认帧逐值相同` |
| 滑窗 `min`/`max`（非单调序列） | `滑窗极值与非单调序列` |
| 帧跨分区边界 | `帧不跨分区` |
| 分区行数 < 帧长 | `帧长于分区时夹到分区边界` |
| **空帧** | `空帧给空值而不是夹到分区边` |
| 含 NULL 的列 | `空值口径`（顺带钉住与默认帧**逐值相同**） |
| `RANGE` 仍拒 / 非法边界拒 / 排名类带帧拒 | `该拒的都拒且指路` |
| 溢出路径 == 内存路径 | `溢出路径逐值相同` |
| 同 spec 两个不同帧不许去重 | `同_spec_不同帧不许去重` |
| `count(*)` vs `count(x)` | `count_星号数行而_count_列数非空` |

## 四、给生态的**建设表**（第三步产出，这里先定形态）

> 目的：让生态工具**照协议开工**，不必等内核完工。三列就够：
> **能力 | 协议（怎么写） | 状态（已支持 / 明确拒绝 / 计划支持 + 预计）**

| 能力 | 协议/写法 | 状态 |
|---|---|---|
| 查询/写入/元数据 | `POST /api/v1/query`、`/write`、`/tables`…（`对接契约.md` §三） | **✅ 稳定，只增不改** |
| 批量装载 | `bulk`(列式) / `rows`(行式) | ✅ |
| 取消查询 | `X-QSDB-Query-Id` + `/queries/{id}/cancel` | ✅ |
| 错误码 | `GET /api/v1/error-codes`（**运行期拉，别硬编码**） | ✅ |
| `JOIN`：INNER/LEFT/RIGHT/FULL/CROSS/USING | `ON`/`USING`；**大表放左边** | ✅ |
| 行级 `UPDATE` / `DELETE … WHERE <非分区键>` | —— | **✋ 定位**：分析库不做行级改；换数据用 `INSERT OVERWRITE` |
| 窗口帧 `ROWS BETWEEN` | `OVER (ORDER BY … ROWS BETWEEN a AND b)` | **✅ 2026-10-15**（`RANGE`/`GROUPS` 仍 ✋；帧不给空值就别指望 `sum` 回 0，它回 NULL） |
| `count(*) OVER (…)` | 同左 | **✅ 2026-10-15** |
| `GROUP BY 1` | `GROUP BY <列名>`（`ORDER BY 1` 已支持） | ⏳ 计划（#2） |
| 聚合 `FILTER (WHERE …)` | `count(*) FILTER (WHERE …)` | ⏳ 计划（#3） |
| CTAS | `CREATE TABLE` + `INSERT INTO … SELECT …` | ⏳ 计划（#4，**已有替代写法**） |
| 参数化查询 | —— | ⏳ 计划（协议面加 `params`；**客户端别自己拼 SQL**） |

**纪律**：表里的"状态"**只增不改**；任何一格从 ⏳ 变 ✅ 时，**协议列不许变**。
