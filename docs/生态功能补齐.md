# 生态面功能补齐（**性能留最后**）

> **用户 2026-10-17 定的顺序**：先把**功能**补齐（缺的、异常的、协议说不清的），
> **性能排最后** —— 理由：性能没有卡住功能，而功能缺失会让生态工具直接没法用。
>
> **总原则**：**内部再乱，对外协议先钉死**。生态工具照协议开工，我们内部慢慢对齐；
> 进度差用一张**建设表**（§四）告诉生态"我要支持什么、协议长什么样、做到哪了"。

---

## 一、为什么是这个顺序（不是性能）

- **性能不卡功能**：慢一点的查询仍然**能跑完**，工具能出结果；
- **功能缺失卡死工具**：`ROWS BETWEEN` 拒了，Tableau 的移动平均就跑不了 —— 工具方
  没有任何绕路（等价改写是自连接，没人会那么在 BI 里写）；
- **协议的稳定性**比两者都重要：驱动/生态一旦按协议开工，我们**不能**因为内部
  重构就改协议面（`对接契约.md` §五已承诺"端点只加不改不删"）。

## 三、批次 1 交付记要：`ROWS BETWEEN`（**2026-10-17 已落地**，`58a9e8d`）

代码即真相（`exec/window.rs` + `sql/translate.rs`），这里只留**决策与偏差**。

### 落地形态

- `WindowFn` 的聚合变体带 `Option<RowFrame>`：`Some` = 用户写了帧（走滑窗路径），
  `None` = 默认帧（**原运行累加器一字不改**）。`RowFrame` = `{start, end}`，
  边界 `Unbounded | Preceding(n) | Current | Following(n)`。
- 求值：`sum/count/avg` 走**前缀和**（O(1)/行）；`min/max` 走**单调队列**
  （摊还 O(1)/行，帧两端都随行号单调不减是它能用的前提）。溢出路径逐分区算
  ⇒ 与内存路径走的是**同一段代码**（`run_window`）。
- 验收：`crates/qsdb/tests/window_frame.rs`，13 条逐值手算对照。

### ⚠️ 与原设计（本轮侦察稿）的**四处偏差** —— 都是"按标准/按纪律"改的

1. **空帧给 NULL，不是"夹到分区边界"。**
   原稿只写了"分区内行数 < 帧长 ⇒ 夹到边界"，漏了另一种：边界**整个落在当前行
   之外**（`ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING` 在分区首行）。回夹到分区首行
   会变成"取首行" —— 静默错值。PG / DuckDB 都给 **NULL**，故按标准来：
   帧 = `{j | i-a ≤ j ≤ i+b}` ∩ 分区，**可能为空**；空帧时 `count` = 0、其余 NULL。

2. **帧 + 无 `ORDER BY` ⇒ 显式拒**（原稿写的是"提示但不报错"）。
   本仓**没有 warning 通道**；而没有 `ORDER BY` 时行序由扫描决定（并行下会变），
   按行号分帧的值**不可复现** —— 那就是静默错值。例外：`ROWS BETWEEN UNBOUNDED
   PRECEDING AND UNBOUNDED FOLLOWING`（整分区，与行序无关）放行。

3. **默认帧的 NULL 口径一并修正**（0 / NaN → **NULL**）。
   不改的话，"显式默认帧"与"隐式默认帧"两种写法会给**不同的值** —— 恰是这批要
   消灭的东西，而且验收表里就有一条"两者必须逐值相同"。做法：主循环只多一个
   `else if cnt == 0` 的判空（**无 NULL 数据时一次都不 push，零额外分配**），
   真出现"帧内无值"时才付一次 `Vec<Option<T>>`。
   ⇒ 已生效的连带改动：`tests/limit_offset_nulls.rs` 里钉住旧行为 `0` 的断言
   改成 `NULL`（那条断言钉的正是错值）。

4. **`count(*) OVER (…)` 一并补**（原侦察没发现它压根不支持）。
   报的是 `needs an argument`（把"没实现"说成"你写错了"），而 `SQL支持面.md`
   声称窗口 `count` 可用 —— 与 F29 同一类。改法：`Count(Option<PhysExpr>, …)`，
   `None` = `*`（数**行**），与聚合那边同一套表示。**不要**用 `count(1)` 顶替：
   那样列名会变成 `count(1)`，与用户写的对不上。

### 另外一处**原侦察漏掉的必改点**

`window_spec_sig`（`collect_window_calls` 的去重键）**必须把帧算进去**。
原签名只有 `PARTITION BY` + `ORDER BY`：两个只差帧的窗口调用（`sum(x) OVER (…
1 PRECEDING …)` 与 `… 2 PRECEDING …)`）会被当成**同一个调用**去重 ⇒ 两列都拿
第一个帧的结果。数字只差一点，肉眼极难发现 —— 典型静默错值。

### 验收清单（原稿 12 条 → 落点）

| 用例 | 落点 |
|---|---|
| 居中三行和 / 移动平均 / 显式默认帧 == 隐式默认帧 | `居中三行和` / `移动平均` / `显式默认帧与隐式默认帧逐值相同` |
| 滑窗 `min`/`max`（非单调序列） | `滑窗极值与非单调序列` |
| 帧跨分区边界 | `帧不跨分区` |
| 分区行数 < 帧长 | `帧长于分区时夹到分区边界` |
| **空帧** | `空帧给空值而不是夹到分区边` |
| 含 NULL 的列 | `空值口径`（顺带钉住与默认帧**逐值相同**） |
| `RANGE` 仍拒 / 非法边界拒 / 排名类带帧拒 | `该拒的都拒且指路` |
| 溢出路径 == 内存路径 | `溢出路径逐值相同` |
| 同 spec 两个不同帧不许去重 | `同_spec_不同帧不许去重` |
| `count(*)` vs `count(x)` | `count_星号数行而_count_列数非空` |

## 三之二、批次 2 交付记要：`GROUP BY 1`（**2026-10-17 已落地**，`50795ed`）

原计划只有"位置序号"一项，落地时**连环挖出两个更大的既有洞**，一并闭环。
记在这里是因为**第 2、3 条与序号无关**，只是被它引出来的。

### ① 序号本身

`group_key_expr`：绑定**之前**把裸整数换算成投射里那个表达式
（`GROUP BY 1` ≡ 第 1 列，与此前 `ORDER BY 1` 那套**同标准**，不再是不对称）。
四类显式拒：越界 / 非整数（`1.5`）/ 指向聚合 / 指向 `SELECT *`。

### ② ★ 表达式分组键**全都不工作**（比 ① 严重得多）

`GROUP BY upper(s)` / `v % 2` / `CAST(…)` / `CASE WHEN …` / `a ‖ b` **无一能跑**，
全报"列 's' 必须出现在 GROUP BY 里"——**把"没实现"说成"你写错了"**（F29 同族）。

**根因是判据用错了渲染器**：`rebind_over_agg` 拿 **AST 的 `to_string()`** 去比
**`PhysExpr::display()`**，而后者带括号（`(g + 1)` vs `g + 1`）⇒ **永远比不中**，
于是所有表达式键都掉进递归，最后在里面的裸列上报错。
修法：两边都**绑定成 `PhysExpr`** 再比（同一个渲染器），收口成 `group_key_pos`。

⚠️ **`SQL支持面.md` 的 `GROUP BY` 整行一直标 ✅ —— 那条是虚的**（第三次栽在
"文档说 ✅、实测不 ✅"上）。已把表达式键单列一行并注明。

### ③ ★ 「常量数组必须广播到批长」一族，**四个落点**

`eval` 对常量返回**长度 1** 的数组，而下游处处按**批内行号**索引它。四种表现
**全是内部错误或 panic**（此前没人撞见，因为报的是"引擎坏了"式的内部话术、
不像"我写错了"）：

| 落点 | 此前表现 |
|---|---|
| `ProjectExec`：`SELECT 1, g FROM t` | `all columns in a record batch must have the same length`。**这是最普通的一句 SQL**；全常量 `SELECT 1 FROM t` 靠事后那段广播侥幸能过 ⇒ 洞**只对"混合"形态显形** |
| 聚合**分组键**：`GROUP BY 'k'` | **panic** `Trying to access an element at index 1 from a StringArray of length 1` |
| 聚合**参数**：`sum(1)` | **panic**（同上，PrimitiveArray） |
| JOIN **残留谓词**：`ON a.k = b.k AND true` | **panic**（BooleanArray） |

收口成一个 `exec::broadcast_const`（**同一份实现四处共用**，不再各写各的）。

### ④ 连带修一处**静默无效**：`ORDER BY <越界序号>`

它此前是**借了 ③ 的力**才报错的（越界序号退回"当常量排序键"，常量列与真列对不齐
⇒ 抛内部错误）；③ 把广播修好后，它就**静默变成不排序**了（用户以为排了、其实没有）。
`sql_gaps::order_by_ordinal` 当场抓到 —— 那条断言一直是"借 bug 通过"。
现在显式校验范围。

### 教训（写给下一次）

**"按行索引数组"的代码，先问一句：它会不会是常量？** 这族坑咬过四次，
每次的报错都指向错的嫌疑人（"引擎坏了"而不是"我写错了"）。

## 三之三、批次 3 交付记要：聚合 `FILTER (WHERE …)`（**2026-10-17 已落地**，`8693282`）

### 落地形态

`AggExpr` 增 `filter: Option<PhysExpr>`；语义**落到执行层**（`exec::agg` 在更新
每个聚合**之前**按自己的掩码筛行）。掩码是**逐聚合**的 —— 同一条 SELECT 里两个
聚合可以各有各的谓词，所以**不能**在批次层面统一预筛（那会让它们互相污染）。
无 FILTER 时**原路径一字不改**（热路径零代价）。

分组键的形成**不受** FILTER 影响：谓词只决定"这行喂不喂给某个聚合"，不决定组
存不存在（PG 同样 —— 全不匹配的组照样出现、回 `0` / `NULL`）。

### ★ 四条**独立**的坑（全是"先跑到红"才发现的）

| 坑 | 表现 |
|---|---|
| **① 元数据短路**（`sql/mod.rs`） | `count(*)` 直接回 parquet footer 行数、**压根不看行** ⇒ `count(*) FILTER` 回全量 |
| **② JOIN 计数下推**（`JoinCountExec`） | 只按键计数，没有"逐行谓词"这一步 |
| **③ DISTINCT 融合计数**（`DistinctCountExec`） | 整行计数 |
| **④ `out_name` 去重键漏了谓词** | `collect_aggs` 按 `out_name` 去重，而它一直是 `count(*)` ⇒ `FILTER (v>15)` 与 `FILTER (v<15)` 被并成**同一个聚合**、两列拿同一个数字 |

①②③ 是同一族：**"整表/整行计数"式捷径，各自不看行**。它们**都不报错**，
只会回个大数字。加聚合的语义维度时（`DISTINCT` / `FILTER` / 将来的 `ORDER BY`），
要**逐条**回去检查每个捷径的准入条件 —— 与"有残留谓词就不能下推 join 计数"
是同一个坑，那次也栽过。

④ 与窗口帧那次的 `window_spec_sig` 是同一类：**去重键漏了语义维度**。

另外两处**列收集**漏了谓词（`collect_plan_columns` 与 join 的 `needed` 掩码）⇒
扫描投影把谓词要的列裁掉/换位 ⇒ 执行期按旧索引取列、**越界 panic**
（`len is 1 but the index is 1`）。这与 join 残留谓词当时踩的是同一个坑。

### 顺带处理的两处"新能力会撞上的旧账"

- **窗口函数不走 `try_bind_agg`** ⇒ 聚合 FILTER 一放行，窗口 + FILTER 会从
  `audit_function` 漏进去被静默丢掉 ⇒ 在 `parse_window_fn` 单独拦。
- **`DISTINCT` + `FILTER`** 显式拒：去重改写会换掉输入，谓词引用的列就不在了。

### 验收

`tests/agg_filter.rs`（8 条，全值级）：最初那个错值案例（2 而非 5）、不同谓词不被
去重、全不匹配的组仍出现、NULL 三值语义、各聚合、**三条捷径各自不许绕过**
（每条一个值断言）、溢出路径 == 内存路径、拒绝面。
`sql_silent_drop.rs` 的 FILTER 闸门从"拒绝"改为**断言值**。

## 三之四、批次 4 交付记要：`CREATE TABLE AS SELECT`（**2026-10-17 已落地**，`8a032ae`）

四个批次的收官项。此前报 `table needs at least one column`（把"没实现"说成
"你建表建错了"）；文档一度声称"报错文案已明确"，实测**根本没落地**（F29 家族）。

### 落地形态

**派 schema → 建表 → 跑计划落表**，与"手工两步"（`CREATE TABLE` + `INSERT INTO …
SELECT …`）只差两处：列名/类型由 SELECT 的**输出**推导；**失败回滚**（PG 的 CTAS
是全有全无 —— 留一张空表让人以为"建好了、只是没数据"比报错更坏）。

schema 复用 `insert_select` 那条路（`translate_select_full_with_ctes` +
`exec_builder::build`），取 `plan_output_columns(&plan)` ⇒ **建表之前**就能拿到类型。

### 三处**设计取舍**（都不是默认就对的）

1. **表达式列名 ⇒ 拒 + 指路，不替用户改名。**
   `SELECT g, count(*)` 推导出的名字是 `count(*)`，不是合法表列名（表列名限
   `[A-Za-z_][A-Za-z0-9_]*`）。PG 会改成 `count` —— 那是**另一种静默**（表里出现
   一个用户从没写过的列名，而且改名本身还可能撞车）。本仓拒，并给两条出路
   （`AS n` / 显式列清单），**两条都实测可用**。

2. **JOIN 的限定名要剥表限定**（`a.g` ⇒ `g`，与 PG 一致）。
   本仓 JOIN 场景下列名是**限定名**（右表列必须限定，见 `SQL支持面.md` §二），
   而表列名不允许 `.` ⇒ 不剥的话 `CREATE TABLE j AS SELECT a.g, b.v FROM … JOIN …`
   （最普通的写法之一）必被拒。剥完重名（`SELECT a.g, b.g`）由重复检查报出来。

3. **`CREATE OR REPLACE TABLE … AS SELECT` 仍拒**，且把这条判断放在 CTAS 分支
   **之前** —— 它是最容易让人以为"反正要重建、OR REPLACE 无所谓"的写法。

### 验收里最要紧的一条

回滚那条**特意测了"写了一半才失败"**的形态：类型转换是在 `InsertSink` **落盘
那一步**做的（不在绑定期），所以能造出"表建好了、正在塞数据、塞到一半塞不进去"。
只测"建表前就失败"的话，**回滚分支一行都不会执行** —— 而那正是它存在的理由。
外加**边界**：表已存在时 create 先失败 ⇒ 绝不能走到回滚把旧表删了
（实测旧数据原封不动）。

## 四、给生态的建设表 —— **已独立成契约**

> 这张表**已搬到 [`docs/生态能力契约.md`](生态能力契约.md)**（2026-10-17）。
> 为什么不留在本文：本文是**内部**排期稿（含"为什么排这里"、批次进度），而建设表
> 是**对外**承诺 —— 两者读者不同、变更节奏也不同（表里的状态每次交付都动，内部
> 排期不是）。**同一份内容不抄两遍**，这里只留指针。
>
> 契约里的三条纪律：**状态只增不改** / **协议列不许变**（能力 ⏳→✅ 时"怎么写"
> 一个字都不改）/ **✋ 是承诺不是待办**（附理由与替代写法）。
