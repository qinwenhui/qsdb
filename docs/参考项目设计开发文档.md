\# MiniDB 完整设计开发文档



\---



\## 一、设计目标与约束



\### 1.1 产品定位



MiniDB 是一个\*\*单机、嵌入式、分析型、Arrow-native、Parquet-backed\*\* 的高性能计算引擎。



| 维度 | 决策 |

|------|------|

| 数据模型 | 列式，不可变（Append-only），无 UPDATE/DELETE |

| 事务 | 无（由写入端保证分区级互斥） |

| SQL | 完整 DDL + 受限 DML（SELECT / INSERT），JOIN 仅支持 INNER / LEFT |

| 执行模型 | 拉式迭代（Pull-based Iterator），向量化批处理 |

| 并发模型 | 分区内串行，分区间 rayon 数据并行 |

| 内存模型 | Arrow RecordBatch 贯穿全程，零拷贝为默认 |

| 存储后端 | 本地文件系统 / HDFS（通过 object\_store 抽象） |

| 对外接口 | SQL（门面）+ CLI + HTTP + 嵌入式 API |

| 扩展路径 | SIMD（运行时检测）→ GPU（Vulkan / CUDA feature） |



\### 1.2 性能红线



| 指标 | 目标 |

|------|------|

| 元数据加载（万级分区） | < 50ms（热缓存） |

| 单分区扫描启动延迟 | < 5ms |

| 聚合查询（1 亿行，3 列 group by） | < 2s（单线程），< 500ms（8 线程） |

| 内存基线（空闲） | < 32MB |

| 二进制大小（release） | < 15MB（不含 GPU feature） |

| 元数据操作 | 不依赖任何外部服务，纯本地文件 + 内存 |



\### 1.3 历史教训（Hive Metastore 问题）



你在 Spark + HDFS + HMS 场景遇到的 timeout 问题，根因是：



\- HMS 是\*\*中心化元数据锁服务\*\*，高并发写入时 commit 路径串行

\- 每个写入任务都要 `acquireLock → write → releaseLock`，锁竞争爆炸

\- HMS 的 MySQL 后端在并发 `ALTER PARTITION` 时成为瓶颈



MiniDB 的解法：



> \*\*元数据 = 本地文件 + 内存缓存 + 分区级文件锁（flock），不走任何网络服务。\*\*

\## 三、类型系统规范（重点）



\### 3.1 核心类型定义



MiniDB 定义\*\*独立的逻辑类型系统\*\*，不与 Rust 原生类型绑定。对外格式严格约束，内部执行时再映射到 Arrow / SIMD / GPU 类型。



| 逻辑类型 | 别名 | 存储编码 | Arrow 映射 | 说明 |

|---------|------|---------|-----------|------|

| `BOOLEAN` | `BOOL` | 1 byte (0/1) | `BooleanArray` | |

| `INT8` | `TINYINT` | 1 byte | `Int8Array` | |

| `INT16` | `SMALLINT` | 2 bytes | `Int16Array` | |

| `INT32` | `INT` | 4 bytes | `Int32Array` | |

| `INT64` | `BIGINT` | 8 bytes | `Int64Array` | |

| `FLOAT32` | `FLOAT` | 4 bytes IEEE 754 | `Float32Array` | |

| `FLOAT64` | `DOUBLE` | 8 bytes IEEE 754 | `Float64Array` | |

| `DECIMAL(p,s)` | — | \*\*见 3.2 节\*\* | `Decimal128Array` / `Decimal256Array` | \*\*重点\*\* |

| `STRING` | `VARCHAR(n)` | UTF-8 bytes + length prefix | `StringArray` | 见 3.3 节 |

| `BINARY` | `VARBINARY` | bytes + length prefix | `BinaryArray` | |

| `DATE` | — | INT32 (days since 1970-01-01) | `Date32Array` | 见 3.4 节 |

| `TIME` | — | INT64 (nanoseconds since midnight) | `Time64NanosecondArray` | |

| `TIMESTAMP` | — | INT64 (nanoseconds since epoch) | `TimestampNanosecondArray` | 见 3.4 节 |

| `TIMESTAMP\_TZ` | — | INT64 + timezone metadata | `TimestampNsArray` + tz | |

| `INTERVAL` | — | 12 bytes (months, days, nanos) | `IntervalMonthDayNano` | |

| `ARRAY<T>` | — | Arrow List | `ListArray` | 后续 feature |

| `MAP<K,V>` | — | Arrow Map | `MapArray` | 后续 feature |



\### 3.2 DECIMAL 类型规范（重点）



Decimal 是金融/业务计算的核心，必须严格规范。



\#### 逻辑定义



```

DECIMAL(precision, scale)

```



\- `precision`：总有效数字位数，1 ≤ p ≤ 38

\- `scale`：小数位数，0 ≤ s ≤ p



\#### 存储映射规则



| precision 范围 | 内部存储类型 | Arrow 类型 | 字节数 | 说明 |

|---------------|-------------|-----------|--------|------|

| 1 ≤ p ≤ 9 | `Decimal64` (i64) | `Decimal128Array` (但只用低 32 位有效) | 8 | 高性能路径，无溢出风险 |

| 10 ≤ p ≤ 18 | `Decimal64` (i64) | `Decimal128Array` | 8 | 标准路径 |

| 19 ≤ p ≤ 28 | `Decimal128` (i128) | `Decimal128Array` | 16 | 高精度路径 |

| 29 ≤ p ≤ 38 | `Decimal256` (i256) | `Decimal256Array` | 32 | 超高精度路径 |



\#### 对外格式约束



| 场景 | 格式 |

|------|------|

| SQL 文本输入 | 标准数字字符串，如 `'123456789.12345'` |

| SQL 文本输出 | 格式化字符串，保留 trailing zeros（按 scale），如 `123456789.12345` |

| JSON 输出 | 字符串（避免浮点精度丢失），如 `"123456789.12345"` |

| Arrow IPC / Flight | `Decimal128Array` / `Decimal256Array` |

| Parquet 存储 | `FIXED\_LEN\_BYTE\_ARRAY` (16 bytes for decimal128, 32 for decimal256) 或 `INT64`（p≤18 时） |

| 内部计算 | 见下方 |



\#### 内部计算策略



```

默认路径：i128 (Decimal128)

&#x20; - 聚合 sum：i256 累加（防止溢出）

&#x20; - 比较：直接 i128 cmp

&#x20; - 加减：i128 运算，检查溢出

&#x20; - 乘除：i256 中间结果，再 round 回 i128



SIMD 路径：

&#x20; - 使用 128-bit SIMD 指令（AVX2 的 \_mm\_mul\_epi64 + 移位，或 AVX-512 的 128-bit 整数）

&#x20; - 批量 decimal multiply：4 个 decimal64 并行



GPU 路径：

&#x20; - CUDA：使用 \_\_int128 / cuBLAS 扩展

&#x20; - Vulkan：使用 GL\_EXT\_shader\_integer\_mix + 手动 128-bit 模拟

```



\#### 精度规则



| 运算 | 结果 precision, scale |

|------|---------------------|

| x(p1, s1) + y(p2, s2) | max(p1-s1, p2-s2)+max(s1,s2)+1, max(s1,s2) |

| x(p1, s1) - y(p2, s2) | max(p1-s1, p2-s2)+max(s1,s2)+1, max(s1,s2) |

| x(p1, s1) \* y(p2, s2) | p1+p2, s1+s2 |

| x(p1, s1) / y(p2, s2) | p1+s2+max(s1+s2, 4), max(s1+s2, 4) |

| sum(x) | min(p+10, 38), s |

| avg(x) | min(p+10, 38), max(s, 4) |



\#### 舍入模式



\- 默认：`HALF\_UP`（银行家舍入的替代，业务友好）

\- 可配置：`CEIL` / `FLOOR` / `TRUNCATE`

\- 溢出行为：`ERROR`（默认）或 `SATURATE`



\### 3.3 字符串类型规范



| 类型 | 定义 | 存储 | 说明 |

|------|------|------|------|

| `STRING` | 无长度限制 | UTF-8 bytes | 内部用 Arrow `StringArray`（offset + data） |

| `VARCHAR(n)` | 最大 n 字符 | UTF-8 bytes，写入时校验长度 | n ≤ 65535 时可用 `StringArray`；n > 65535 时标记为 `LARGE\_STRING` |

| `CHAR(n)` | 定长，不足补空格 | 定长 bytes | 内部仍用 `StringArray`，比较时 trim |



\*\*超长字符串（> 2MB 单值）处理：\*\*



\- 不存储在 Parquet data page 中

\- 写入 `overflow/` 目录，Parquet 中存引用 ID

\- 读取时 lazy load（通过 `ExternalRef` 类型）

\- 聚合/分组时只用 hash of string，不加载完整值



\### 3.4 时间类型规范



| 类型 | 存储 | 精度 | 范围 | 时区处理 |

|------|------|------|------|---------|

| `DATE` | INT32 | 天 | 0001-01-01 \~ 9999-12-31 | 无时区 |

| `TIME` | INT64 | 纳秒（since midnight） | 00:00:00.000000000 \~ 23:59:59.999999999 | 无时区 |

| `TIMESTAMP` | INT64 | 纳秒（since 1970-01-01） | 1677-09-21 \~ 2262-04-11 | 可选时区 |

| `TIMESTAMP\_TZ` | INT64 + tz string | 纳秒 | 同上 | 存储时统一转 UTC，查询时按 session tz 转换 |



\#### 时间格式约束



| 场景 | 格式 |

|------|------|

| SQL 输入 | ISO 8601: `2026-10-04T14:30:00.123Z` 或 `2026-10-04 14:30:00` |

| SQL 输出 | `YYYY-MM-DD HH:MM:SS.ssssss` |

| JSON 输出 | ISO 8601 字符串 |

| Parquet 存储 | `TIMESTAMP(isAdjustedToUTC=true, timeUnit=NANOS)` |

| Arrow IPC | `TimestampNanosecondArray` |



\#### 时间计算规则



\- 所有内部计算统一到 \*\*纳秒 INT64\*\*

\- 时区转换：使用 `chrono-tz` 或 `tz-rs`（纯 Rust，无系统依赖）

\- 夏令时：不做自动处理（分析场景不关心 DST），只做固定偏移



\### 3.5 类型系统代码结构



```

types/

├── mod.rs          # Type enum, TypeId

├── logical.rs      # LogicalType, DecimalMeta, VarcharMeta

├── physical.rs     # PhysicalType, 映射到 Arrow DataType

├── compare.rs      # 跨类型比较（decimal vs double 等）

└── serde.rs        # 类型序列化（DDL 文本 ↔ 内部表示）

```

\## 四、元数据管理层设计



\### 4.1 设计原则



| 原则 | 实现 |

|------|------|

| 无外部依赖 | 元数据存本地文件系统，JSON / MessagePack 格式 |

| 内存优先 | 启动加载全部元数据到内存，文件只做持久化 |

| 分区级锁 | 每个分区一个 `.lock` 文件，flock 互斥 |

| 读写分离 | 读不阻塞读，写串行化 |

| 轻量格式 | 不用 Iceberg / HMS，自定义 segment manifest |

| 快速加载 | 二进制格式（MessagePack）+ 内存 mmap（可选） |



\### 4.2 元数据层次结构



```

{db\_root}/

├── \_meta/

│   ├── catalog.msgpack      # 全局 catalog：数据库/表/schema

│   ├── tables/

│   │   ├── {table\_name}/

│   │   │   ├── schema.json  # 表结构（字段/类型/约束）

│   │   │   ├── partitions.msgpack  # 分区列表（只存分区值+文件列表引用）

│   │   │   └── stats.msgpack      # 全局统计（行数/列 min-max 缓存）

│   └── constraints/

│       └── {table\_name}.json      # 唯一约束/范围约束

├── {table\_name}/

│   ├── \_segments/

│   │   ├── segment\_0001.msgpack   # 每个 segment 的文件列表+统计

│   │   ├── segment\_0002.msgpack

│   │   └── ...

│   ├── dt=2026-10-04/

│   │   ├── segment\_0001.parquet

│   │   ├── segment\_0002.parquet

│   │   └── .lock                  # flock 文件

│   └── dt=2026-10-10/

│       └── ...

```

\#### 约束管理



```text

ConstraintMeta

├── table\_name

├── constraints: Vec<Constraint>

│   ├── Constraint::Unique { columns: Vec<String> }

│   │   └── 实现：写入时检查 segment 内 + 内存 hash set

```



\### 4.4 元数据读写流程



\#### 启动加载



```

1\. 读 \_meta/catalog.msgpack → 内存 Catalog

2\. 对每个 table，读 schema.json → TableMeta

3\. 读 partitions.msgpack → 分区列表（只加载分区值，不加载文件详情）

4\. 每个分区的 segment 列表懒加载（第一次查询该分区时才读）

5\. 全局 stats 加载到内存（行数/大小，用于优化器估算）

```



\#### 写入流程



```

1\. 获取分区 .lock（flock，阻塞等待）

2\. 生成 segment\_id（原子递增，存 \_meta/next\_segment\_id）

3\. 写 Parquet 文件到分区目录

4\. 构建 SegmentManifest（含列统计）

5\. 写 \_segments/segment\_{id}.msgpack（原子写：先写 .tmp，再 rename）

6\. 更新内存 Catalog（行数/大小）

7\. 释放锁

```



\#### 查询流程



```

1\. 从内存 Catalog 获取表 schema

2\. 根据 WHERE 条件过滤分区（partition pruning）

3\. 加载目标分区的 segment manifest（如果不在内存）

4\. 根据 column\_stats 过滤 row group（row group pruning）

5\. 返回需要读的文件列表 + row group 列表

```



\### 4.5 性能优化



| 优化 | 方法 |

|------|------|

| 启动速度 | catalog.msgpack 二进制格式，mmap 加载 |

| 查询时元数据 | 分区 manifest 懒加载 + Moka LRU 缓存 |

| 并发读 | 读不加锁，用 ArcSwap 做无锁切换 |

| 写入并发 | 分区级 flock，不同分区完全并行 |

| 统计信息 | 写入时计算 min/max/null\_count，存 manifest |

| Bloom Filter | 高频等值查询列自动建 bloom filter（可选 feature） |

| 元数据压缩 | MessagePack + zstd 压缩（可选） |



\### 4.6 与 HMS 的对比



| 维度 | HMS + Spark | MiniDB |

|------|-------------|--------|

| 元数据锁 | 全局 MySQL 行锁 | 分区级 flock |

| 并发写入 | 串行 commit | 分区并行 |

| 启动依赖 | 需要 HMS 服务 | 无 |

| 网络 IO | 每次操作走 Thrift | 本地文件 |

| 超时风险 | 高（MySQL 瓶颈） | 无（本地） |

| 扩展性 | 加 HMS 实例 | 加磁盘 |

\## 五、存储层设计



\### 5.1 文件格式



| 层 | 格式 | 说明 |

|----|------|------|

| 数据文件 | Parquet | 列式，snappy 或 zstd 压缩 |

| 元数据 | MessagePack | 二进制，比 JSON 快 3-5x |

| 写入锁 | flock | 分区级 |

| 临时文件 | `.tmp` 后缀 + rename | 原子性保证 |



\### 5.2 Parquet 写入参数



| 参数 | 值 | 理由 |

|------|-----|------|

| Row Group Size | 128 MB（按压缩后估算） | 平衡读取并行度和内存 |

| Page Size | 1 MB | 列裁剪粒度 |

| Compression | snappy（默认）/ zstd（可选） | snappy 快，zstd 压缩比高 |

| Dictionary | 对 cardinality < 10000 的列启用 | 减少存储空间 |

| Bloom Filter | 对 WHERE 等值查询列启用 | 加速 point lookup |

| Statistics | 每列 min/max/null\_count | 用于 row group pruning |

| Max Row Group Rows | 1,000,000 | 防止单行过大 |



\### 5.3 目录结构



```

{table}/

├── dt=2026-10-04/

│   ├── segment\_0001.parquet    # 一个 segment 一个文件（或拆分多个）

│   ├── segment\_0002.parquet

│   └── .lock

├── dt=2026-10-10/

│   ├── segment\_0003.parquet

│   └── .lock

└── \_segments/

&#x20;   ├── segment\_0001.msgpack
```

\### 5.5 写入流程详细



```

1\. 客户端提交 Arrow RecordBatch

2\. 按分区字段分组（如果跨分区）

3\. 对每个分区：

&#x20;  a. 获取 .lock

&#x20;  b. 分配 segment\_id

&#x20;  c. 将 RecordBatch 追加到 Parquet writer

&#x20;  d. 收集列统计信息

&#x20;  e. 关闭 Parquet writer

&#x20;  f. 写 segment manifest

&#x20;  g. 更新内存 Catalog

&#x20;  h. 释放 .lock

```



\### 5.6 读取流程详细



```

1\. SQL → 分区过滤条件

2\. 从 Catalog 获取匹配分区列表

3\. 对每个分区加载 segment manifest

4\. 合并所有 segment 的文件列表

5\. 对每个文件：

&#x20;  a. 读 Parquet footer

&#x20;  b. 根据 column\_stats 过滤 row group

&#x20;  c. 根据 projection 选择列

&#x20;  d. 根据 predicate 生成 row group filter

6\. 生成 ParquetExec 列表

7\. 并行执行（rayon）

```

\## 六、执行层设计



\### 6.1 执行模型



```

每个查询 = 一棵 PhysicalPlan 树

每个 PhysicalPlan 节点 = 一个 Executor

Executor::next() → Option<Result<RecordBatch>>



执行方式：拉式（Pull）

\- 顶层调用 next()

\- 逐层向下拉数据

\- 每个 batch 1024\~8192 行

```



\### 6.2 算子清单



| 算子 | 实现 | 说明 |

|------|------|------|

| `ParquetScanExec` | 读 Parquet 文件，列裁剪 + row group 过滤 | 最底层 |

| `FilterExec` | Arrow compute kernels | 向量化 |

| `ProjectExec` | 表达式求值 | 向量化 |

| `HashAggregateExec` | hashbrown hash table | 核心优化点 |

| `SortAggregateExec` | 排序后流式聚合 | 小数据量 / 已排序数据 |

| `SortExec` | 外部排序（超过内存时 spill） | |

| `LimitExec` | 计数截断 | |

| `TopNExec` | 堆 + Limit | ORDER BY ... LIMIT |

| `HashJoinExec` | 构建侧 hash table，probe 侧查表 | |

| `NestedLoopJoinExec` | 小表驱动 | 无等值条件时 |

| `UnionExec` | 多输入合并 | |

| `DistinctExec` | HashDistinct / SortDistinct | |

| `BroadcastExec` | 小表广播到所有线程 | Join 优化 |



\### 6.3 表达式系统



```

PhysicalExpr trait

├── eval(batch: \&RecordBatch) → Result<ArrayRef>



内置实现：

├── ColumnExpr        # 取列

├── LiteralExpr       # 常量

├── BinaryExpr        # + - \* / % 等

├── ComparisonExpr    # > < = != 等

├── CastExpr          # 类型转换

├── ScalarFnExpr      # 标量函数

├── AggregateExpr     # 聚合函数（sum/count/avg/min/max）

└── WindowExpr        # 后续 feature

```



\### 6.4 聚合函数实现



| 函数 | 内部状态 | 说明 |

|------|---------|------|

| `count` | u64 | |

| `sum(int)` | i128 / i256 | 防溢出 |

| `sum(decimal)` | i256 | |

| `avg` | (sum: i256, count: u64) | 最终除法 |

| `min/max` | 对应类型 + Option | |

| `distinct\_count` | HashSet / HyperLogLog | |

| `approx\_percentile` | TDigest | 后续 feature |



\### 6.5 并行策略



```

查询级：单查询内多线程

├── 分区级并行：每个分区一个 rayon task

├── 文件级并行：每个文件一个 task

└── 算子内并行：HashAggregate 分 partition 聚合，最后 merge



写入级：

├── 不同分区：完全并行

├── 同分区：串行（flock）

└── 批量写入：攒批 → 一次写

```

```
&#x20;   ├── SystemAllocator（默认）

&#x20;   ├── JemallocAllocator（feature）
```

\## 七、Feature 扩展设计



\### 7.1 SIMD Feature



```toml

\[features]

simd = \["arrow-simd", "wide"]

simd-avx2 = \["simd", "wide/avx2"]

simd-avx512 = \["simd", "wide/avx512"]

```



| 层次 | SIMD 优化点 |

|------|------------|

| 表达式 | 批量比较（gt/eq/and），wide crate 做 256/512-bit 并行 |

| Hash | 批量 hash 计算（aes-ni / clmul） |

| Decimal | 4x decimal64 并行乘 |

| Filter | 位图操作 SIMD 化 |

| Copy | memcpy 用 SIMD |



\*\*运行时检测\*\*：启动时检测 CPU flag，选择最优实现。



\### 7.2 GPU Feature (Vulkan / CUDA)



```toml

\[features]

gpu-vulkan = \["wgpu", "wgpu-types"]

gpu-cuda = \["cudarc"]

```



\#### 抽象层



```

Device trait

├── cpu: CpuDevice    # 默认，Arrow RecordBatch

├── vulkan: VulkanDevice  # wgpu compute shader

└── cuda: CudaDevice       # CUDA kernel



算子接口：

trait GpuExecutable {

&#x20;   fn supports\_gpu(\&self) -> bool;

&#x20;   fn to\_gpu\_plan(\&self) -> GpuPhysicalPlan;

}

```



\#### GPU 执行模型



```

1\. 数据在 CPU Arrow RecordBatch

2\. 检测是否值得 offload（数据量阈值）

3\. 拷贝到 GPU buffer (wgpu::Buffer / cuda::CudaBuffer)

4\. 执行 GPU kernel（hash join / hash agg / sort）

5\. 结果拷回 CPU（或留在 GPU 给下一个 GPU 算子）

```



\#### 适合 GPU 的算子



| 算子 | GPU 加速比 | 说明 |

|------|-----------|------|

| HashAggregate | 5-20x | 高并行度 |

| HashJoin | 10-50x | build + probe |

| Sort | 3-10x | 基数排序 |

| Filter | 2-5x | 简单谓词 |

| 表达式 eval | 2-8x | 复杂表达式 |



\#### Vulkan vs CUDA 选择



| 维度 | Vulkan | CUDA |

|------|--------|------|

| 跨平台 | ✅ | ❌（NVIDIA only） |

| Rust 生态 | wgpu（成熟） | cudarc（可用） |

| 开发难度 | 中（shader 语言） | 低（C++ kernel） |

| 性能 | 略低 | 最高 |

| 推荐 | 默认 GPU feature | 可选 |

\## 十、关键设计决策总结



| 决策 | 选择 | 理由 |

|------|------|------|

| SQL 引擎 | sqlparser-rs（只解析） | 执行完全自主 |

| 执行模型 | 拉式迭代 + 向量化 | 简单、可控、低延迟 |

| 内存模型 | Arrow RecordBatch | 零拷贝、生态兼容 |

| 存储格式 | Parquet | 成熟、列裁剪、统计 |

| 元数据 | 本地文件 + 内存 | 无外部依赖、无锁竞争 |

| 并发写入 | 分区级 flock | 不同分区并行 |

| 事务 | 无 | Append-only 不需要 |

| Decimal | i128 为主，i256 聚合 | 精度 + 性能平衡 |

| 时间 | 纳秒 INT64 | 统一精度 |

| GPU | feature flag + Device trait | 可选、不增加基线 |

| 对外格式 | 严格约束 | 专业、可预测 |
