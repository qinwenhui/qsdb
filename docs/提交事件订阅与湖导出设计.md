## 一、T2：提交事件钩子 + 订阅端点

### 1.1 内核钩子（照抄 `主备与qsdb-sync设计.md` §4.2 的规格）

```rust
pub struct CommitEvent {
    pub table: String,
    pub partition_values: Vec<Literal>,
    pub generation: u64,
    /// 本次提交**新增**的段（follower 据此直接取文件，免一次 list）
    pub new_segments: Vec<SegmentEntry>,
    pub kind: CommitKind, // Append | Overwrite | Compact | Clear
}
```

挂点：`QsdbOptions.on_commit: Option<Arc<dyn Fn(&CommitEvent) + Send + Sync>>`。
`None` ⇒ 一次 `Option` 判断，**零开销**。

**粒度：逐分区。** `partition_values` 与 `generation` 本来就是分区级的；
一次 `append` 跨 N 个分区 ⇒ **N 个事件**。好处是 follower 的进度可以**按分区**记，
不必整表重来。

**触发点：在 `api.rs` 里、每次 `append_partition`/`overwrite_partition` 成功返回之后。**
选这里而不是 `write.rs` 里，是因为：① 那几处的 `_guard` 是在 `append_partition`
**内部** `drop` 的 ⇒ 在 `api.rs` 里触发**天然在锁外**（设计稿明确要求"锁外"）；
② `write.rs` 是自由函数（只收 `store`），把钩子穿进去要动一串签名，没必要。

### 1.2 ★ 最要紧的一条：**钩子是加速器，不是真相来源**

钩子**可能丢事件**，而且必须容忍：

| 情形 | 后果 | 为什么这样定 |
|---|---|---|
| 回调 **panic** | 捕获并丢弃 | ⚠️ 反过来（让它传播）**更坏**：数据**已经提交了**，而调用方收到一个错误 ⇒ 它会以为写失败去重试/回滚 ⇒ 一次"静默改语义"。**提交成功就必须报成功。** |
| 回调**慢** | 拖慢写入 | 文档写明"回调要快"；真要 IO 就自己丢队列（这是调用方的事） |
| 服务端**重启** | 事件缓冲没了 | 订阅端点**报错说"游标太旧"**，而不是假装连续（见 §1.4） |

⇒ 因此**订阅端点必须带游标（`since`）**，消费方可据此**补齐**；消费方也**可以**保留
一个慢轮询当兜底。**任何"正确性依赖钩子必达"的设计都是错的。**

### 1.3 订阅端点（用户拍板：订阅端点，不做 server 内嵌 follower）

```
GET /api/v1/watch?since=<cursor>&wait=<secs>
```

- **长轮询**（不是 SSE 流）：有事件**立刻**返回，没有就挂到 `wait`（默认 25s、上限 60s）
  再回空。**为什么先做长轮询而不是流式**：交付同样的毫秒级延迟，但**没有**流式解析、
  keep-alive、半开连接检测这些要处理的边角；将来要加流式，那是**新端点**（契约允许
  "只增不改"），`since` 游标与事件 schema 这两个真正要稳定的东西**一个字不用变**。
- 响应（新行分隔的 JSON 数组，或单对象）：
  ```json
  {"events": [ {"table":"t","partition":["2026-01-01"],"generation":7,
                "kind":"Append","segments":[{"path":"…","rows":65536,"bytes":…}]} ],
   "next": 42, "more": false}
  ```
- `more=true` ⇒ 还有积压，客户端**立刻**用新 `next` 再拉（别等下次 `wait`）。
- 与 `/api/v1/query` 同一套鉴权（token → 角色）；**reader 角色即可订阅**（它只读事件）。

### 1.4 游标与"太旧了"

- 事件缓冲是**进程内存**里的环形缓冲（容量可配）；游标 = 单调递增的事件序号。
- `since` 早于缓冲区最旧事件、或服务端重启过 ⇒ **显式报错**
  （`CURSOR_TOO_OLD`，409/带提示），**绝不**假装连续：调用方据此走一次全量/按
  `generation` 对账——这正是它今天轮询 `partition_stats` 时本来就会做的事。
- 这是本仓纪律的直接应用：**宁可报错，也不给一条看起来连续的假流。**

## 二、F9：湖导出（**出得去 + 读得进**，用户拍板一起做）

### 2.1 为什么"两半一起"才闭环

他们的 sink 按 **Spark 惯例**写：分区列**只在目录名**、不在数据文件里。
于是：我们导出的湖，**我们自己读不回来**（`read_parquet` 没有 hive 目录语义 ⇒ 分区列丢失）。
只做"出"= 单向能出不能进，湖互操作**没闭环**（他们自己也是这么说的）。

### 2.2 出：`COPY … TO`

```sql
COPY (SELECT * FROM orders)
  TO 's3://bucket/lake/orders'
  (FORMAT PARQUET, PARTITION_BY (dt, region));
```

- **为什么用 `COPY … TO` 而不是 `write_parquet(...)` 函数**：DuckDB / Spark / Hive 都是
  `COPY` 形状，**这是唯一对标物**（本仓的性能基准也只跟 DuckDB 比）；而且它是**语句**
  不是表达式 ⇒ 不跟 `SELECT` 的求值模型打架。
- 布局与他们一致：`<root>/dt=2026-01-01/region=cn/part-00000.parquet` + `_common_metadata`。
  **分区列不进数据文件**（同 Spark 惯例，理由见他们 `sink-parquet` 头注释：
  pyarrow/Spark 读 hive 数据集时同名会冲突）。
- 目标路径走**本仓的 `Store`**（本地 / S3 / HDFS 三后端已有）⇒ 导到对象存储是原生支持的，
  不用各工具自己写 writer。
- ★ **顺带把导出的性能差距修了**：基准文档已把它归类为"能力缺口"（`真机基准对账.md`
  §831-842："我们没有导出原语…拿到就是 arrow-rs 单线程的水平"）。写入**按分区并行**
  （P0② 的导出侧，此前只接了导入侧）⇒ 3.5–4.6× 那两格的正解在这里，不在调参。

### 2.3 读：`read_parquet` 的 hive 目录语义（= F12）

```sql
SELECT * FROM read_parquet('lake/orders/**/*.parquet', hive_partitioning => true);
```

- 发现期扫目录、把 `k=v` 路径段**组装成分区列常量**（**零文件读开销**），与分区裁剪天然协同。
- 显式开关优先；**路径里含 `k=v` 段时是否自动启用**——按他们建议的"或自动启用"，
  但要**显式写在文档里**（自动行为必须有据可查，不能靠猜）。
- 与分区裁剪协同：`WHERE dt = '2026-01-01'` 应能**只扫对应目录**（这是湖读性能的全部意义）。

## 三、落地顺序（每步自成闭环 + 过闸门）

| # | 内容 | 验收 |
|---|---|---|
| **A1** | `CommitEvent` + `on_commit` 钩子 + 各提交点触发（锁外、`None` 零开销） | 单测：append/overwrite/compact/clear 各触发一次；回调 panic **不影响**写入返回成功；`None` 时不进分支 |
| **A2** | 订阅端点 `GET /api/v1/watch`（长轮询 + 游标 + `more` + `CURSOR_TOO_OLD`） | HTTP 契约测：事件能到手、游标连续、太旧显式报错、reader 角色可用 |
| **A3** | `COPY … TO`（parquet + hive 布局 + 分区列不入文件 + 并行写） | 值级：导出的目录结构与文件内容；**用 `read_parquet` 读回来逐值一致**；`.14` 复测导出耗时 |
| **A4** | `read_parquet` hive 目录语义 + 与分区裁剪协同 | 值级：分区列正确重建；`WHERE dt=…` 只扫对应目录（断言读的文件数） |

**A1/A2 给 qsdb-sync，A3/A4 给他们的 sink-parquet 反哺**；四步都做完，湖互操作才闭环。

## 四、明确不做（写清楚，别让人等）

| 不做 | 理由 |
|---|---|
| **`qsdb server --follow <上游>`**（server 内嵌 follower） | 用户拍板走订阅端点。理由也充分：同步工具是**独立仓库**，`qsdb-cli` 不依赖它 ⇒ 要么把两个 repo 耦合，要么在 server 里重写一份 follower（两处维护）。订阅端点让**他们**的进程仍是唯一实现 |
| 钩子的**持久化**事件日志 | 事件是**加速器**（§1.2）。持久化等于把内核变成 WAL/CDC 引擎 —— 那是另一个产品，与"低占用"定位冲突。丢事件由游标 + 对账兜 |
| 流式（SSE）订阅端点 | 长轮询先交付同样的延迟；要加时是**新端点**，游标与事件 schema 不用变 |
