## 二、本批做的（2026-10-13，"批次 3"）

| 改动 | 收益（实测） |
|---|---|
| **TopN 接线 + 有界缓冲**：`Limit{Sort}` 把 n 交给 `SortExec`（此前恒传 `None`），带 limit 时缓冲攒到 `8n+4096` 行就排序截断 | `order_topn`（3M 行）**0.0975s → 0.0230s（4.2×）**；内存从 O(输入) 降到 O(n) |
| **路由免分配**：`to_sql_string()`（每行每列一次 `format!`，字符串键还要整串 `replace`）→ **规范字节编码**（`enc_literal`/`enc_value` 两侧逐字节等价，类型等价性由单测逐类型钉住） | `spill_group_by` **0.686s → 0.582s（1.18×）**，且离散度 **88% → 4%**；`spill_distinct` ~1.1× |
| `SortExec` 溢出目录 → `ctx.spill_base()` | 全仓最后一个没走配置目录的溢出点（此前落系统临时目录） |
| **顺带发现并修掉两个静默错误**（不属清单，但比优化更值钱） | 见 §四 |

## 三、值得排期（收益明确、且不违红线）

| 项 | 做法 | 预期 |
|---|---|---|
| **聚合的 batch 内去重**（清单 4.3） | 一个 batch 内先按 key 局部合并再入表——`g = i % 200k` 这类高重复键域下，入表次数可降一个量级 | group by 热点直接受益 |
| **Hash probe 预取**（清单 5.2/11） | 自建 `I64Map` 上做 linear probing + 软预取（`cfg(target_arch)` 内联汇编/`_mm_prefetch`，无新依赖） | join probe 是大头，cache miss 是主因 |
| **排序键为整数时用 radix sort**（清单 6） | 单/多整数键走基数排序（arrow 的 lexsort 是通用比较排序） | 大表排序 2-3x 量级（需实测） |
| **归并输出流式化** | `SortExec` 现在把归并结果攒成 `Vec<RecordBatch>` 再 concat（二次膨胀），改成逐批吐 | 内存峰值 |
| **join 探测侧流式取回** | probe 是流着过哈希表的，改 `for_each_partition`（同 P3 的聚合收尾） | 省一个分区的驻留 |
| **`approx_count_distinct`（HLL）** | 手写 HLL（~100 行，零依赖）作为**显式函数**提供，绝不悄悄替换精确 `count(distinct)` | 大基数去重内存 O(1) |

## 四、本批发现的两个静默错误（比 §三 的优化更优先）

1. **列裁剪 × ORDER BY 把排序键的索引空间搞混**（`exec_builder.rs::rewrite_plan`）：
   排序键 idx 是**输入自身的输出序**，却被拿去过"表列序 → 投影序"的映射 →
   `SELECT v, w FROM t ORDER BY v, w`（t 有 g,v,w）**静默排错**（并列不按第二键排，
   无任何报错）。修复：Sort 的键不重写（并注释两个索引空间的区别）。
2. **隐藏排序列出网**（`translate.rs`）：ORDER BY 引用未投影列时追加的 `__sort_N`
   没被收回 → `SELECT v FROM t ORDER BY w` 给客户端回**两列**。对按列数/列名解析的
   客户端（JDBC…）是凭据错位。修复：Sort 之上补一层"收回客户端列"的投影。

回归测试：`tests/order_by_prune.rs`（3 例，**已用"把 bug 注回去"验证会红**）、
`tests/topn.rs`（4 例）。注：这两个 bug 是写 TopN 用例时暴露的——**用例要按"能区分
对错"构造**（并列值 + 列数断言），否则排序错了也看不出来。

## 五、明确不做（附理由，避免以后重复讨论）

| 清单条目 | 为什么不做 |
|---|---|
| 表达式/谓词 **JIT（cranelift / dynasm）** | 引重依赖 + 平台相关（本项目要跨 Windows/Linux 嵌入）；收益在"解释执行"的基线才显著，我们是 arrow kernel 向量化基线 |
| **`std::simd` / `packed_simd` / `wide`** | nightly 或新依赖；arrow kernel 内部已有 SIMD，自写只在个别热点有增量 |
| **io_uring / O_DIRECT** | Linux 专属 + 与"嵌入式、跨平台"定位冲突；远端走 range GET，本地走 page cache 已够 |
| **NUMA / CPU pinning / core 绑核** | 宿主环境不可控（嵌入式库不该改宿主线程亲和性）；留给部署层 |
| **`hashbrown` / `ahash` / `indexmap` 替换标准库** | 新依赖；且我们的键路径是自建 `I64Map`/arena，本就不吃 `SipHash` |
| **HyperLogLog 默认替换精确 distinct** | **语义降级不能默认**——错答案不能因为"省内存"就给出去；只能作为显式函数（见 §三） |
| **arena allocator 每算子一个（bumpalo）** | 依赖 + 生命周期重构大；现状"批级 `Arc` 释放 + SoA 列式 arena"已无碎片大头 |
| **替换选择（replacement selection）生成变长 run** | 收益是"run 更长、归并轮数更少"，但实现复杂度高；当前 k 路归并已是单轮 |
| **loser tree 替代堆做 k 路归并** | 常数因子优化（log k 比较 → 更少），等排序实测成瓶颈再说 |
| **分布式 Top-N / 多机** | 不在单机嵌入式产品的范围内 |
