# 内存预算与溢出设计

> 版本：v0.2（2026-10-13）· 状态：**P0 已落地**（§六 分期表；现状均以代码为准，逐条附 `文件:行号`）
> 目标读者：内核实现者、部署方（要一个可承诺的内存上界）、驱动作者（新增一个错误码）

---

## 一、要立的承诺（先定不变量，再谈机制）

**核心不变量 I1**：进程内**可回收内存**有一个硬上界，
超出时表现为「**拒绝某个查询**」，而不是 OOM、不是拖垮进程、不是换页反噬。

拆成三条可测的承诺：

| # | 承诺 | 怎么测 |
|---|---|---|
| **C1** | 执行内存（物化算子占用）≤ 全局预算 | 预算 512MB 下并发跑 4 个各需 1GB 的 group by：全部被拒或溢出，RSS 不越界 |
| **C2** | 缓存（热数据/远端段）可被执行内存**挤兑到 0** | 缓存填满后跑一个吃满预算的查询：查询完成，缓存被清 |
| **C3** | 溢出只改「完成 vs 拒绝」的边界，**不改结果** | 同一查询在 `limit=1B` 与 `limit=∞` 下结果集逐值相同 |

**非目标**（明确不承诺，避免虚假安全感）：
- 不承诺 RSS 字节级精确——Arrow/parquet 内部缓冲、分配器碎片、栈、线程栈不计入；
- 不自造分配器、不接管 `malloc`（与「最小依赖、零虚调用」的项目惯例冲突）；
- 不做「跨进程」预算（预算的宿主是**一个 `Qsdb` 句柄**；server 单句柄 = 进程级）。

### 2.1 记账面：6 处有账，5 处没账

> CTE 那行是**最刺眼的一条**：`benign()` 让整个 CTE 子计划（含它下面的所有算子）
> 既不吃内存闸、也不吃超时与取消——**三条隔离全部绕过**。

### 2.2 记账语义本身有缺陷

`QueryContext::charge_memory`（`query.rs:78-91`）是「先加后比」：

```rust
let used = self.memory_used.fetch_add(bytes, Relaxed) + bytes;   // 先加
if used > limit { return Err(QueryMemoryLimit) }                  // 后比，且**不回滚**
```

三个后果：
1. **失败不回滚**——超限那次增量留在账上（`memory_used()` 是 `GET /api/v1/queries` 对外回显的值，会被污染）；
2. **没有配额预留（reservation）语义**——「记账」与「实际持有」靠人工配对 `charge`/`release`，6 处里 `HashAggExec` 就**只记不还**（`mod.rs:864` 无配套 release），账只增不减；
3. **无全局账本**——每条查询一个 `QueryContext`（`api.rs:774`），互相不可见；`QsdbRuntime` 只有 timeout / memory_limit 两个原子（`api.rs:200-202`）。于是上界 = `per_query_limit × 并发数`（4GB × 16 = 64GB，见 `configuration.md:128` 的自我交底）。

### 2.3 记账口径低估（账要记在放大发生的地方）

- **聚合分片放大**：并行聚合起 `clamp(1,4)` 个分片（`sql/exec_builder.rs:1319/1341`），**每分片各建一份完整 `GroupTable`**（`Vec<GroupTable>`，`exec_builder.rs:1018-1026`）再 merge。实测 1M 组 ≈ 32MB/表 → **真实占用 ≈ 4× 单表**。而 `HashAggExec` 只按 `输入批/2` 记一次 → **双重低估**（既没算放大，`/2` 也是拍的）。
- **扫描在途批不计**：`ParScanExec` 用有界通道 `sync_channel(threads*2)`（`par_scan.rs:32`，`threads ≤ 16`）背压，但通道里的批由 `Arc` 持有、不进任何账。宽表下这批内存不小（32 批 × 批大小）。
- **缓存与执行内存互不知情**：`SegmentCache` 自带 `scan_cache_bytes` 预算与 LRU（`cache.rs:50-54`），是唯一跨查询共享的内存结构；它与执行内存**抢同一份 RSS**，但两者之间没有任何协调。缓存「驱逐后仍在途被查询持有」的批由 `Arc` 兜住、**不计入 used**（`cache.rs:143-159`），所以缓存自己的预算也不是硬上界。

### 2.4 溢出：只有排序，机件可复用

`exec/spill.rs`（482 行）**已实现且被测试覆盖**（`crates/qsdb/tests/session_isolation.rs:96-118` 的「1KB 上限 ORDER BY 落盘完成」）：

| 机件 | 位置 | 可复用性 |
|---|---|---|
| `SpillDir`（独立临时目录 + `Drop` 清理） | `spill.rs:30-59` | 目录策略要改（见 §五） |
| `write_sorted_run`（批内 lexsort → zstd(1) parquet run） | `spill.rs:66-90` | 通用（任何「有序 run」都行） |
| `RunMerger`（k 路归并，类型化单元格比较 + pg NULL 序） | `spill.rs:342-482` | 通用 |
| `cmp_cell`（Int/Date/Timestamp/F32/64/Utf8/Bool/Decimal） | `spill.rs:198-283` | 通用（**其余类型视作相等——这是溢出路径的正确性缺口**） |

两个现有边界：
- **归并输出不流式**：`SortExec::collect_all` 把全部输出批收进 `outs: Vec<RecordBatch>`（`mod.rs:629-632`，注释自陈「流式化留待后续」）→ 溢出之后内存可能**二次膨胀**；
- **溢出目录在系统 temp**（`spill.rs:38` `std::env::temp_dir()`）：不可配、不随库、崩溃残留不清理；
- **TopN 未接线**：`SortExec` 有 `limit` 字段并下传 `lexsort_to_indices(..., limit)`（`mod.rs:689`），但 SQL 构建路径恒传 `None`（`exec_builder.rs:501-506`）→ **SQL 层 TopN 目前等于全量物化**。

## 三、模型：一个账本，三类租户

### 3.1 结构

新增 `crates/qsdb/src/memory.rs`（贴合项目惯例：单文件、无新依赖、enum 派发）：

```rust
pub struct MemoryPool {                 // 每个 Qsdb 句柄一份，Arc 共享
    budget: u64,                        // 0 = 不限
    exec: AtomicU64,                    // 执行侧已保留
    cache: AtomicU64,                   // 缓存侧已用（可被挤兑）
    yielders: Vec<Yielder>,             // 可挤兑者（enum 派发，见 3.3）
}

pub struct Reservation {                // RAII：Drop 即归还
    pool: Arc<MemoryPool>,
    bytes: u64,
    _query: Arc<QueryContext>,          // 同时递减每查询账
}
```

- `QueryContext` 新增 `pool: Option<Arc<MemoryPool>>` + 保留自己的 `memory_limit`
  （= **每查询配额**，语义不变）。
- **准入只有一个入口**：`pool.try_reserve(bytes, &ctx) -> Result<Reservation>`。
  删掉 `charge_memory` / `release_memory` 这对手工 API——
  **「忘还」在类型上不可能**（现有 6 处手工配对已有 1 处忘还，见 §2.2）。这是减法。

### 3.2 准入顺序（一次 `try_reserve` 内的三段）

```
① 每查询配额：  ctx.used + bytes > ctx.limit        → Err(QUERY_MEMORY_LIMIT)   [400, 不可重试]
② 挤兑缓存：    exec + bytes + cache > budget        → 令 yielders 释放足够字节（可到 0）后重试
③ 全局仍不足：  → 交回算子：有溢出能力则溢出；无 → Err(MEMORY_PRESSURE)         [503, 可退避重试]
```

**为什么③是拒绝而不是排队**：与既有闸门哲学一致（「闸门的职责是拒绝，不是缓冲」）；
排队会引入「持内存者等释放者」的死锁面与公平性/优先级问题，收益只是把一次明确的
拒绝换成一次不确定的等待。给客户端的救济是**码**：`503 + retry=yes` 精确表达
「此刻内存吃紧，退避重试有意义」——这正是「别的查询跑完就好了」的正确语义。

**为什么②在③之前**：缓存是**纯缓存**（丢了大不了重算），执行内存是**在算的东西**。
压力下先丢缓存、再谈拒绝，与「低占用」定位一致。

### 3.3 挤兑接口：enum 派发（不用 trait object）

```rust
enum Yielder {                          // 可挤兑的内存持有者
    SegmentCache(Arc<SegmentCache>),    // 解码后批 LRU
    FileCache(Arc<FileCache>),          // 远端段文件磁盘缓存（不占内存，留位）
}
impl Yielder { fn yield_bytes(&self, want: u64) -> u64 { /* 驱逐至多 want，返回实际可释放量 */ } }
```

- `SegmentCache` 增加 `evict_bytes(want) -> u64`（沿 LRU 摘索引；**在途被引用的批摘了也不释放**，故返回「索引侧可释放量」，与 `cache_used` 记账保持同一口径）。
- **只挤到够用**，不一挤到底：避免「一个查询把热缓存全清了、下一个查询全冷读」的抖动放大（`configuration.md:136` 记的就是这个现象的反面）。

### 3.4 记账口径：记在放大发生的地方

| 算子 | 记什么（保留字节） |
|---|---|
| `HashAggExec` / `DistinctExec` | `GroupTable` 的**实际容量**（key arena + 状态 SoA + 槽数组，`agg.rs:345-369`），**每分片各记各的**；随增长**增量预留** |
| `HashJoinExec` build | build 侧 concat 后实际字节 + 键索引 |
| `CrossJoinExec` | 物化的右表单批 |
| `SortExec` | 输入 chunk 累积（现状即可），归并输出流式化后按窗口记 |
| `WindowExec` / `UdafAggExec` | 输入物化批 |
| `SetOpExec` / `JoinCountExec` / semi-anti 存在集 | 集合/计数 map 的实际容量 |
| CTE 物化 | 批缓存字节，**用真 `ctx`**（替换 `benign()`，`sql/mod.rs:431`） |
| 扫描在途批 | §七 残留项：P0 不逐批记，改为有界化 |

**成本约束**：记账点是**批边界**（每批一次 Relaxed 原子加/减），不是每行；
全局准入按**块预留**（≥ 一个批的估算字节，如 64KB~1MB 粒度）摊薄 CAS 争用。
必须落进零回退 gate 的 ±5% 噪声带内（gate 见 §六）。

## 四、溢出

### 4.1 复用与抽象

把 `spill.rs` 现有的「有序 run + k 路归并」抽成两层：
- **run 层**（已有）：写 run / 读 run / 归并；
- **分区层**（新增）：`PartitionedSpill { buckets: Vec<RunWriter> }`——按 `hash(key) % P` 分桶，
  桶满即落盘。P 按预算与输入估算自适应。

### 4.2 分算子的溢出策略（按落地顺序）

| 序 | 算子 | 策略 | 备注 |
|---|---|---|---|
| P0 | `SortExec` | 已有；补 TopN 接线（`limit` 恒 `None` 的遗留） | 顺带把归并输出流式化 |
| P1 ✅ | `HashAgg` / `Distinct` | 按 group key **分区** → 分区缓冲超界落盘 → 逐分区读回**分区内**聚合（`exec/agg_spill.rs`） | 走 GroupTable 的 ingest/merge；`SetOp` 留 P1.5 |
| P2 ✅ **已落地 2026-10-13** | `HashJoin` build（**INNER / LEFT OUTER**） | **分区块 hash join**：两侧按 join key 分区落盘 → 逐分区 build+probe。路由口径 = `encode_join_key`（**与 join 索引同源**，故同键必然同分区、分区内连接即完整）；probe 侧必须落盘一次（它是流式的，得能按分区重放） | 单分区仍超（**键倾斜**）→ 如实报 `MEMORY_PRESSURE`，**不递归再切分**；**不覆盖** semi/anti（只存键集、体量小一个量级）与非等值 join（无键可分区）。验收：`crates/qsdb/tests/join_spill.rs`（3 例） |
| P3 | `Window` | 按 `PARTITION BY` 键溢出（天然可切分） | |

**溢出正确性不变量**：溢出路径与内存路径**逐值相同**——含 NULL 序、Decimal 精度、
类型化比较。现存缺口：`cmp_cell` 对未列举类型视作相等（`spill.rs:198-283`），
溢出路径遇到这类类型**必须显式报错**（`UNSUPPORTED`）而不是给出错序。

### 4.3 溢出目录

- 新增 `--spill-dir` / `QsdbOptions.spill_dir`，默认 `<db_root>/_spill`
  （随库、与数据同盘、`gc()` 可清）；
- `read_only` 或远端库（库根不可写）→ 回落系统 temp；两者都不可用 → 明确报错；
- **崩溃残留清理**：`open` 时清 `_spill/*`（对齐 staging 的崩溃恢复姿势）；
- 溢出字节**不计入内存预算**（已落盘），但溢出 I/O 的批缓冲（8192 行）计入。

## 五、配置与观测

| 面 | 新增 | 默认 | 说明 |
|---|---|---|---|
| `QsdbOptions.memory_budget_bytes` | ✅ | `None`（不限） | 嵌入方自控（与 `query_memory_limit_bytes` 同惯例） |
| server `--memory-budget-mb` | ✅ | **4096**（4GB） | 与单查询默认同量级；小机器显式调小。**这是 C1 承诺的落点** |
| `--spill-dir` | ✅ | `<root>/_spill` | §4.3 |
| `--max-concurrent-queries` | 语义变更 | **16 → 0（不限）** | 见下 |
| `GET /api/v1/config` | `memoryBudgetBytes` / `memoryUsedBytes` / `cacheUsedBytes` | | 运行期可查 |
| `GET /metrics` | `qsdb_memory_used_bytes{pool=exec\|cache}`、`qsdb_memory_budget_bytes`、`qsdb_queries_rejected_total{reason}` | | 告警用 |

**`--max-concurrent-queries` 的重新定位**：它当初被定为 16，是因为「它是**唯一**的系统级
内存上界」（`configuration.md:125` 自陈的过渡值）。有了真预算之后，它退化为**纯并发策略**
（过载保护/公平性），不再承担内存职责 → 默认回到 `0`（不限），内存交给预算管。
**这是一处行为变更，在 P0 落地时一并切换**。

### 新增错误码（三类拒绝必须分得开）

对齐刚落地的「两个 503 拆分」的做法：

| 码 | HTTP | retry | 触发 | 客户端动作 |
|---|---|---|---|---|
| `QUERY_MEMORY_LIMIT` | 400 | no | 查询超**自己的配额** | 改查询或调配额 |
| `MEMORY_PRESSURE`（**新增**） | 503 | **yes** | 全局预算耗尽（多为他人占用） | **退避重试** |
| `TOO_MANY_QUERIES` | 503 | yes | 并发条数满 | 退避重试 |

SQLState 建议 `53000`（insufficient_resources）；`error-codes.md` 加一行即可
（只增不改政策允许，防漂移测试会强制文档同步）。

| **P3** | 归并流式化 + `spill_dir`/残留清理 + TopN 接线 + Window 溢出 | 1-2 天 | 溢出查询的峰值 RSS ≤ 预算（消除二次膨胀） |

## 七、残留与风险（明确不承诺的部分）

**P0 之后仍不记账的内存**（诚实交底）：
- **扫描在途批**：`ParScanExec` 通道 `threads*2` 批（`par_scan.rs:32`）+ 算子间在途批。
  占用上界 = `并行度 × (通道容量+算子缓冲) × 批字节`，由**批大小**决定。
  收敛手段（择一，P0 后定）：① 显式上界公式写进文档 + 提供 `--batch-rows` 收紧；
  ② 给批加 RAII 包装（`TrackedBatch`）逐批记账（侵入大，但上界才真）。
- **WriteBuffer**（池③）：`flush_batches=64` / `flush_bytes=128MB`（`write_buffer.rs:25-36`）
  自带上界，**不纳入**全局预算（写路径与读路径同时打满时总量仍超预算——文档写明）。

**风险**：
1. **组表分片放大 4×**：记账若按「合并后」记，C1 直接失效——必须**按分片实记**；
2. **挤兑抖动**：缓存被挤空后热查询变冷查询（`configuration.md:136` 的现象）→
   只挤到够用 + 挤兑量记入指标，可观测；
3. **RAII 化触碰所有物化算子的状态结构**（每个算子加一个 `Option<Reservation>` 字段）：
   改动面广但机械。P0 只做「记账 + 准入」，**不动物化结构本身**，缩小一次改动的爆炸半径；
4. **`PanicWhileHolding`**：`Reservation` 的 `Drop` 必须在 unwind 下也归还
   （项目已恢复 unwind + `catch_unwind` 隔离，`query.rs:111-120`）——`Drop` 天然满足，
   但**测试要覆盖**「算子 panic 后预算被归还、后续查询仍可跑」。
