# 多库 · 访问控制 · 会话 —— 设计规范（2026-10-18，第十六批设计稿）

> **缘起**：server 面要给多个客户端/生态工具用（qsdb-jdbc、qsdb-odbc、qsdb-sync），
> 三个缺口被点名：**没有会话概念**、**只有一个库**（用户需要"库 × 用户 × 库级权限"）、
> **高并发从未实测**。本文一次把概念模型定稿，再给分期落地。
>
> **纪律**：抽象贴合 QSDB 风格——enum 派发、最小依赖、减法优先、零回退；
> 服务端多租户语义**全部落在 qsdb-cli（server 面），内核不动**（嵌入模式由宿主自治，
> 这是 M7-A 以来的既定边界）。
> 实测数据出处：`docs/真机基准对账.md` §二点查探针 + 本文 §七。

---

## 一、现状盘点（2026-10-18）

| 域 | 已有 | 缺口 |
|---|---|---|
| 用户 | `_catalog/users.json`，三角色 **Admin/Writer/Reader**（enum 派发，无 RBAC 表）；SHA-256(password‖salt) 迭代哈希；HTTP Basic → Bearer token（登录签发、进程内存表 `token → Role`）；`user export/import` 管理命令；`--token` 保留为超级凭证 | **角色是全局的**——一个用户一个角色，管到所有表；无"某用户对某库只读" |
| 会话 | `GET /api/v1/queries`（在跑查询：id/sql/elapsed/memory/cancelled）+ `POST /api/v1/queries/{id}/cancel`（J11）+ 并发闸（超限 503 `TOO_MANY_QUERIES`） | **没有会话对象**：HTTP 无状态，空闲连接不可见；token 只是 `token→Role`（无连接时间/活跃度/归属/统计）；踢客户端无从谈起 |
| 库 | `Qsdb::open(目录)` = 一个库；catalog 在 `<库根>/_catalog` | **server 一次只开一个库**；无 `db.table` 限定名、无 SHOW DATABASES |
| 配置 | `docs/configuration.md` 五层清单（启动期/运行期/查询级/表级/服务器级）+ `PUT /api/v1/config` 热更 | 会话级/用户级配额留位；19 个 `QSDB_*` 调试开关未收编成文；个别条目过期（并发闸默认值，已修） |
| 并发 | `--max-concurrent-queries` 默认 **0（不限）**；内存三角：全局预算 4GB × 单查询 4GB × 并发条数 | **从未压测过**（本设计稿附首轮实测，§七） |

## 二、概念模型（目标态，一张图定稿）

```
Instance（一个 qsdb server 进程）
 ├─ Mount   { name: "sales",   handle: Qsdb(目录A) }     ← 多库 = 多次挂载
 ├─ Mount   { name: "settle",  handle: Qsdb(目录B) }
 ├─ User    { name, credential, grants: { "settle": Reader, "*": None } }
 ├─ Session { id, user, token, client, created_at, last_active_at,
 │            default_db, running: [query_id…], stats }
 └─ Query   { query_id, session_id, ctx(QueryContext), sql }   ← 现有注册表 + 归属
```

判定规则（每个认证请求）：

```
token → Session（无效即 401）
    → 请求目标库 = 显式指定 ?? session.default_db
    → role = user.grants[目标库] ?? user.grants["*"] ?? None
        → None ⇒ 403 NO_SUCH_GRANT（文案区分"库不存在"与"无权限"）
    → role.can_* 闸门（现有 Role::can_write/is_admin 原样复用）
```

**内核零改动**：Role/UserStore/QueryContext/并发闸/预算全部原样；新增的都是
server 面（qsdb-cli）的编排层。嵌入模式不引入上述任何概念（宿主自治）。

## 三、会话设计

### 3.1 Session 对象（qsdb-cli 层新增）

```rust
pub struct Session {
    pub id: String,              // 服务端生成（uuid），与 token 1:1
    pub user: String,            // 用户名（审计与展示；判定看 grants 不看它）
    pub role_at_login: Role,     // 快照展示用；**判定始终现查 grants**
    pub client: ClientInfo,      // ip:port + User-Agent（登录时定格）
    pub created_at: Instant,
    pub last_active_at: AtomicU64, // 每个认证请求 touch
    pub default_db: Mutex<String>,  // 会话默认库（USE 的落点），初始 "default"
    pub running: Mutex<Vec<String>>, // 在跑的 query_id（queries 注册表反查同源）
    pub stats: SessionStats,     // queries_total / rows_written / bytes_read 累计
}
```

- `AppState.tokens: HashMap<token, Role>` **升级为** `HashMap<token, Session>`
  ——同一把锁、同一处签发/吊销，改动面最小。
- **每个认证请求 touch `last_active_at`**（一次 `store(Relaxed)`，无锁竞争面）。
- 查询注册表 `queries: HashMap<query_id, QueryEntry>` 增加 `session_id` 字段
  ——`GET /api/v1/queries` 每行多回显 `sessionId`，会话踢人靠它反查。

> **M-A 落地定案（2026-10-18，对上稿的三处细化）**：
> ① `running` **不冗余存进 Session**——查询注册表是唯一真源，`GET /sessions`
>   反查同源（原稿"注册表反查同源"的落实），防两处记账漂移；
> ② 会话 token 统一 **`sess-` 前缀**——"带此前缀却不在表"即可判定吊销，
>   不需要 tombstone 集合；配新码 401 `SESSION_REVOKED`（码表 24→25，
>   `docs/error-codes.md` 同步，与 `UNAUTHORIZED` 的区分：这把 token 永远不会
>   好，别重试，重登）；
> ③ 登录响应回显 `{token, sessionId, role, defaultDb}`；`default_db` 校验按
>   `AppState.mounts` 白名单（M-A 恒 `["default"]`，M-B 由 `--mount` 填充）。
>   Basic / 超级 token / 开放模式**不建会话**（不可踢、无默认库可设）。

### 3.2 端点（REST 面定稿）

| 端点 | 语义 | 权限 |
|---|---|---|
| `GET /api/v1/sessions` | 列出全部会话：id/user/client/created/lastActive/defaultDb/在跑查询数/累计统计 | Admin |
| `GET /api/v1/sessions/{id}` | 单会话详情（含在跑查询明细） | Admin 或本会话 |
| `DELETE /api/v1/sessions/{id}` | **踢人**：取消它在跑的全部查询（复用既有 cancel 路径）→ 吊销 token → 从表移除。被踢会话的下一个请求 401（`SESSION_REVOKED`） | Admin |
| `PUT /api/v1/sessions/current/database` | 设会话默认库（`USE db` 的 REST 落点；body `{ "database": "settle" }`） | 本会话 |

**不做**（减法，v1 定案）：会话保持/心跳协议（HTTP 无状态天然不需要）；会话级
临时表；会话级 SQL 变量；Flight 面的独立会话表（gRPC 连接即会话的天然边界，
v1 只把 connection meta 记进 Session.client，不另建机制）。

### 3.3 空闲回收（可选开关，默认关）

`--session-idle-timeout-mins <N>`（默认 0 = 永不回收）：server 周期扫
`last_active_at`，超时会话按"踢人"路径清理。默认关的理由：踢错活跃会话的代价
大于泄漏代价（会话对象 ~百字节级，泄漏不是内存问题而是审计噪音）。

## 四、多库设计

### 4.1 方案对比（定案：A）

| 方案 | 内容 | 判定 |
|---|---|---|
| **A. server 级多库挂载** | `qsdb server --mount settle=/data/qsdb-settle --mount sales=/data/qsdb-sales`（可重复参数；缺省仍开 `default=第一个位置参数`）。`AppState` 持 `HashMap<String, Arc<Qsdb>>`，SQL 面做限定名路由 | ✅ **内核零改动**；单库场景完全兼容；库间天然隔离（各自 catalog/预算/锁） |
| B. 内核 catalog 层级 | `Qsdb` 内建 database/schema 树，跨库事务、跨库查询 | ❌ 大改内核（catalog/exec/commit 全动）；跨库事务与查询 v1 无需求；违背减法 |

### 4.2 SQL 面

- **限定名路由**：`SELECT * FROM settle.t_dnl_day_24result_unit`——绑定期解析
  `db.table`，落到对应句柄。单段名 = 会话 `default_db`（初始 `default`）。
- **`USE db`**：改会话 `default_db`（仅 server 面；嵌入面单句柄单库，报
  "不支持"并指路限定名——显式拒绝，不假装支持）。
- **`SHOW DATABASES`**：列挂载名（Admin 全列；非 Admin 只列有 grant 的）。
- **跨库 JOIN（`a.t1 JOIN b.t2`）**：v1 **显式拒**（文案指明"跨库查询未实现，
  请分别查询或同库"）。理由：两句柄两套预算/分区机制，融合执行是另一个项目，
  静默做成"逐个查询再拼"必然是错的半吊子语义。

### 4.3 REST 面

- 查询/写入请求体新增可选字段 `"database": "settle"`——**优先级最高**；
  未给 = 会话 `default_db`；会话也没设 = `default`。
- `GET /api/v1/databases`：列挂载与各自只读态。
- 写入端点（`/api/v1/write`）的表名解析走同一套 `db.table` 路由。

### 4.4 预算与并发归属（多库后的新问题，v1 定案）

- **内存预算按挂载各自独立**（每句柄自己的 4GB，`--memory-budget-mb` 变为
  每挂载默认值，可 `--mount name=path,budget-mb=2048` 覆写）。
- **并发闸是实例级**（整个 server 一张注册表）——这是过载保护的本意。
- 只读挂载：`--mount name=path,read-only`（复用 `QsdbOptions::read_only`）。

## 五、权限模型（库级 grants）

### 5.1 模型

```jsonc
// _catalog/users.json 的用户条目升级（向后兼容见 5.3）
{
  "name": "op_settle",
  "credential": { "salt": "…", "hash": "…" },
  "grants": {                      // ← 新增；旧文件无此字段 = 全库 Admin（见 5.3）
    "settle": "Reader",
    "sales":  "Writer",
    "*":      null                 // null = 通配无权（白名单制）
  }
}
```

- **角色延续三枚**（Admin/Writer/Reader，enum 派发不变）：库级生效——
  同一用户在不同库可以是不同角色。
- **白名单制**：grants 里没有的库 = 无权（403），`"*"` 是显式通配。
  旧语义（一个全局角色）= `{"*": role}` 的语法糖。
- **表级 ACL 不做**（M7-A v1 定案延续；真要做是另一个量级的元数据系统）。

### 5.2 判定与管理

- 判定：§二 的四行规则。**每请求现查**（角色不缓存进会话——管理员改了权限
  立即生效，这是 M7-A 既有纪律的延续）。
- 管理（v1 保持文件 + 管理命令，不做 SQL DDL）：
  - `qsdb user add/remove/list` 子命令扩一个 `--grant db=role`（可重复）；
  - `user export/import` 原样（grants 随 JSON 走）；
  - `PUT /api/v1/users/{name}/grants`（Admin 热改；写 `_catalog/users.json`
    走既有原子写路径）。
- **登录签发**：登录响应回显 `{ session, grants 摘要, default_db }`——
  客户端可以自查能干什么，不用撞 403 试探。

### 5.3 兼容与迁移（一段话说死）

旧 `users.json`（无 grants 字段）加载时视为 `{"*": 旧角色}`——行为与今天
逐位一致；首次经任何管理命令写回时落新格式。`--token` 超级凭证不变
（等效 `{"*": Admin}` 的隐式会话，user 名记 `__token__`）。

> **M-C 落地定案（2026-10-18，对上稿的实现细化）**：
> ① 文件层面走**双轨**而不是替换：`grants` 字段存在 ⇒ 判定唯一依据（白名单制，
>   缺键 = 无权，`null` = 显式无权，库级精确项优先于 `"*"`）；`grants` 缺省 ⇒
>   `role` 字段照旧管所有库。好处：旧文件**零迁移**逐位兼容，export/import 的
>   旧导出体也照吃（新导出体 grants 随行、旧用户段保持旧形状）。
> ② **判定每请求现查**落在 `UserDef::role_for(db)`（内核 users.rs，唯一判定
>   入口）；server 面 `authenticate()` 会话命中后按**会话默认库**现查，Basic 按
>   `default` 现查——`PUT grants` 返回即生效，无需重登。
> ③ `Session` **不存角色**（M-A 的 `role_at_login` 快照在 M-C 移除）——快照
>   只会骗人；`/sessions` 的 `role` 与登录响应的 `role` 都是现查值（无权为
>   `null`）。**登录只验凭证不做授权判定**（白名单制用户也能登录，403 留给
>   每请求）。
> ④ `ALTER USER SET ROLE` = 写 `"*"` 槽位（库级精确项保留）；
>   `SHOW USERS` 增第三列 `grants` 摘要（只增不改）。
> ⑤ 途中抓到并关掉的**存量漏洞**：`/write` 端点此前只查"登录没登录"、
>   没过 `can_write` 闸——reader 一直能经 HTTP 写入（SQL 面的闸是好的），
>   契约测试钉死 403。
> ⑥ 资源端点的旧鉴权写法 `if let UNAUTHORIZED = auth()` 只拦 401——403
>   响应被丢弃后 handler 照跑；已改为错误响应直通（契约测试抓出来的第二个）。

## 七、并发实测（2026-10-18 首轮，.14，生产形态）

**口径**：负载生成在**客户端机**（Windows/Python stdlib 线程），打
`http://192.168.1.14:9430`；server 默认参数裸起（缓存 256MB / 预算 4GB /
并发闸 0 / 分片 4）；`--rows 5000000` 基准表。三类负载：

| 负载 | 形状 | 结果 |
|---|---|---|
| light | `SELECT count(*) FROM t`（元数据短路，结果 1 行） | **qps 平台 ~3400**（C=64 已到 2908，C=128 达 3463，C=256 持平）；p50 17→59ms 随 C 缓涨；**零错误**；server RSS 稳定 315MB |
| point | `WHERE id=<常量>`（点 1 行） | 与 light 同档（C=128 达 3284 qps）——**点查吞吐不是问题** |
| med | `GROUP BY g`（10 万组，**10 万行结果集**） | server 侧（同机口径对照）qps 平台 **~16**；远程口径 qps ~5——**瓶颈是结果集传输不是引擎**；C=8 起延迟线性涨（p50 1.5s@C=8 → 6.6s@C=32），**无准入 ⇒ 排队无界** |

三条硬结论（写进部署纪律）：

1. **轻查询容量充足**：3.4k qps @ 128 并发、p95 < 50ms、内存 315MB——
   BI 看板/高并发点查形态不是瓶颈。
2. **重聚合容量 ~16 qps**（16 核 × 每查询 4 分片 ≈ 8-16 并发即饱和），
   之后加并发**只加延迟不加吞吐**。容量规划按此算，不要按核数外推。
3. **结果集大小是远程吞吐的第一决定因素**（16× 差距）→ 大结果集的分页/截断
   是服务面后续课题（本稿只立题不展开）。

**压测纪律（同机压测是伪象）**：负载生成必须与 server **分机**——同机时
负载发生器与 server 抢 CPU，实测出现过 C=64 qps 崩到 4.8 + 客户端自缠
（Python 线程）的假象。本轮数据以分机口径为准，同机数据只作 server 侧
容量参考。

**后续压测矩阵（未做，立项待排）**：写并发（WriteBuffer 多客户端写同一表/
分区内竞争）、混合读写长稳（server 版 soak，含 compaction/gc 同跑）、
JDBC 连接池形态（连接数 × 池大小 × 查询大小）、503 准入的真实退避行为
（gate 显式收紧后 TOO_MANY_QUERIES 的客户端重试风暴验证）。

## 九、不做清单（v1 边界，与 §三/§四/§五 呼应）

- 表级 ACL / 列级脱敏（M7-A 定案延续）
- 跨库 JOIN / 跨库事务（显式拒，不留半吊子语义）
- 会话级临时表、SQL 会话变量、用户级/会话级配额（留位不做）
- SQL DDL 管理用户（`CREATE USER/GRANT`）——管理面保持文件+命令+REST
- Flight 面独立会话机制（gRPC 连接即边界）
- 大结果集分页/截断（§七 立题，另批设计）
- 会话持久化（server 重启会话全失效——token 重登即可，批处理场景零成本）
