## 四、拦路虎（按"性质"分类，不是按次数）

### 4.1 ⬜ `least` / `greatest`（21 + 10）——**trivial，建议第一件事就补**

逐行取多参的最小/最大值，NULL 语义按 Spark（忽略 NULL，全 NULL 则 NULL）。
实现 ≈ 20 行（照 `coalesce` 那条路：绑定期算公共超类型 + 执行期逐行比较）。

### 4.2 ❌ `stack(n, k1, v1, k2, v2, …)`（52）——**列转行**

真实用法（清单 2437 行附近）：

```sql
SELECT …, stack(6, '跨区跨省点对点中长期交易合约电量', CAST(ENERGY AS decimal(38,11)),
                   '跨区跨省点对点中长期交易合约电价', CAST(PRICE AS decimal(38,11)), …)
FROM …
```

语义：**每个输入行展开成 n 行**，第 i 行取第 i 组 `(key, value)` ⇒ 输出行数 ×n。

**难点**：它是**行数会变的生成器**（`Generated`/`LateralView` 一类），不是逐行标量函数
—— 要动执行层的"一行进、多行出"能力，且要与 `SELECT` 里其它列一起对齐。
**这一条要单独出设计稿**，别顺手做。

### 4.3 ❌ `PIVOT ( … FOR col IN ( … ) )`（54）——**数据透视**

Spark 的透视子句（清单 2448 行附近）：`FROM (子查询) PIVOT (sum(x) FOR col IN ('a','b','c'))`
⇒ **列名由数据决定**（行转列）。

**难点**：**输出 schema 依赖数据**（`IN (...)` 里的值列表；Spark 还支持子查询动态取）
⇒ 与我们"绑定期定 schema"的模型正面冲突。**这条也要单独出设计稿**，
而且要**先明确口径**（只支持字面量 `IN` 列表？还是要动态？）。

### 4.4 ❌ `库.表` 限定名（266 次，全是 `js_produce.…`）——**是个"设计决定"，不是"没实现"**

本仓**显式拒**限定名（`qualified names (db.table) not supported yet; single database in use`，
见 `SQL支持面.md` §〇）。但这里有个**真问题要拍板**：

- 语料里的 266 次**全是同一个库**（`js_produce.`）⇒ 在我们单库模型下**没有歧义**
  （`js_produce.t_x` 只可能指 `t_x`）；
- 那么**"接受并忽略库前缀"**算不算"静默"？本仓纪律是"不静默兜底"，
  但这里忽略的是**没有歧义的信息**，与"拼错不报错"不是一回事。

⇒ **建议按这个口径**：**接受限定名，但要求前缀必须等于当前库名（或 `default`）**，
否则显式拒 —— 既让 Spark 的 SQL 原样能跑，又不会把"指到另一个库"的意图悄悄吞掉。
**这条要用户拍板**（它影响整个语料能不能"原文照跑"）。

## 十、★ 死 CTE：怎么判、怎么设计（用户专门问过）

**判断**：建 CTE 引用图，从主查询出发做**传递闭包**，闭包外的即死。

**设计**：把判断**挪到绑定之前**。改前我们与 Spark 语义**一模一样**（全量绑定、
只执行可达的）—— 这正是死 `pivot` 会拦路的原因。

**量出来的规模**（比预想重）：

| | |
|---|---|
| CTE 定义总数 | **2890** |
| **死的** | **562（19.4%）** |
| 含死 CTE 的块 | **55 / 154** |
| **死 CTE 里含 `pivot`/`stack`** | **46 处** |

最臃肿的 `L8-03` 第 1 块：**46 个定义里 38 个是死的**，主查询只是 `SELECT * FROM t23`，
活链只有 `t23←t18←t13←t8←t2` 五节 —— 死的那 18 个是**同一任务另外 4 个产出的分支**
被复制进了每一块。

**判定口径刻意保守**（`translate.rs::live_cte_names`）：按 AST 分段取文本、扫标识符 token。
`Display` 保真渲染标识符 ⇒ **不会漏**（漏了会让引用处硬报 `table not found`，不是错值）；
字符串字面量 / 嵌套局部同名 CTE 只会**多留** ⇒ 退回今天的行为。**两个方向都安全**。
（sqlparser 的 `visitor` 特性会拖进 `sqlparser_derive` proc-macro，**违反零新增依赖**，不用。）
名字唯一性仍对**全部** CTE 查 —— 名字空间与"用不用得上"是两件事。

⚠️ **与 Spark 的一处刻意偏离**（实测真 Spark 3.5.2：死 CTE 里写错表/列/函数**照样报错**，
它 analysis 覆盖全文、只是不执行）：我们提前砍 ⇒ **在非法 SQL 上比 Spark 宽松**。
方向安全 —— **永不产错值**，只是少报一个"你那段死代码写错了"。

### ★ 多值 `IN` 不下推（`beb9707`）

`x IN (a,b,c)` 绑定期展开成 `x=a OR x=b OR x=c`，而 `split_pushdown`
**只认 `Cmp` 和 `And`** ⇒ `Or` 掉兜底 ⇒ **三级裁剪全都拿不到**。
单值 `IN` 不生成 `Or`（退化成 `Eq`）所以一直是对的 —— 语料里绝大多数是单值，
把这个洞盖住了；而"**多日**"算法正是要 `PDATE IN (d1,d2,…)`。

⚠️ `Or` 与 `And` 规则**刻意不同**：`And` 可只推一侧；**`Or` 必须两侧都能推且都无残余**，
否则整体留作过滤 —— 半推会**静默丢行**。验收 `tests/in_pushdown.rs`（5 条，两路对撞）。

**68/68 张可分区表全部分区**（`<t>_p` 副本，原表不动）。DAG 驱动的 A/B，120 个两边都跑通的块逐块对齐：

| | 原表 | 全分区 |
|---|---|---|
| 单条耗时总和 | 128,292 ms | **11,389 ms（9%）** |
| 中位 | 998 ms | **92 ms** |
| 任务总墙钟（全并发） | 7080 ms | **2118 ms（3.3×）** |
| **行数不同的块** | — | **0** |

`t_cal_day_agent_relation` 119 个 —— 语料每条过滤**单日** ⇒ 扫描量降到 1/15~1/119。

⚠️ 口径：全并发下 16 核超订，墙钟把单条差异压扁了（单条 11× vs 墙钟 3.3×）。

### 途中撞出的两堵墙（**都不在本批的预料里**）

两堵墙都**藏在 `stack` 的前置拒绝后面** —— 不把 `stack` 放开，它们连露头的机会都没有。

#### 墙一：`CAST(x AS byte)`（8 个块）

`byte` 是 **Spark 的 `TINYINT` 别名**，sqlparser 认不出这个词、落到 `DataType::Custom`。
语料 24 处 `CAST(x AS byte)`，**全在 `stack` 的参数里**。
修法：**只认 `byte` 这一个词**（`Custom` 是"任何不认识的类型名"的收容所，
顺手放行等于把拼错的类型名也当成 TINYINT）。

#### 墙二：`数值列 = ''` 的比较短路顺序（9 个块）

语料里"空串当零"的惯用写法：`CASE WHEN SUM_VALUE = '' THEN 0 ELSE SUM_VALUE END`
（`SUM_VALUE` 是 `DECIMAL(38,8)`）。报的错是 **`cannot compare DECIMAL(38, 8) with BOOLEAN`**
—— 方向指得离谱。

病根：`promote_string_lit` 按 Spark 语义把转不动的字符串变成 `Lit(Null)`
（`''` 转不成小数），而 "一侧是 NULL 就短路" 当时挂在提升**之前**；
轮到 `cmp_common_type` 时拿到 `DECIMAL(38,8)` 对 `Lit(Null)`，
而 **`Lit(Null).data_type()` 的兜底恰好是 `Boolean`** ⇒ 报出那条莫名其妙的错。
修法：把 NULL 短路挪到两个提升**之后**（`null_cmp_short_circuit`）。
回归见 `tests/expr_complete.rs::数值与字符串字面量比较_转不动给_null_而不是报错`。

#### 墙三：CLI 的单元格截断 —— **它其实一直在 panic**（已修）

`L5-01_01` 一开始被记成"引擎错误（输出里带出一张表头）"。查下去发现**不是引擎的事**：

```
panicked at crates/qsdb-cli/src/main.rs:1086:46:
end byte index 21 is not a char boundary; it is inside '平' (bytes 19..22)
```

截断写的是 `&v[..21]` —— **按字节**切片。21 一旦落在多字节字符中间（中文值），
直接 panic，而**前半屏已经打出去了**，看着像查询失败。

这条截断至此**连坑三次**：① `SHOW TABLES` 的截断表名拿去做 `DESCRIBE`，
**39 张表被静默跳过**；② 长列名被截进 DDL，拼出语法错；③ panic + 伪造出一个引擎失败。

**已修**（`crates/qsdb-cli/src/main.rs`）：
- 按**字符**截（不再按字节切），列宽也按字符数算（否则中文列一律错位）；
- **重定向/管道时一个字都不截** —— 截断只对"人在终端上看"有意义，
  输出一旦被程序消费，截断就是**静默丢数据**。
- 回归：`crates/qsdb-cli/tests/output_values.rs`（3 例）。

修完语料 **146 → 147**（`L5-01_01` 本来就跑得通，只是 CLI 把它打崩了）。

### 本批修的四件事

1. **集合操作归一的 cast 拿错了"现状类型"**（L4-01 三块的真凶，**潜伏的老 bug**）
   `cast_setop_side(右侧, common, lc)` 把**左边**的列类型当右列的现状类型。
   当 `common` 恰好等于左侧类型（左侧在归一里"赢"）时，`cast_to_impl` 看到
   类型相等**不包 Cast** ⇒ 右侧的真实类型裸穿到声明的 schema 下 ⇒
   `project failed: expected Decimal128(38,8) found Decimal128(30,8)`。
   那个 30 是 CASE 折叠整数 `0` 每层 +10 位精度攒出来的 —— 三层 CASE 就是 (30,8)。
   **修法**：cast 按各侧**自己的**声明类型。
2. **UNION 里的裸 `NULL AS x`**（L7-02_01 / L8-02_02）
   `Lit(Null)` 无类型，`data_type()` 兜底 Boolean ⇒ NULL 分支把整列"变成" Boolean，
   下游 `V1 = ''` 报 BOOLEAN vs STRING；更阴的是 NULL vs BIGINT 归一时
   **BIGINT 侧被字符串化**，下游报 STRING vs BIGINT —— 错的是归一，报错却指向
   用户没写过的比较。**修法**：归一时裸 NULL 列**采纳对侧类型**（Spark 的 NullType 语义）。
3. **字符串参与算术 / 字符串表达式比较**（L11-01_01 / L8-02_02 的另一半）
   `COALESCE(fee,0.0)*CAST(energy AS STRING)`：Spark 把字符串转 **double** 再算。
   `CAST(VALUE AS STRING) = 1`：字符串表达式 vs 数字，两侧转 double 再比。
   字面量侧照旧绑定期转（转不动给 NULL）。
4. **`js_data.` 前缀**（L0-06_01）：单库模型不收限定名，runner 侧剥前缀
   （`run_dag.py`，与 Spark 侧的 js_bench 改写同一段），引擎不动。

### 本批追加：跨类型 JOIN 键（对账挖出的第 5 个洞，**静默错值**）

154/154 达成后的**逐值对账**挖出来的：L7-02_01 行数与 Spark 一致性检查过了，但
**逐值**对不上 —— Spark **5832 行，我们 0 行**。

**根因**：`t5 INNER JOIN t8 ON t5.SETTLE_TYPE = t8.JS_OBJECT`（**数值列 = 字符串列**）。
`as_equi_key` 把两侧**各自绑定**、类型原样进哈希 join —— 编码不同 ⇒ **0 匹配、无报错**。
（比较路径早有字面量提升，但 JOIN 的 ON 走的是另一条路，从没归一过类型。）

**修法**（三处，全是"包装里的列必须跟着换空间"）：
1. `as_equi_key`：键两侧走与比较路径**同一套**提升（temporal/字符串字面量/字符串表达式），
   归到公共比较类型；归一不了落到残留由 `bind_expr` 给确切错。
   ⚠️ **先判侧、后 cast** —— cast 会把裸列包成 `Cast{Column}`，`side()` 只认裸列。
2. `exec_builder` 两处"右键减左宽"（`key_to_build_local`）与
3. `translate` 的换边换算（`shift_col_idx` / `swap_sides_expr`）——
   全都要**钻进 Cast 包装**，只认裸列 ⇒ 全局 idx 进 build 批 ⇒ 越界 panic
   （实测 7 个块 panic）或静默读错列。

**结果**：L7-02_01 **5832 行与 Spark 逐格一致**；154 块中**只有它**的行数变了
（0 → 5832，正是修复目标），其余 153 块一格没动。

### 排障路上的两条假线索（都查到水落石出，记下免得再查一遍）
