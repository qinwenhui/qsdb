## 一、三层与判据

```
T0  内核      crates/qsdb —— 一个 lib。能力/原语都在这里
T1  内核仓    crates/*（同 workspace，bin `qsdb` 的子命令 / 附属 bin）
T2  生态仓    独立 repo（qsdb-sync / qsdb-jdbc / qsdb-odbc）
```

**判据：按顺序问三个问题，第一个答"是"的就是它的层。**

| # | 问题 | 是 → | 理由 |
|---|---|---|---|
| ① | **除了 CLI，还有谁会调它？**（HTTP 客户端 / JDBC / ODBC / 嵌入方） | **T0 内核** | 只放 CLI = 让每个消费方自己实现一遍，且**行为会漂** |
| ② | **它要的依赖，内核要不要？**（`tower-lsp` / `rmcp` / 云厂商 SDK…） | 不要 → **T2** | 内核的红线是**零新依赖**；为一个工具破它不划算 |
| ③ | **发布节奏和内核一样吗？** | 不同 → **T2** | 一起发版 = 工具被内核的节奏绑住 |

### ★★ 一条从"低占用"定位直接推出来的硬结论

> **默认不拆 bin，加子命令。**

每个独立 bin 都要**静态带一份 arrow + parquet**（~20MB 量级）。现在 `qsdb`
**一个 bin 装了 shell / query / admin / server 四个角色** —— 这是对的。

拆成 `qsdb-shell` + `qsdb-export` + `qsdb-import` + `qsdb-sql` ⇒ **体积 ×4**。
而"独立仓"这件事**必然**导致独立 bin ⇒ 必然重复。

⇒ **"靠近内核"不但不该拆仓，反而该合并。** 只有判据 ② / ③ 成立时才拆。

> 佐证：`tokio-util` 那次（`/files` 流式下载）本仓专门写了一段注释论证
> "**它本来就在依赖树里，不新增任何 crate，二进制增量 ≈ 0**" —— 同一把尺子。

## 二、全景清单

### A. 今天已经有了

| 现在 | 是什么 | 层 |
|---|---|---|
| `qsdb shell` | 交互式 REPL（`rustyline`，历史/编辑） | T1 |
| `qsdb query <sql>` | 执行单条 SQL 后退出 | T1 |
| `qsdb admin …` | 11 个子命令：`tables` `partitions` `refresh-index` `gc` `compact` `user-add/drop/passwd/list/export/import` | T1 |
| `qsdb server` | HTTP API（+ 可选 Arrow Flight） | T1 |
| `crates/qsdb-client` | Rust 薄客户端（零网络依赖，手写 HTTP/1.1） | T1 |
| `crates/qsdb-bench` | 基准 suite + 一批探针 bin | T1 |
| `qsdb-sync` / `qsdb-jdbc` / `qsdb-odbc` | 独立仓（`D:\qinwh\code\myself\` 下） | T2 |

### B. 你提到的 —— 逐个定层

| 你说的 | 实际 | 处置 |
|---|---|---|
| `qsdb-shell` | ✅ **就是现有的 `qsdb shell`** | 不新建 |
| `qsdb-sql` | 🟡 **一半已存在**：`qsdb query <sql>` 有了；**缺 `-f file.sql` 与 stdin 管道**（`psql -f` / `psql < a.sql` 那种） | **先在内核仓补 `-f`**。它与 `shell` 共享 ~90%（连接、格式化、错误渲染），拆开=复制粘贴 |
| `qsdb-export` | 新 | **T1 子命令**。是 A3 之上的**壳**，见 §三 |
| `qsdb-import` | 新 | **T1 子命令**，反向。**与 export 共享实现**（格式推断 / 并行度 / 进度），但**别合成一个命令**（方向不同、参数不同） |

### C. 你没想到的

#### C1. 出事时第一个想跑的 —— **全是真空白**

| 工具 | 干什么 | 为什么重要 |
|---|---|---|
| **`qsdb fsck`**（别名 `doctor`） | **体检报告**：manifest ↔ 段文件对账（缺失 / 孤儿 / 长度不符）、trash 与 staging 残留、分区索引与实际目录漂移 | ⚠️ 现在只有 `admin gc`（**动作**），**没有"先诊断再决定"**。sync / JDBC 报障时第一步就是这个。<br>**别默认修** —— 先出报告、`--repair` 才动手 |
| **`qsdb diff <a> <b>`** | 比对两个库 / 主备：哪些分区、哪些段、哪些行不一致 | sync 现在只会"推"，**没有任何东西能回答"我到底同步对了没有"**。主备一致性的验收就靠它 |
| **`qsdb backup` / `qsdb restore`** | **物理快照**：manifest + 段文件整体打包，含 `generation` / `epoch` / 用户面，能在另一台机器**原样起库** | ⚠️ **和 export 完全不是一回事**：export 出的是**给别人读的数据**（Spark/DuckDB 能读）；backup 出的是**能原样恢复的库**。**这条线现在整个是空的** |

#### C2. 可观测 —— 顺带说个**刚查出来的空白**

| 工具 | 现状 |
|---|---|
| **`qsdb explain <sql> --analyze`** | ⚠️ **内核连 `EXPLAIN` 这个语句都没有**（2026-10-15 grep 确认：`crates/qsdb/src/` 里 `EXPLAIN` 只出现在两行注释中）。裸文本都不存在，更没有"每算子行数 / 耗时 / 内存 / 溢出量" |

> `--analyze` 是**性能冲刺的刚需**。现在调优靠"改完跑基准看总时间"，
> 有了它才能一眼看出**是哪一层**退化的。它本身是 **T0**（SQL 语句，HTTP/JDBC 也该能拿到计划），
> CLI 只负责**渲染**（树状 / JSON）。

| 工具 | 干什么 |
|---|---|
| `qsdb top` / `activity` | `pg_stat_activity` 那种：**现在在跑什么查询、多久、吃多少内存**。`server` 有并发上限，但没暴露"当前在跑啥" |
| `qsdb stats <table>` | `partition_stats` 的聚合视图（`admin partitions` 只沾了个边） |

#### C3. 造数 / 回放

| 工具 | 干什么 |
|---|---|
| `qsdb gen` / `dbgen --tpch sf=1` | 数据生成器。现在基准数据靠脚本 ⇒ **做成子命令后基准可复现**，直接服务 `超越DuckDB路线.md` |
| `qsdb replay` | 回放慢查询日志做压测（`crates/qsdb-bench/src/bin/soak.rs` 有雏形，**没有入口**） |

#### C4. 元数据 / 交付

| 工具 | 干什么 | 备注 |
|---|---|---|
| ~~**`qsdb dump`**~~ | ✅ **2026-10-16 已做**：`SHOW CREATE TABLE`（T0 原语，往返有回归）+ `qsdb dump [--data <目录>]` / `qsdb restore`（T1 壳）。**逻辑备份闭环**：结构 + 数据，导出去能原样恢复 |
| `qsdb meta` | 库的体检卡：表 / 分区 / 段 / 字节 / 用户 / **格式版本** / 内核版本 | 运维交接用。`--format json` 便于机器读 |

#### C5. 协议桥 —— **两条战略级**

| 工具 | 分量 |
|---|---|
| **`pgwire`（PostgreSQL 线协议）** | ★★★ **分量最大的一条**。一旦支持，**`psql` / DBeaver / TablePlus / Metabase / Superset 全部零驱动直连**。而且它会让 **`qsdb-jdbc` / `qsdb-odbc` 从"必需"降为"可选"**（现成的 PG JDBC / ODBC 驱动直接可用）。<br>⚠️ **必须尽早拍板** —— 那两个仓**已经在投了**。它是 `server` 的另一个 listener，属 T0/T1，**不是独立工具仓** |
| `qsdb mcp` | 把库暴露成 MCP server 给 AI 客户端。成本低（几个工具定义 + 调内核），现在正是时候。依赖 `rmcp` ⇒ 可能落在 **T2** |

#### C6. 其余（可以缓）

| 工具 | 处置 |
|---|---|
| `qsdb-lsp` | 编辑器 SQL 补全（表名/列名）。重依赖（`tower-lsp`）⇒ **T2**，**没有明确用户就别做** |
| `qsdb-ctl` | 启动 / 停止 / 状态 / 重载（`pg_ctl`）、daemon 化、systemd unit。**生产必须有，但不急** |
| `qsdb migrate` | 从 PG / MySQL 迁入 —— 其实就是 `import` 的特例，**别单开** |

## 三、★ A3 与 `qsdb-export` 的分界

用户问的"是不是吻合了"—— **吻合，但是两层，不是重复**：

```
T0 内核原语   COPY (SELECT …) TO '…' (FORMAT PARQUET, PARTITION_BY (dt))
                    ↑ 谁都能调：HTTP /query · JDBC · ODBC · sync 的 sink · 嵌入方
                          │
T1 CLI 壳     qsdb export   ← 只是它的命令行外壳
```

**判据（§一 的问题①）**：`COPY … TO` 会被 HTTP `/query` 调到、会被 JDBC 调到、
sync 的 sink 能复用 ⇒ 它**必须在内核**。

**只有命令行要的那部分留给壳**：异构源（glob / CSV / JSON 目录）、进度条、
断点续传、批量多表、失败重试、并行度旋钮。

> ⚠️ **顺序不能反**：如果先做 `qsdb-export`、让它自己写 parquet writer，
> 那就是**造第三遍轮子**（qsdb-sync 已经造过一次 `sink-parquet`；我们再来一次
> 就变成两次）。**先 A3，工具只当壳。**
>
> ⚠️ **反过来也要防**：别把壳的能力塞进内核。进度条、断点续传**不属于内核**
> —— HTTP/JDBC 消费方不需要它们。

**一句话判据**（新想一个工具时直接套）：
> **下载单个查询到 hive 湖** → A3 够了，别做工具。
> **从一堆异构源导入 N 张表、要进度要续传** → 那是工具的事。

## 四、战略级（**保留待拍板，不删**）

按"影响面 × 现在不做会不会浪费已投入"排：

| # | 项 | 为什么**要尽早**拍板 |
|---|---|---|
| 1 | **`pgwire` 做不做** | 它决定 **`qsdb-jdbc` / `qsdb-odbc` 两个仓的必要性**。**那两个仓已经在投了** —— 越晚知道越浪费 |
| 2 | **`EXPLAIN`（含 `--analyze`）补不补** | 性能冲刺**下一批正缺这只眼睛**。是 T0（内核语句），不是工具 |
| 3 | **`backup` / `restore`** | 这条线**整个空着**，而它是"**通用独立数据库**"的**基本盘**（不是生态工具，是产品缺件） |

> 这三条**不占本轮排期**，但**要在这轮结束前给个说法**（做 / 不做 / 什么时候）。
> 悬着比拒了更贵 —— 悬着 = 别的决策会按错误的假设做。

## 五、明确不做（写清楚，别让人等）

| 不做 | 理由 |
|---|---|
| `qsdb-sql` / `qsdb-shell` **拆成独立仓** | 它们与内核共享 90% 代码（连接 / 格式化 / 错误渲染）；拆仓 ⇒ 拆 bin ⇒ **每个 bin 各带一份 arrow+parquet**。与"低占用"正面冲突。**判据 ② / ③ 都不成立** |
| `qsdb-migrate` 单开 | 是 `import` 的一个特例 |
| `qsdb-lsp`（默认不做） | 重依赖 + 没有明确用户。**有人真要时再立项**（那时它自然是 T2） |
| `qsdb server --follow <上游>` | 用户已拍板走**订阅端点**，见 `提交事件订阅与湖导出设计.md` §四 |
| 把进度条 / 断点续传塞进内核 | HTTP / JDBC 消费方不需要；壳的能力留在壳里 |
