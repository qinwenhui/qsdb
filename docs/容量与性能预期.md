# 容量与性能预期（“百公里油耗”表）

> **给谁看**：要拿 QSDB 做决策的人（选机器、估容量、判断"这事能不能干"）。
> **不要求**你懂并行度、row group、在途批 —— 那些是我们的喷嘴直径，与你无关。
>
> **怎么用**：拿你的数据量，在下表里找最接近的一行，读秒数和内存。
> 再做一次乘法（两条经验规则）就能外推到你的规模。

---

## 一、基准机器（相当于"综合工况"）

| | |
|---|---|
| CPU | 16 核 |
| 内存 | 62 GB |
| 盘 | SSD（数据与库同盘） |
| 数据形状 | 7 列（4 个整数/浮点 + 2 个字符串 + 1 个日期），字符串约 20 字节 |
| 行宽 | 源 Parquet 约 **100 字节/行**（505 MB / 500 万行） |

⚠️ **标定点是 100 万行与 500 万行**。别的规模是**外推**（见 §三），不是实测。

## 二、主表：多少数据、做什么、要多久、要多少内存

| 你要做的事 | 100 万行 | 500 万行 |
|---|---|---|
| 数总行数 `count(*)` | 0 ms / **3 MB** | 0 ms / **3 MB** |
| 全表扫一遍求和 `sum(v)` | 7 ms / **13 MB** | 21 ms / **9 MB** |
| 过滤 + 聚合 `WHERE g<1000` | 11 ms / **19 MB** | 47 ms / **13 MB** |
| 分组聚合（10 万个组） | 31 ms / **103 MB** | 64 ms / **110 MB** |
| 排序取前 100 名 `ORDER BY … LIMIT 100` | 12 ms / **19 MB** | 36 ms / **42 MB** |
| 去重计数 `count(DISTINCT 字符串列)` | 141 ms / **168 MB** | 663 ms / **562 MB** |
| 两张表 JOIN 再分组 | 59 ms / **94 MB** | 233 ms / **87 MB** |
| 导出 Parquet | 183 ms | 852 ms |
| 导出 CSV | 151 ms | 655 ms |

（导入的账见 §五。）

## 三、两条经验规则（**这两条才是你要背的**）

### 规则 1：时间

> **扫描 / 过滤 / 排序 / 导出：约「每百万行 5 ms」，与行数成正比。**
> **JOIN：约「每百万行 45 ms」。去重（DISTINCT）：约「每百万行 130 ms」。**

（这三条是从上面两列实测里取的斜率：扫描 7ms/百万 与 4.2ms/百万，JOIN 59/1 与 47/1，
去重 141/1 与 133/1。）

代入你的量：

| 你的数据 | 全表扫一遍 | JOIN 一次 | 去重一次 |
|---|---|---|---|
| 1000 万行 | 约 0.05 秒 | 约 0.5 秒 | 约 1.3 秒 |
| 1 亿行 | 约 0.5 秒 | 约 4.5 秒 | 约 13 秒 |
| 10 亿行 | 约 5 秒 | 约 45 秒 | 约 130 秒 |

⚠️ **这是外推**：标定点只到 500 万行。上亿行时"数据装不下内存"会改变行为
（落盘、换算法），**别把这张表当承诺**。

### 规则 2：内存（**这条比时间要紧**）

> **内存 ≈ 100 MB 起步 + 「不同值的个数 × 200~350 字节」**
>
> **它随「有多少个不同的值」走，不随「有多少行」走。**

证据就在上表：**分组聚合**从 100 万行到 500 万行，行数 ×5、**内存几乎没变**
（103 → 110 MB）—— 因为两者的**组数都是 10 万**。反过来，**去重**在 500 万行时
吃掉 562 MB —— 因为那时有 **250 万个不同值**。

⇒ **估内存要数「不同的值」，不是数「行」。**
10 万个组 ≈ 100 MB；100 万个组 ≈ 250 MB；1000 万个组 ≈ 2.5 GB。

> **扫描类几乎不占**（10–20 MB），不管多少行都是这个量级 —— 它是流式的，
> 来一批走一批。

## 四、"我要办这件事，大概要什么机器"

| 你想干的 | 最小内存建议 | 备注 |
|---|---|---|
| 只做扫描 / 过滤 / 导出 | **512 MB** | 与数据量基本无关 |
| 分组聚合，组数 ≤ 10 万 | **1 GB** | |
| 分组聚合，组数 100 万 | **2 GB** | |
| 去重（DISTINCT 高基数列） | **按不同值算**：1000 万不同值要 **~3 GB** | 这是最吃内存的操作 |
| JOIN 两张表 | **1 GB** | ⚠️ **大表放左边**（`A JOIN B` 时 B 整张进内存） |
| 多查询并发 | 上面各条 **× 并发数**，再加 20% 余量 | 并发上限可配 |

**内存不够会怎样**：不是崩，是**落盘**（排序/聚合/JOIN 都能溢到磁盘）。
代价是变慢（可能 2–3 倍），结果不变。

## 五、导入的账

| 导入方式 | 500 万行耗时 | 峰值内存 |
|---|---|---|
| Parquet 文件 → 表 | 2.2 秒 | **108 MB** |
| CSV 文件 → 表 | 3.6 秒 | **99 MB** |
| 内存里直接写（程序里 `append`） | 4.5 秒 | **29 MB** |

⇒ 约 **每百万行 0.5–0.9 秒**、**内存 100 MB 上下**（与文件大小无关，流式）。

## 六、机器不够快 / 内存不够时，**唯一需要知道的旋钮**

调 **线程数**（环境变量 `RAYON_NUM_THREADS`），它是一个**天平**：

| 线程数 | 500 万行「过滤+聚合」 | 同一句的内存 |
|---|---|---|
| 1 | 121 ms | **6 MB** |
| 4 | 32 ms | 13 MB |
| 16（默认） | **36 ms** | 13 MB |

⇒ **默认（用满核）速度最好，内存也只多几 MB —— 绝大多数情况不用管它。**
只有当机器**非常挤**（比如你要在一台 1 GB 的小机器上跑）时，把它调小。

> 注：真正吃内存的**不是并行**，是 §三规则 2 的「不同值个数」。
> 那一条调线程数**救不了**（它是结果的固有大小）。

## 七、跟 DuckDB 比，我们在哪

> 口径：同一台机、同一份数据、同一轮。

**我们已经更快的**：数行数（20×）· 简单过滤/分组/取前 N（1.2–1.4×）·
CTE · **导出 Parquet（1.2×）** · **导出 CSV（1.5×）** · 导入 CSV（1.1×）

**还慢一些的**：排序去重类（2–3×）· 多表 JOIN + 分组（2.3–2.8×）

**内存**：11 个格子里**我们更省 6 格**（导入 CSV 只有对手的 1/11）。
胖的地方集中在**排序/去重**这类要攒住不同值的操作。

> ⚠️ 别拿这张表当"DuckDB 更快/更慢"的结论 —— 两边**优化的目标不同**：
> DuckDB 是嵌入式单机引擎；QSDB 是**要当服务器使**的（并发、权限、提交事件、
> 湖导出、主备）。**你的场景该选哪个，取决于你要不要后面那些。**
