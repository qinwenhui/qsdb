# 整型去重的密集直索引 —— 设计稿（2026-10-17，第十五批）

> **缘起**：`simple_distinct_int` 0.145s vs DuckDB 0.1018s（1.42×），是十四批后
> 「我们在输」仅剩的两格之一。对账表里写的病灶是"哈希常数差"——
> **本批先剖，这个归因是错的**：哈希是常数，**真正在变的是槽表尺寸沿缓存层级的随机访问**。

## 一、剖面（.14，bench-release `sql_bench` 7 轮中位，`QSDB_DISTINCT_PARTS=1`）

基准表 `t`（500 万行），`v = (i·2654435761) mod 1e6` ⇒ 基数恰 100 万：

| 查询 | 组数 | 槽表大小 | 总耗时 | 净成本/行（减 25ms 扫描地板） |
|---|---|---|---|---|
| `count(v)` | — | — | 25.2ms | （扫描地板） |
| `count(DISTINCT g)` | 10 万 | 4MB（**L3 内**） | 33.4ms | **1.6ns** |
| `count(DISTINCT v)` | 100 万 | **32MB = 2×L3** | 148.4ms | **24.7ns**（15× 跳变） |
| `count(DISTINCT id)` | 500 万 | **128MB**（深 DRAM） | 502.8ms | **95.6ns** |

- 本机（hadoop104）缓存：L1d 32K / L2 256K / **L3 16MB**。
- `perf stat`：**cache-miss 率 45.2%**，5 轮 1.18 亿次 miss ⇒ **每行 ~4.7 次缓存缺失**。
- 哈希本身（fxhash 8 字节）~2ns/行，**不随组数变**——15× 的跳变全部来自
  「探测那次随机访问落在了缓存层级的哪一层」。

**结论**：`int_slots`（`(i64,u32)` 16B/槽、负载 0.5）在 1M 组时 32MB，
**2 倍于 L3**，每行探测都是 DRAM 级随机访问。十四批给 join 建的
`HashIndex::Direct`（数组直取，免哈希、4B/槽）正是对症的形状——搬到
`GroupTable` 的 count-only 单 Int64 路上。

## 二、设计：`DenseInt`（count-only 单 Int64 键的密集直索引）

```
struct DenseInt { min: i64, slots: Vec<u32> }   // slots[(v - min)] = gid；EMPTY = u32::MAX
```

- **4B/槽 vs 现在的 16B**，且**免哈希免探测**：一次随机访问拿 gid。
  span 100 万 = 4MB（L3 的 1/4）⇒ 预期净成本回到 ~4-13ns/行。
- **NULL** 沿用 `count_only_null_gid` 专门槽（`i64::MIN` 是合法值，键值不能当哨兵）。
- **`key_arena` 纪律不变**：建组仍走 `push_group`（arena 写规范编码 `[1]+LE8` / `[0]`）
  ⇒ **dense 只是缓存**，随时可按 arena 重建（与 `rebuild_int_slots` 同一条铁律）。

### 2.1 锚定（streaming 输入，min/max 不可预知 ⇒ 惰性锚定）

`assign_groups_count_only_int` 进入时，`dense` 为空且未死 ⇒ 用**当前批**的
min/max（顺序扫一遍，~0.3ns/行）试探：

- 批内 span ≤ **CAP（8M 槽 = 32MB 上界）** ⇒ 分配 `slots`；**表非空 ⇒ 先按
  arena 回填**（`insert_raw_key` 灌过或溢出分区表续灌的形状，M4-1 同款教训）。
- span > CAP ⇒ `dense_dead = true`（span 单调不减，永无翻案）⇒ 永走槽路。
- 批内无非空值 ⇒ 不锚定（纯 NULL 批走 null 槽），下批再试。
- 开关 `QSDB_NO_DENSE_GROUP=1` ⇒ 永不锚定（A/B 对撞用）。
- `QSDB_DENSE_GROUP_CAP=N` ⇒ 覆盖 CAP（探针/单测用，默认 8_000_000）。

### 2.2 行循环

```
若 col.is_null(row)          → null 槽（既有逻辑）
k = col.value(row)
i = k - min                  // i128 语义，usize 化前判界
0 ≤ i < len 且 slots[i]≠EMPTY → out.push(gid)          ← 命中：一次随机访问
slots[i]==EMPTY（在界内）     → 建组（push_group 写 arena）+ slots[i]=gid
                               + max_seen = max(max_seen, k)
越界                          → dense_grow(k)（见 2.3）后重试本行；
                                坠回 ⇒ 本行起交给槽路循环
```

### 2.3 增长与坠回（值域一边跑一边长出来）

越界值 `k` 到来时：`lo = min(min, k)`，`hi = max(max_seen, k)`，
`need = hi - lo + 1`（**i128 算**，`i64::MIN/MAX` 不 panic）：

- `need ≤ CAP` ⇒ **几何增长重建**：`new_alloc = min(max(need, 2×alloc), CAP)`，
  按 arena 回填新数组（成本 O(组数)，翻倍摊还 O(终态 span)），锚点移到 `lo`，
  然后处理本行。**每批至多一次重建**。
- `need > CAP` ⇒ **坠回**：`dense_dead = true`，`dense = None`，
  调既有 `rebuild_int_slots()`（按 arena 重建槽表），**本行起**槽路接手。
  已 push 的 out 前缀原样保留——两条路产出同一 gid 空间。

### 2.4 状态一致性（谁动了表，dense 就得让位）

| 入口 | 处置 |
|---|---|
| `insert_raw_key`（溢出分区重灌） | `dense = None`（下次 assign 按 arena 回填再锚定） |
| `merge` / `merge_subset` | `self.dense = None`（count-only 表今天没人 merge，一线保险） |
| `estimated_bytes` / `profile_bytes` | dense 按槽 ×4B 计（与 int_slots 互斥，不会双算） |

dense 与 `int_slots` **互斥持有**：锚定/增长重建时清槽表，坠回时清 dense。

## 三、正确性钉子

1. **gid 空间唯一**：dense 与槽路共用 `push_group`（arena + gid），坠回前后
   已有组不动 ⇒ 两条路产出**同一个 gid 空间**，out 前缀无需修补。
2. **NULL 三处不变**：null 槽专用；键值 `i64::MIN` 合法（不用键值当哨兵，
   EMPTY 是 gid 侧的 u32::MAX，不与键冲突）。
3. **i64::MIN/MAX**：span 计算与下标全部走 i128；`(i64::MAX - i64::MIN + 1) = 2^64`
   > CAP ⇒ 必然坠回，不 panic、不错分。
4. **arena 是唯一真相**：任何时刻扔掉 dense 都能按 arena 精确重建
   （锚定回填 / 增长重建 / 坠回重建三条路都走同一份规范编码）。
5. **不能逐批判定走不走**（十四批前的旧教训）：进入与否仍由
   `count_only + 单 Int64` 类型驱动；dense 锚定失败只影响速度不影响语义
   ——组永远经 `push_group` 建在唯一真相上。

## 四、验收

1. **值对撞**（`tests/distinct_int_dense.rs`，env 全局 ⇒ SERIAL Mutex）：
   默认 vs `QSDB_NO_DENSE_GROUP=1` 逐值相等，覆盖——基础锚定+NULL、
   跨批增长（升序多批）、`QSDB_DENSE_GROUP_CAP=1000` 触发坠回、
   `i64::MIN/MAX`、负值锚定后正向增长、纯 NULL 批先于值批、
   `insert_raw_key` 灌入后再 ingest（溢出分区形状）、随机数据 parity（定种）。
2. **基准**（.14，5 轮中位，DuckDB 同轮）：`simple_distinct_int` 目标 ≤0.11s
   （现 0.145s，DuckDB 0.1018s）；其余 18 例零回归
   （`simple_distinct` 字符串格不动、join/分组格不动）。
3. **探针三格**：`DISTINCT v`（4MB dense）、`DISTINCT g`、`DISTINCT id`
   （span 5M ⇒ 20MB dense，现 502.8ms，预期能吃到同一刀）。
4. 语料 154/154 行数零漂移；本地闸门全绿（http_contract 3 条已知环境 flaky 除外）。

## 五、不做清单

- **变长键（W1b 自适应）**：字符串去重已由 v2（排序去重）负责；本批只动整型。
- **非 count-only 的 `fast_slots_inline`**（普通 GROUP BY 内联槽）：那批表形态不同
  （带 literal、要求逐批非空），另案。
- **sum/count 复合聚合的 dense 化**：count-only 单列才进这条门。
- **默认 CAP 之上的形状**（span > 8M）：槽路原样，不为它们冒险。

## 六、风险

- **锚定错一批 = 全错** ⇒ 锚定只从批数据取 min/max（无元数据赌猜），
  span 单调 ⇒ 坠回判定不可逆但**只输速度**；对撞测试钉死。
- **增长重建漏键** ⇒ 三条重建路都扫**同一份 arena**（`key_of`），
  单测里 `insert_raw_key` 形状专门覆盖。
- **32MB 上界被滥用**（低占用纪律）：CAP 默认 8M 槽，超过即坠回；
  实测 bench（4MB）/DISTINCT id（20MB）都在界内，且 dense 比现行槽表
  同条件下**小 4×**（1M 组：4MB vs 32MB）。

## 七、落地结果与实测（2026-10-17 追记）

**基准**（.14，5 轮中位，DuckDB 同晚间轮）：

| 格 | 改前 | 改后 | DuckDB 同轮 | 相对 |
|---|---|---|---|---|
| simple_distinct_int | 0.145s | **0.066s** | 0.097s | **~1.47× 领先**（原 1.42× 落后） |
| DISTINCT id（探针，500 万组） | 502.8ms | **123.9ms** | — | **4.1×**（对当晚槽路对照 623.8ms 则 5.0×） |
| DISTINCT v（探针，100 万组） | 148.4ms | **69.7ms** | — | 2.1×（净成本 24.7 → **6.7ns/行**） |
| DISTINCT g（探针，10 万组） | 33.4ms | 23.4ms | — | 1.4× |

- 基准 **19/19 PASS**（值断言全过）；语料 **154/154 OK ERR 0**、
  行数对 `dag_opt1.tsv` **diff = 0**、墙钟 11.9s。
- **值对账**：三条探针查询的 digest 在 dense 路与槽路（`QSDB_NO_DENSE_GROUP=1`）
  下**逐位一致**；bench A/B 同值（60ms vs 136ms）。
- 本地闸门全绿（fmt + clippy 全 feature 组合 + 94 个测试二进制；
  `http_contract` 的并行端口偶发单跑即过，与 HEAD 同款）。

**途中撞出来的（与十四批同款教训，工具链层面）**：本机 rustfmt/clippy 升级
（rustfmt 1.9.0 / clippy 1.97.0）⇒ HEAD 上 fmt 20 文件、clippy 8 条**既有代码**
全红（上一次闸门绿是旧尺子量的）。处置：fmt / clippy 各自**独立 chore 提交**
（纯格式 / 机械修），不与性能改动混 diff。**下次闸门突然整段红、而红的全是
没碰过的文件 ⇒ 先怀疑尺子换了，再怀疑代码。**

**NULL 语义（测试里钉死的两条）**：`count(DISTINCT v)` 无分组时绑定层
在去重前插 `IS NOT NULL` ⇒ NULL 永远到不了 dense 的 null 槽；把 null 槽真实
走到的是 `count(*) FROM (SELECT DISTINCT v)`（NULL 行是去重行集的一员，+1）。
两形态在测试里都有手工期望值。
